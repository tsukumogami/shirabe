# Phase 6: Loop-back

This phase executes only when the verdict is key `work/review_loopback.md` in
`plan-<topic>` and `/plan`'s keys are there to loop back to (a run on the PLAN
document alone stops at Phase 5). It reads the loop-back findings, extracts
correction hints, removes `/plan`'s keys back to the loop target, increments the
review round counter, and signals `/plan` to re-enter at the target phase.

**Steps:**

1. Read key `work/review_loopback.md` and extract `loop_target` and all
   Category C and Category E `correction_hint` values from `critical_findings`
2. Remove `/plan`'s keys from `loop_target` forward (`koto context remove
   plan-<topic> <key>` for each) — see the key removal sequences below; do not
   remove the loopback key itself. Check each key exists first; one already gone
   counts as removed, so a loop-back repeated after an interruption finishes
3. Set `review_rounds` in key `work/analysis.md` to the loopback key's `round`,
   one more than it was (get it, edit, add it back). This is the loop-back's last
   write: until it lands, a resume reads the loop-back as pending. On
   `loop_target: 1` there is no key to write; Phase 1 writes it.
4. Signal `/plan` to re-enter at `loop_target` (the existing resume logic handles
   re-entry naturally once the keys back to that phase are removed)

**Loopback key lifecycle — important:**

The loopback key is NOT removed during Phase 6 execution. It persists while Phases
1 to 5 regenerate the plan so agents can read correction hints directly from it,
and it is overwritten (not explicitly removed) when the next review run writes its
verdict: a new `work/review.md` (proceed) or a new `work/review_loopback.md`
(another loop-back round).

Since the key outlives its loop-back, its presence can't tell "loop-back needs to
run" from "loop-back already ran". The round numbers can. The verdict is written
with `round: <review_rounds + 1>`, and the loop-back's last write raises
`review_rounds` to that round (step 3, or Phase 1 on `loop_target: 1`). With R the
loopback key's `round` and N the stored `review_rounds` (0 if absent):

```
R == N + 1   → the loop-back is pending: execute it
R <= N       → it already ran; once Phases 1 to 5 have rebuilt the plan, run
               /review-plan for round N + 1 and remove nothing
R > N + 1    → inconsistent state: stop and report R and N
```

Whether `work/manifest.json` exists decides nothing: Phase 5 writes a new one
before the run returns to Phase 6. `/plan`'s Phase 6 Resume Check and this skill's
Resume Logic apply this same rule.

## Key Removal Sequences per loop_target

Remove every listed key from `plan-<topic>` for the given `loop_target`. Always
preserve the loopback key. Remove in the order listed to avoid leaving partial
state. The issue body keys are the ones `koto context list plan-<topic> --prefix
work/issue_` prints.

### loop_target: 1 (re-enter at Phase 1 — Analysis)

Remove all of `/plan`'s working keys:

```
work/dependencies.md
work/manifest.json
work/issue_<id>_body.md        (every issue body key)
work/decomposition.md
work/milestones.md
work/analysis.md
```

Do NOT remove: `work/review_loopback.md`

Phase 1 will produce a new `work/analysis.md`, which becomes the new resume anchor.
Step 3 has no key to write here, so Phase 1 carries the counter: it writes
`review_rounds` in the new key equal to the loopback key's `round` (step 1.4 of
`skills/plan/references/phases/phase-1-analysis.md`).

### loop_target: 3 (re-enter at Phase 3 — Decomposition)

Remove from Phase 3 forward:

```
work/dependencies.md
work/manifest.json
work/issue_<id>_body.md        (every issue body key)
work/decomposition.md
```

Preserve: `work/analysis.md`, `work/milestones.md`, `work/review_loopback.md`

Phase 3 reads the existing `work/analysis.md` and `work/milestones.md`. Re-entering at
Phase 3 does not re-run Phase 1 (Analysis) or Phase 2 (Milestones). The loopback key
is present at this point; a Category E finding's hint (a layer-shaped cut, a first
step that is not a walking skeleton, steps past the horizon) reaches Phase 3 here,
because Phase 3 is where the cut is made again.

### loop_target: 4 (re-enter at Phase 4 — Agent Generation)

Remove from Phase 4 forward:

```
work/dependencies.md
work/manifest.json
work/issue_<id>_body.md        (every issue body key)
```

Preserve: `work/analysis.md`, `work/milestones.md`, `work/decomposition.md`,
`work/review_loopback.md`

Phase 4 reads the existing `work/decomposition.md` and re-generates issue bodies.
The loopback key is present at this point — Phase 4 agents should read it to
retrieve `correction_hint` values for affected issues.

### loop_target: 5 (re-enter at Phase 5 — Dependencies)

Remove Phase 5 and review keys forward:

```
work/dependencies.md
work/manifest.json             (regenerated by Phase 5 from the existing issue body keys)
```

Preserve: `work/analysis.md`, `work/milestones.md`, `work/decomposition.md`, every
`work/issue_<id>_body.md`, `work/review_loopback.md`

Phase 5 re-runs dependency mapping against the existing issue bodies (which are
unchanged) and produces a new `work/dependencies.md`.

## Correction Hints and Phase 4 Injection

When the loopback key contains Category C or Category E findings with non-empty
`correction_hint` values, and `loop_target` is 3 or 4 (both re-enter Phase 4), the
hints must reach the phases that regenerate the plan. Category E hints on a
loop-back to Phase 3 reach Phase 3's step decomposition first (see
`skills/plan/references/phases/phase-3-decomposition.md`, "Review Hints on a
Loop-back"), framed as below; Phase 4 then receives both categories' hints for the
steps they name.

Phase 4's step 4.4 reads the `{{REVIEW_CORRECTION_HINTS}}` placeholder from the
agent prompt template. On a loop-back round, this placeholder is populated from the
loopback key:

1. Read all `correction_hint` values from `critical_findings` where `category` is
   `"C"` or `"E"`
2. For each hint, format it with its `affected_issue_ids`:
   ```
   Issue <N>: <correction_hint text>
   ```
3. Wrap the block with explicit framing before injection into the agent prompt:
   ```
   The following correction hints are from the prior review round. They describe
   what was missing in the previous acceptance criteria. Use them as guidance when
   writing new ACs — do not copy them verbatim.

   <formatted hints>

   End of correction hints.
   ```

The framing wrapper marks the boundary between trusted prompt content and
externally-sourced hint text. This mitigates prompt injection risk from
correction_hint values that might contain instruction-like phrasing.

See `skills/plan/references/phases/phase-4-agent-generation.md` step 4.4 for
where `{{REVIEW_CORRECTION_HINTS}}` is substituted.
