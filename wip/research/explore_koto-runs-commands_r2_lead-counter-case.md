## Findings

**1. Observability: the danger is real and koto's own design doc admits it.** `default_action` output is captured into a `DefaultActionExecuted` event in the JSONL state file, not shown to the agent, unless `requires_confirmation: true` halts the loop (`koto/docs/designs/current/DESIGN-default-action-execution.md:290-306`). The design's own Consequences section flags a risk nobody has fully closed: "action stdout/stderr is persisted in the state file, which is committed to feature branches. If an action command's output contains secrets... those secrets end up in the event log. Mitigation: document that action commands should not produce sensitive output. Truncation at 64KB limits exposure" (`DESIGN-default-action-execution.md:433-438`). That's a documentation-only mitigation for a real leak surface, and it exists precisely because output now lands somewhere nobody routinely reads.

**2. There is a real, filed, damaging incident that matches this exact failure shape.** `BRIEF-skill-preflight-checks.md:5-15` (status: Done) states: "Five filed incidents show shirabe runs going wrong on mismatched hosts, and the worst of them succeeded silently: a koto subcommand that does not exist, its error filtered away, twelve child workflows dispatched against a branch nobody created." Cross-referencing `execute.md:355-384`, this is almost certainly the `koto context set` vs `koto context add` bug documented in the settled-branch block: "There is no `context set`... The old line failed on every run since it was written," caught only because someone added a comparison-based read-back instead of an emptiness test, and because the `2>/dev/null` reflex (needed to suppress koto's noisy migration-skipped stderr spam) had been hiding the real error. That incident happened with the **agent** running the command in prose, and it still cost twelve misdirected child workflows before anyone noticed. This cuts two ways for the exploration: it proves silent-failure cascades are a live risk in this exact system (strong support for caution), but it also proves agent visibility is not a guarantee by itself — an agent can blind itself with a stray `2>/dev/null` just as easily as a gate can. The difference is recoverability: the agent-run version left a paper trail in prose and transcript that let someone diagnose and fix it with a documented rationale (lines 374-384 explain *why* the fix must be comparison-based, not presence-based). A `default_action` version of the same block would reduce that entire diagnosis to a boolean gate result, with no comparable narrative anywhere for a future maintainer to reconstruct the reasoning from.

**3. Adaptation: the two states named as the clearest default_action wins are, on inspection, the ones requiring the most judgment.** `DESIGN-default-action-execution.md:41` names `setup_issue_backed` and `setup_free_form` (both backed by `references/phases/phase-1-setup.md`) as target states. That file's "Create Feature Branch" step is not mechanical — it's a decision tree: reuse `SHARED_BRANCH` if set, reuse the branch if the user said to continue on it, reuse it if already on a feature branch from a prior session, and only create a new branch otherwise. Then "Establish Baseline" says: "Run the project's test suite. **Use project-specific commands from the language skill or CLAUDE.md.**" There is no single command here — the correct command is a per-repo lookup the agent performs by reading CLAUDE.md and the language skill, not a string that can be frozen at template-compile time. A `default_action` can express none of this branching; it can only run one fixed command. Converting this state means either (a) picking one command that's wrong for most repos, reproducing the `[ ! -f go.mod ] || go test ./...` problem already baked into the `tests_passing` gate (`work-on.md:441`, discussed below), or (b) leaving the judgment in the agent's hands, in which case there's nothing left to automate.

**4. The one gate that already does what default_action promises is already brittle across environments, which previews what a wider rollout would look like.** `work-on.md:441`: `tests_passing: command: "[ ! -f go.mod ] || go test ./... 2>/dev/null"`. Because the guard is `[ ! -f go.mod ]`, this gate reports **pass** for any repo without a `go.mod` at the working directory root — a Rust addon, a JS/TS package, a Go monorepo with `go.mod` files only in subpackages, or any repo using `make test`/`cargo test`/`pnpm test` instead. The gate silently no-ops rather than failing loud, meaning "tests passing" can be reported true when no test ever ran. This is a compiled, shipped-as-a-plugin command; shirabe's templates run against "many repos" per the lead brief, and this one gate already demonstrates the exact brittleness concern: a single hardcoded shell string cannot span the actual variety of build tooling in the repos this plugin targets. `default_action` inherits the identical constraint — it's the same `sh -c` mechanism (`koto/src/action.rs:33` and `run_shell_command`, shared by gates and actions per the design's own note: "The shared run_shell_command utility eliminates duplication between gates and actions").

**5. Trust and review surface: default_action genuinely bypasses the permission layer, confirmed at the code level.** `koto/src/action.rs:33` runs `Command::new("sh").arg("-c").arg(command)` directly from the koto binary process — not through the agent's Bash tool. The design doc states this plainly: "Action commands run via `sh -c` with the user's credentials, same as gate commands. The threat model is identical to gates" (`DESIGN-default-action-execution.md:430-431`). This matters independent of session permission mode: when an agent runs `git push` or `gh pr create` itself via the Bash tool, that command text is visible in the transcript and is a discrete tool call a permission policy can key on (allow/deny/ask patterns). When the same operation is baked into a template's `default_action`, it executes as an opaque side effect of one `koto next` call — the user's Bash permission rules for `git push` or `gh pr create` never see it, because it's never a distinct tool invocation. The only safety valve is `requires_confirmation`, and per the design doc, "the template author is responsible for setting this flag correctly; the engine can't determine reversibility automatically" (`DESIGN-default-action-execution.md:442-445`). That moves the decision of what needs a human's eyes from the user's own permission configuration to the template author's judgment at compile time — a real reduction in what a user can catch before an outward-facing action fires, not a hypothetical one.

**6. The koto-protocol self-talk (round 1's 26 sites in `/work-on`): mostly not genuinely automatable, and the clearest counterexample is the settled-branch block itself.** The remaining explicit `koto next`/`koto context add`/`koto context get` calls after a state's `accepts` block exist specifically where the agent must inject judgment output into the state machine (evidence submission) or must defensively verify that a side-effecting call actually took (the settled-branch read-back). You cannot eliminate "the agent calls `koto next`" — that's the fundamental protocol handshake, and koto's auto-advance already chains states with no accepts/no failing gates through a single `koto next` call without any explicit self-talk (per `DESIGN-default-action-execution.md`'s own account of the advance loop). What's left after that automatic chaining is disproportionately the fragile, judgment-bearing bookkeeping — exactly the settled-branch block, whose prose (`execute.md:374-384`) exists *because* a prior silent failure at this exact kind of call site cost twelve misdirected workflows. Converting that block to `default_action` would not remove the risk; it would remove the only artifact (the prose reasoning) that let someone catch and explain the bug. Most of the 26 sites are load-bearing defensive code wearing a "mechanical" disguise, not filler.

**7. Script-per-state (`run-cascade.sh`, `extract-context.sh`) already gets most of the claimed benefit without any koto changes, and is strictly more debuggable.** Both scripts are invoked by the agent via prose + Bash, and both always exit 0 and communicate outcome through a structured JSON contract on stdout that the agent reads and acts on (`extract-context.sh`'s `json_success`/`json_failed` functions; `run-cascade.sh`'s documented `cascade_status: completed | partial | skipped` with a `steps` array, each with `status: ok | skipped | failed` and a `detail` field). This is the "koto runs deterministic work, agent gets judgment" split the exploration wants — achieved via a script whose failure modes are structured, visible in the transcript, gh-authenticatable, greppable in history, and can carry per-step diagnostics no gate exit code can express. Nothing here requires koto's action-execution machinery, its 30-second one-shot cap, its 64KB truncation-into-a-committed-file behavior, or its bypass of the permission layer. Where the scripts fall short — `extract-context.sh`'s `parse_table_agent` and `summarize_with_agent` are literally stubbed to `return 1` with a `# TODO: Implement agent-based parsing in future iteration` — the gap is unfinished script work, not a gap only `default_action` could fill.

**7a. Empirical correction from the orchestrator's probe against shipped koto 0.11.6: the script-per-state pattern is not a portable escape hatch, and this cuts both ways.** `koto next` holds a workspace-scoped lock across its entire advance loop, so any `default_action` that shells out to a koto command touching the session store (`koto context add/list`, `koto status`, `koto workflows`) deadlocks against that lock — it doesn't error, it hangs for the full 30-second one-shot cap and returns `exit_code: -1` with nothing written, even for read-only commands and even against other sessions. Verified directly against the scripts named above: `extract-context.sh:92` runs `echo "$context" | koto context add "$SESSION" context.md` as its storage step, so this exact script, as written, could never be dropped into a `default_action` — it would deadlock every time `--session` is used. `run-cascade.sh` contains no koto calls (confirmed by grep — it only shells to git and the `shirabe` binary), so it has no such obstruction and would convert cleanly if someone wanted to. This is a concrete, present-tense point in favor of the counter-case for the `context_injection` state specifically: the agent-run script pattern works today for exactly the step (`koto context add`) that a `default_action` cannot perform at all, full stop, not merely "with reduced observability." But it undercuts the counter-case's own fallback framing wherever it implied "script-per-state" is a general substitute koto could someday call on its own: any future design that wants koto itself to invoke a script touching the session store inherits the identical deadlock. The pattern's safety is a property of *the agent* being the caller, not of the script contract — so this argument supports "keep `koto context add` steps with the agent" specifically, not "prefer scripts over actions" as a general principle.

**7b. This deadlock is itself the debugging-cost example the observability argument was making abstractly.** A `default_action` wrapping `koto context add` produces: a 30-second stall with no explanation visible anywhere in the interactive session, an `exit_code: -1` that reads identically to "command not found" or any other spawn failure, and a `koto next` response that mentions none of it — the response format has no field for "the action deadlocked against the engine's own lock." A human reviewing a transcript sees a 30-second gap and a bare negative exit code; nothing in the JSONL event log or the `koto next` output says *why*, because the lock contention isn't a shell-level error the `sh -c` wrapper can capture — it's the outer `koto next` process blocking the inner one from acquiring a lock it already holds. This is a self-inflicted failure mode unique to `default_action` (an agent-run `koto context add` from a normal shell completes in ~30ms, per the probe) and it is exactly the class of "opaque failure with no diagnostic surface" the earlier findings warned about in the abstract.

## Implications

- The states the design already targets for `default_action` (`setup_issue_backed`, `setup_free_form`) are the wrong candidates on inspection: their "mechanical" steps are branch-selection and baseline-command judgment calls, not fixed commands.
- `ci_monitor`'s polling loop is the strongest actual candidate: `gh pr checks`/`gh pr view --json mergeStateStatus` is a stable, side-effect-free, environment-independent read, and the template already treats DIRTY vs green as something the agent must interpret via a second gate rather than the first — meaning the judgment already lives in gate *design*, not in the agent watching raw output turn-by-turn. Converting the polling itself (not the interpretation) costs little.
- Any state whose command varies by repo (test runners, build tooling, CI auth) is a poor `default_action` candidate by construction — a compiled template cannot carry "read CLAUDE.md and figure out the right command."
- Any state that writes to a remote (push, PR create/edit, comment) is a poor candidate unless `requires_confirmation: true` is set — and once it is, `default_action` gives nothing an agent-run Bash command didn't already give, since the loop halts and the agent inspects the result anyway.
- The `tests_passing` gate should itself be treated as a warning sign already present in the codebase, not a hypothetical: it's committed evidence that one hardcoded command already silently passes on non-Go repos.
- `context_injection` is now a hard "no," not a soft one: `extract-context.sh` cannot be wrapped in `default_action` at all without deadlocking against koto's own workspace lock (finding 7a). `run-cascade.sh` (used in `plan_completion`) has no such obstruction and is the cleaner conversion candidate of the two scripts, if any script-wrapping conversion is wanted at all.
- The deadlock finding narrows "script-per-state is strictly better" to "script-per-state is better for any step that itself talks to koto's session store" — it is not a general argument that scripts beat actions everywhere; a script with no koto calls (like `run-cascade.sh`) has no structural advantage over a `default_action` running the same script, only the pre-existing observability and permission-surface advantages from findings 1 and 5.

## Surprises

- The strongest counter-evidence wasn't hypothetical brittleness — it was a **documented, closed incident** (`BRIEF-skill-preflight-checks.md`) that appears to be the same bug narrated defensively in `execute.md:374-384`. Finding the incident and the defensive prose written *about* it in the same corpus was not expected going in.
- The design doc for `default_action` itself concedes the permission-bypass and secret-leak points almost verbatim to what the lead asked about ("New risk: action output in event log," "the engine can't determine reversibility automatically") — this isn't an inferred objection, it's the implementers' own risk log, only mitigated by documentation and truncation, not by anything structural.
- The clearest win in the entire investigation (`ci_monitor` polling) is not a "hardcoded command staying with the agent" question at all — the design doc itself says the *right* long-term home for CI monitoring is a typed `integration`, not `default_action`, because `default_action`'s output is just a shell string to parse (`DESIGN-default-action-execution.md`, "Future direction: actions vs integrations"). That weakens even the strongest pro-conversion case: the design's authors already flag `default_action` as the wrong final destination for the one state where it clearly helps today.

## Open Questions

- Would truncating a `default_action`'s working directory strictly to the koto session's repo (closing the unblocked `..` escape from round 1) make the permission-bypass point moot, or is it orthogonal — the escape is a path-traversal concern, the bypass is a command-visibility concern, and closing one doesn't touch the other.
- Is there a middle path where `default_action` is restricted to *read-only, side-effect-free* commands only (mirroring gates), leaving all side-effecting mechanical work — branch creation, pushes, PR edits — to prose + script, which would resolve most of findings 3, 4, and 5 while still capturing the `ci_monitor` win?

## Summary
The enthusiastic case is right for exactly one state today — `ci_monitor`'s polling loop, a read-only, environment-stable command whose koto authors themselves say should really become a typed integration rather than `default_action`. Everywhere else the exploration is looking to convert — branch setup, baseline establishment, the settled-branch self-talk, and now confirmed empirically for `context_injection` — the "mechanical" commands turn out to be judgment calls in disguise, the exact call sites where a filed twelve-workflow incident already happened because output went unwatched, or structurally impossible to wrap (`extract-context.sh`'s `koto context add` deadlocks against koto's own workspace lock inside a `default_action`, hanging 30 seconds for a call that takes 30ms from a normal shell). `default_action`'s own design doc concedes the secret-leak and permission-bypass risks it introduces, mitigated only by documentation. The script-per-state pattern is the better lever specifically where a script talks to koto's session store (`context_injection`); where it doesn't (`run-cascade.sh`), the advantage narrows to the same observability and permission-surface case made throughout, not a categorical one.
