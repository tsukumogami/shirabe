# Lead: What should happen when a koto `default_action` fails, and what is the smallest change that expresses it?

## Findings

**The design never intended raw exit-code checking.** DESIGN-shirabe-work-on-template.md's Decision 6+8 defines the failure path as: "The default action fails or produces unexpected results. koto surfaces the failure to the agent with the state's evidence schema." DESIGN-default-action-execution.md's data flow confirms the mechanism: "engine evaluates gates against the result → on gate failure with accepts block, agent sees action output in fallback directive." Gates, not exit codes, are the intended arbiter of success. `action.rs`'s only real-world worked example (`tests/integration_test.rs:3846`, `template_with_default_action_creating_file`) proves this out: the action is `touch marker.txt`, and the state's `gates.file_exists` (`test -f marker.txt`) is what actually certifies success — not the action's own `$?`. This is a deliberate design choice, and it's the right one: it's what lets a state legitimately use a command like `grep -q pattern file` or `gh pr list | grep -q .` as its default action, where a non-zero exit is a valid, non-failure outcome that a literal "halt on non-zero" rule would misclassify as a failure.

**Two real gaps exist, and both are in the code, not the design.** The design's own account of the mechanism has an unstated assumption: it says "agent sees action output in fallback directive," but nothing actually threads action output into the fallback path.

1. `src/engine/advance.rs:291`, the action-execution match arm for `ActionResult::Executed { .. }` discards `exit_code`, `stdout`, `stderr` outright (`{ .. }` pattern) and falls through to gate evaluation. That's fine per the design (gates are the arbiter) — but it means the action's own output never enters `gate_evidence_map` or any evidence structure. It only survives in the `DefaultActionExecuted` event (`src/cli/mod.rs:4027`), which the fallback directive doesn't read.
2. `StopReason::GateBlocked(BTreeMap<String, StructuredGateResult>)` (`advance.rs:58`) and `StopReason::EvidenceRequired { failed_gates: Option<...> }` (`advance.rs:60`) carry only gate results, and gate results themselves only carry `exit_code` (`src/gate.rs:206-221`, confirmed in round 1). The `NextResponse::GateBlocked` and `NextResponse::EvidenceRequired` variants (`src/cli/next_types.rs:69-84`) have no `action_output` field at all — that field exists only on `NextResponse::ActionRequiresConfirmation` (`next_types.rs:104`, `ActionOutput` struct at `next_types.rs:788`). So even when a gate correctly detects that the action failed, the agent's response carries zero evidence of *why* — no stdout, no stderr, not even the action's own exit code. The agent gets told "gate `file_exists` failed" with no way to see what `touch marker.txt` actually printed.

**A third, narrower gap: states with `default_action` and no gates have zero failure detection.** If a template state declares `default_action` but no `gates`, step 6 (`advance.rs:317` onward) never runs — `template_state.gates.is_empty()` skips the whole block — and the loop proceeds straight to transition resolution regardless of the action's exit code. This is exactly what round 1's empirical probe showed (`exit 3` with a passing gate advanced to terminal): the probe's gate wasn't actually validating the action's effect, so it degenerated to this case. Any deterministic state whose author forgets (or doesn't bother) to write a gate gets silent failure-swallowing, with no safety net.

**`requires_confirmation` is orthogonal and needs no change.** It fires unconditionally at step 5 (`advance.rs:297-310`), before gates run, regardless of exit code — by design, since it's a reversibility gate ("this state does something irreversible, always show the agent before proceeding"), not a failure signal. It composes cleanly with any of the options below because it intercepts before step 6.

**Polling (`ci_monitor`) is unaffected by any of this.** Its execution model (`src/cli/mod.rs:3987-4017`, `execute_with_polling`) loops action+gate-check together internally and only returns once its own gate condition resolves; it always has a gate by construction (the gate is what tells the polling loop when to stop). The `gates.is_empty()` safety-net gap above cannot arise for a polling state in practice.

**Backward-compatibility surface is effectively zero.** `grep -rln default_action` across both `tsuku` recipes/templates and `shirabe` skills returns nothing — the only real occurrences are Rust unit/integration tests inside koto itself (139 hits total in `src/` and `tests/`). No shipped template declares `default_action`. The design doc itself anticipated this: adding a fourth closure parameter "break[s] all existing test call sites (mechanical fix: add a no-op closure)." The same licence applies to reshaping `StopReason`/`NextResponse` further — every call site that would need updating is a test, not a shipped artifact.

## Implications

The right fix is not a new failure-classification mechanism (no `on_failure:` policy field, no `expected_exit_codes:`/`allow_failure:` opt-out, no `StopReason::ActionFailed` that halts independent of gates). All three of those either fight the design's deliberate "gates are the arbiter" model or add schema surface to solve a problem that's actually a plumbing gap. The smallest change that expresses the target design ("koto falls back to giving instructions to the agent... only when commands fail") is:

**A. Thread action output through the existing gate-failure paths.** Add `action_output: Option<ActionOutput>` to `StopReason::GateBlocked` and `StopReason::EvidenceRequired` (changing `GateBlocked` from a tuple variant to a struct variant, or adding a field), populated only when step 5 actually executed an action this iteration (`ActionResult::Executed` or `ActionResult::RequiresConfirmation`... but `RequiresConfirmation` already halts before this point, so only `Executed`). Mirror the field onto `NextResponse::GateBlocked` and `NextResponse::EvidenceRequired` (`next_types.rs:69-84`), reusing the existing `ActionOutput` struct (`next_types.rs:788`) and its `skip_serializing_if`-style omission when `None` — this keeps the JSON shape unchanged for every state that has no `default_action`, so `tests/next_response_baseline.rs` needs new assertions for the with-action case but nothing existing changes shape.
  - Files touched: `src/engine/advance.rs` (capture the `Executed` fields instead of discarding them at line 291, thread through the two `StopReason` construction sites at lines ~434 and ~566-576), `src/cli/next_types.rs` (new optional field + serialize impl), `src/cli/mod.rs` (populate the field when mapping `StopReason` → `NextResponse`, ~line 4200 region).

**B. Give gate-less `default_action` states a safety net.** When `template_state.gates.is_empty()` and the action executed with `exit_code != 0`, synthesize a single `StructuredGateResult { outcome: Failed, output: {"exit_code": N} }` under a reserved key (e.g. `_action`) and feed it through the *existing* `any_failed`/`GateBlocked`/`EvidenceRequired` logic at `advance.rs:400-438` unchanged. This isn't a new stop reason or a new code path — it's making the implicit contract explicit: "no gate means the action's own exit code is the gate." States that already declare gates are completely unaffected (gates still take priority, still get to treat non-zero exits as meaningful signal, `grep -q` still works). States with no gates go from "failures vanish silently" to "failures halt the loop, agent sees the output" (via change A).
  - Files touched: `src/engine/advance.rs` only, inside the `if let Some(action) = &template_state.default_action` block, before falling into step 6.

**Default for a template declaring no explicit policy**: with A+B, the default is "gates decide if present; the action's own exit code decides if not" — no new field on `ActionDecl` is needed to express this, so no default-value question exists at the schema level. This is deliberately not a configurable policy; it's the two cases the design already implies (has-gate vs. no-gate) made complete.

**Interaction with `requires_confirmation`**: none — it still intercepts at step 5 before this logic runs.

**Interaction with polling**: none — polling states always have a gate by construction, so B never fires for them; A already applies equally (polling's terminal gate-fail path goes through the same `StopReason::GateBlocked`/`EvidenceRequired` construction).

**Interaction with gate evaluation ordering**: none — B only adds a synthetic gate result to the same map gates already populate; it doesn't move action execution relative to gates (still step 5 before step 6).

## Surprises

- The design doc's decision outcome section describes the fallback mechanism ("agent sees action output in fallback directive") as if it already works — it doesn't. The gap isn't a missing decision, it's an implemented-halfway decision: the plumbing to carry `action_output` into the failure responses was designed conceptually but never built. `ActionOutput` as a struct only ever reaches one response variant (`ActionRequiresConfirmation`), not the two that are supposed to carry it on the failure path.
- Round 1's "exit 3 advances to terminal" finding is not a bug in the gate model — it's the gate-less-state gap (B) manifesting through a probe whose gate happened to be a no-op check, not a genuine flaw in "gates arbitrate success."
- `StopReason::GateBlocked` is a tuple variant, not a struct variant, unlike every other `StopReason`. Adding a field to it requires converting it to a struct variant, which touches every match arm across `advance.rs`, `mod.rs`, and the ~10 test assertions listed in the grep above (all `matches!(result.stop_reason, StopReason::GateBlocked(_))` or `StopReason::GateBlocked(gate_results)`) — mechanical, but not zero-diff.

## Open Questions

- Should the synthetic `_action` gate key in option B be visible to `when` clauses (i.e., injected into `gates.*` evidence like real gates), so a template author could explicitly route on `gates._action.exit_code` if they want to? Leaning no for the smallest change — it's an internal signal to drive the existing block/require path, not a new authoring surface; exposing it adds schema/semantics scope this lead wasn't asked to design.
- Whether the fallback directive text itself becomes failure-aware (Tier 2 "override and failure guidance" per the parent design) is a separate concern owned by whichever lead covers directive/output routing — this lead's answer supplies the data (`action_output` reaching the response); rendering it into prose is out of scope here.

## Summary
The design's failure model was never "halt on non-zero exit" — gates are the intended arbiter of success (proven by the only real example, `touch` + `test -f`), so no `on_failure:`/`allow_failure:` schema field is needed. The actual gaps are plumbing: `GateBlocked`/`EvidenceRequired` never carry the action's stdout/stderr/exit_code (only `ActionRequiresConfirmation` does), and states with `default_action` but no gates have zero failure detection at all, which is what round 1's "exit 3 auto-advances" probe actually exposed. The smallest fix is two additive, backward-compatible changes with zero real-world template impact: thread `action_output` through the two failure `StopReason`/`NextResponse` variants, and synthesize a fail-on-nonzero-exit gate result only for the gate-less case, leaving every state that already declares gates untouched.
