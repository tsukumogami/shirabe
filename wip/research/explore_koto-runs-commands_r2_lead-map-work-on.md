### Retry-Block Treatment (the 8 near-identical 4-key clearing blocks)

Sites: `verification` (work-on.md:1046-1060, the only one inline in the main template), `analysis`/`scope_changed_retry` (phase-3-analysis.md:80-93), `implementation`/`scope_expanded_retry` (phase-4-implementation.md:150-162), `scrutiny` (phase-4a-scrutiny.md:48-60), `review` (phase-4b-review.md:46-58), `qa_validation` (phase-4c-qa.md:44-57), `finalization`/`issues_found` (phase-5-finalization.md:81-94), plus the three panel "passed" aggregation writes (phase-4a/4b/4c) that use the same `koto context add`+`koto next` shape on the success path.

**Correction from round-lead's empirical probe, folded in here rather than left as my original static-analysis-only claim:** the orchestrator ran real nested-koto-call tests against the shipped `koto 0.11.6` binary and found the 30-second stalls they first attributed to a workspace-scoped lock are actually a `run_shell_command` pipe-buffer deadlock (`src/action.rs`): the child is spawned with piped stdout/stderr, `child.wait_timeout` is called before the pipes are ever drained, so any command whose combined output exceeds ~64KB fills the pipe, blocks the child, and the parent kills the process group at the 30s timeout with the output discarded. It's shared by gate evaluation too, and it's live today independent of `default_action` — `/work-on`'s `tests_passing` gate (`work-on.md:439-441`, `[ ! -f go.mod ] || go test ./...`) can trip it on any repo whose test output exceeds 64KB, turning a real pass into a reported `timed_out` failure. In their test workspace specifically, every session-touching koto command also emits ~106KB of `koto: migration skipped ...` warnings on stderr (one line per legacy session, ~1,250 of them), which is what pushed *every* nested koto call over the line regardless of what it was doing — not a lock. I reproduced this independently before seeing their correction: a self-referential `koto context add <own-session> key` nested inside a `default_action`, with its output explicitly redirected to a file (`>file 2>&1`) to sidestep the pipe, completes in ~0.1s with exit 0 and the corresponding `context-exists` gate then reports empty `blocking_conditions` — confirming there is no lock, matching their corrected P13/P14.

**But I also tested the case their probe didn't cover — a nested `koto next --with-data` that performs a real transition on its own session — and that one is broken for a different, independent reason, confirmed empirically, not just reasoned from source:**

```
outer: koto next selfref4          (state "s", default_action redirects its own output to a file)
action: koto next selfref4 --with-data '{"done":"yes"}'   (nested, output redirected, no pipe issue)
```

The nested call succeeds and genuinely advances the session to the terminal state `e` (`{"action":"done","advanced":true,...,"state":"e",...}` in the redirected log). The **outer** `koto next selfref4` invocation — the one whose `default_action` spawned that nested call — returns `{"action":"evidence_required","advanced":false,...,"state":"s",...}`: it reports the workflow is still sitting in `s` awaiting evidence, when the session has already reached `e`. A follow-up `koto status selfref4` then reports `"workflow 'selfref4' not found"` (a further oddity, possibly from terminal-state cleanup interacting badly with the state the outer call still thinks is live). This matches the causal-ordering mechanism I originally reasoned from `advance.rs`'s step 5 (action) running before step 6-8 (gates/transition) with the outer loop's in-memory `state` never told about the nested transition — the pipe-buffer bug explains *why the first probe saw a stall*, but doesn't explain or fix *this*, which is a genuine result-staleness bug in the self-referential pattern, reachable even with output correctly redirected.

**A third, independent reason still applies regardless of the two findings above:** the blocks' entire safety property is the hard `exit 1` on an unconfirmed clear ("neither `remove`'s status nor `exists` alone is enough" — phase-4a-scrutiny.md:69-73 and identically elsewhere). Per round 1's established fact, **a failing action does not stop the loop and is not reported** — only a gate halts, and `advance.rs`'s `ActionResult::Executed { .. }` branch falls through to gate evaluation regardless of the wrapped exit code. So the clearing-only portion, run as a `default_action`, would have its designed fail-loud behavior silently discarded exactly when it matters.

**Revised verdict: still wave B, not wave A, but for narrower and more precise reasons than I first wrote.** The clearing calls themselves (`koto context remove`/`exists`) are *already* redirected to `/dev/null` in the existing prose, so they don't hit the pipe-buffer bug and mechanically *can* run nested without stalling — that part of my original "unsound" framing was too broad. What actually blocks conversion is (1) `needs-failure-propagation` — a failing clearing step is silently ignored today — and (2) the confirmed staleness bug in the trailing `koto next --with-data`, which cannot be nested without corrupting the outer invocation's own result even when its output is clean. Both still need real engine work; neither is a "just add output routing" fix.

**`gh issue view` caching:** confirmed 4 sites in scope (SKILL.md:264 Begin, SKILL.md:154/work-on.md:896 plan-backed injection, phase-1-setup.md:9 setup, phase-4-implementation.md:93 mid-impl — deliberately fresh, stays). If `context_injection`'s script (or a new `plan_context_injection` script) stored the raw issue body under a dedicated context key at the point of first fetch, `setup_*`'s "Review Issue" read (phase-1-setup.md:9) could become a `koto context get` instead of a fourth `gh` call — but that's a `koto context get` + agent read (still judgment: branch-prefix choice), not a new `default_action`, so it doesn't add a wave-A site on its own; it's a low-effort adjacent win once phase-0 is converted.

### `extract-context.sh` — corrected: a script fix, not an engine gap

The round-lead's probe flagged that `extract-context.sh`'s final step, `echo "$context" | koto context add "$SESSION" context.md` (line 92), doesn't redirect its own output — so wrapped in a `default_action` as-is, in a workspace carrying koto's ~106KB-per-command migration-warning noise (see Retry-Block Treatment above), that nested call hits the pipe-buffer deadlock: 30s stall, exit -1, `context.md` never written, `context_artifact` gate blocked. That's a real defect in treating this as a *free* conversion.

It doesn't move `extract-context.sh` out of wave A, though — the fix is a one-line script change (`... | koto context add "$SESSION" context.md >/dev/null 2>&1`), not a koto engine capability. I'm keeping it in wave A with that caveat attached rather than reclassifying it to wave B, since the blocker is entirely inside a file this exploration's own recommendations would touch anyway, and doesn't wait on koto releasing anything. The underlying migration-warning volume (~106KB/command in a 1,250-session workspace) is still worth fixing on its own — it's what turns *any* unredirected nested koto call into a landmine, not just this one script.

### All 8 existing `type: command` gates, ranked by exposure to the pipe-buffer bug

Per the round-lead's request: which of `/work-on`'s 8 shipped gate commands are plausibly exposed to the `run_shell_command` 64KB deadlock, today, independent of anything in this map. I reread each gate's literal command string with one distinction that matters a lot here and that the probe didn't need to draw out: **`run_shell_command` only captures the stdout/stderr of the top-level `sh -c` process it spawns.** A `git ...` call wrapped in `$(...)` command substitution has its output consumed by the shell *inside* that process before the outer `test`/comparison ever produces anything — so a verbose git command can sit right next to a gate declaration and still never reach the pipe. Only a command whose own top-level stdout/stderr is what's compared (a literal top-level `|` pipe, or a command with no substitution wrapping it at all) is actually at risk.

### `needs-var-plumbing` — a fifth dependency class the lead's four don't cover

Three states (`setup_issue_backed`/`setup_free_form`/`setup_plan_backed`'s baseline test run, `finalization`'s "run complete test suite") have no fixed command to hardcode into a shared template — "use project-specific commands from the language skill or CLAUDE.md" is exactly why they're prose today. This isn't a koto engine gap: `default_action` already supports `{{VAR}}` substitution, so a `TEST_COMMAND`/`VERIFICATION_COMMAND` template variable supplied at `koto init` time (an authoring change to the `/work-on` skill's init call, not to koto) would make these convertible. I'm flagging it separately from `needs-output-routing`/`needs-failure-propagation`/`needs-anchoring`/`needs-transition-hook` because the fix lives entirely in shirabe, not koto.

### A structural gap the map surfaced: state-granularity mismatch

`implementation`'s mid-cycle "re-confirm AC" (`gh issue view`, phase-4-implementation.md:93) and "self-review" (`git diff main...HEAD`, phase-4-implementation.md:124), and `pr_creation`'s pre-PR `git diff main...HEAD` (phase-6-pr.md:9) are individually deterministic, read-only, and would be ideal `requires_confirmation: true` actions in isolation. But `default_action` fires once, at the top of a state's processing, on every `koto next` call into that state — and `implementation` is one state spanning an entire multi-step write/validate/commit cycle. Attaching either command to `implementation`'s `default_action` would run it on the state's *first* entry too, before any code exists, which is wrong. These are not convertible without splitting `implementation` into finer-grained states (a template redesign, wave C) — not a koto capability gap like the other four, and not `needs-var-plumbing` either. Worth its own label if the taxonomy grows a fifth category, but for this map I've placed it in wave C with an explicit note rather than inventing a sixth tag unprompted.

### Quantification

Wave A removes **3 of the ~37 total instruction sites (~8%)**, or **3 of the ~14 MECHANICAL sites (~21%)** — small but genuinely zero-risk. It also removes the single largest *individual* prose block (`extract-context.sh`'s full multi-step procedure description) even though it counts as one site.

Wave B, if fully realized, would touch **8 of the 37 sites** (the retry blocks) but only *shrinks* them (clearing becomes a default_action; the outcome-submission call stays agent-issued) rather than eliminating them, plus **3 more sites** (plan_outline path, 3×baseline/verification commands as a group) contingent on non-koto authoring work. None of wave B is "just flip a flag" — it needs real engine work (`needs-failure-propagation`, an evidence-binding primitive) or real authoring work (new scripts, new template variables) first.

Wave C is unavoidably the majority: all 26 KOTO-PROTOCOL sites, the panel dispatch/aggregation, the two structurally-unreachable read-only commands, and every judgment-substance state.

`phase-2.5-worktree-discipline.md` is confirmed absent from `work-on.md`'s states (no `worktree_discipline_check` state in the frontmatter) and is not counted anywhere in this map — it belongs to `/execute`'s inventory.

## Implications

- The retry-clearing blocks looked like the obvious quick win going into this round, and they're still not one — but the reason shifted under empirical testing. It's not that nested koto calls deadlock (they don't, confirmed twice independently); it's that a nested `koto next --with-data` that performs the real transition leaves the *outer* invocation reporting a stale, wrong result (confirmed empirically: outer says `state: s, advanced: false` while the session has already reached a terminal state), plus the pre-existing silent-failure gap. Building `needs-output-routing` without also solving both of those would still leave these blocks unsafe.
- The three cleanest wins (phase-0 script, plan_context_injection fetch, PR-existence check) share a signature: deterministic, side-effect class read-only-or-idempotent-write, and a *pre-existing* gate or read-only output that already carries the real signal. That's a reusable filter for scanning other skills' templates in later rounds, not just `/work-on`. Two of the three end in a nested `koto context add`, though, which makes them subject to the pipe-buffer bug unless their output is explicitly redirected — a small but real caveat that a naive conversion would miss.
- `staleness_check` and `ci_monitor` (and `implementation`'s three gates) show the target design is already half-built — via `gates: type: command`, not `default_action`. Any recommendation to adopt `default_action` broadly should account for the fact that koto already has a working, lower-risk mechanism for the "run a check, route on its result" half of the problem; `default_action` is only needed for the "run a mutating/store-writing step" half, which is a narrower slice than round 1's raw count suggested. That said, the mechanism isn't as low-risk as it looked going into this round — `tests_passing` (`implementation`'s gate) shares the exact `run_shell_command` codepath the round-lead found deadlocks above ~64KB of output, so a real `go test ./...` pass on a large-enough repo can already report as a false `timed_out` failure today, independent of anything `default_action` touches.

## Surprises

- Terminal states structurally cannot run `default_action` at all (the loop returns at the terminal check, step 3, before action execution, step 5) — this quietly rules out `done_blocked`'s rewind guidance and any cleanup-on-terminal idea before it's worth discussing.
- The scrutiny/review/qa panels' Task-tool dispatch is a wave-C category the lead's brief didn't name alongside `koto init`/`koto next` — but it belongs there for the identical reason: it's not a shell command, so no koto action mechanism, present or future, reaches it.
- `implementation` being a single coarse-grained state (spanning the entire multi-step write/validate/commit cycle, plus a mid-cycle AC recheck and self-review) means two individually-perfect `default_action` candidates (`gh issue view` recheck, `git diff` self-review) are unreachable not because of a koto capability gap but because of where the state boundary sits. Converting them would require redesigning the template's granularity, which is a materially different (and larger) kind of change than anything else in this map.
- `verification` has no `type: command` gate at all today, unlike its neighbors — its "definition of done" procedure is prose-only because the verification-map classification is genuinely data-dependent, not because nobody got around to writing a gate.
- What first looked like a workspace-scoped lock on any session-touching koto command (my own first pass at the retry-block question concluded "no deadlock" from reading the locking code alone, and the round-lead's first empirical pass concluded the opposite — a lock) turned out to be neither: a pipe-buffer deadlock in the shared `run_shell_command`, amplified in mature workspaces by koto's own per-session migration-warning noise on stderr. Static code reading got the "no lock" conclusion right but missed this entirely; the first empirical probe found the real symptom but initially misattributed the cause. Neither method alone was enough here.

## Open Questions

- Is a fifth dependency tag worth adding to the taxonomy for the `implementation`/`pr_creation` state-granularity mismatch, or does it fold into `needs-transition-hook` as currently scoped? I couldn't tell from round 1's definitions alone and didn't want to guess at the intended meaning of a tag I didn't originate.
- Does the target design want a `needs-input-routing` capability (action receives structured data, e.g. three reviewers' JSON, as parameters) to eventually unlock the panel aggregation calls, or is that explicitly out of scope for this exploration's "happy path" framing?
- For wave B's `needs-var-plumbing` items: is threading `TEST_COMMAND`/`VERIFICATION_COMMAND` through `koto init --var` an acceptable authoring pattern, or does the target design want language-skill detection to stay inside the agent's judgment even after other mechanical steps convert?

## Summary

Of `/work-on`'s 24 states, only 3 sites convert to `default_action` today at low risk — the `extract-context.sh` script (once its internal `koto context add` redirects its own output), a not-yet-written github-path fetch for `plan_context_injection` (same caveat), and the `gh pr list` existence check in `pr_creation` — because each already has a pre-existing gate or read-only output carrying the real signal. The 8 retry-clearing blocks, initially the strongest-looking candidate, turn out to be the hardest: nested koto calls don't deadlock (confirmed empirically, twice, after an initial false lead about a workspace-scoped lock that traced instead to a `run_shell_command` pipe-buffer bug shared with gate evaluation), but a nested `koto next --with-data` that performs the retry's real transition leaves the *outer* invocation reporting a stale, wrong result — confirmed by direct reproduction, not just static reasoning — and separately, `default_action`'s silent-failure semantics would defeat the blocks' entire fail-loud safety design even before that. Everything touching Task-tool subagent dispatch (the three review panels), judgment-substance work, and two individually-mechanical-but-structurally-unreachable commands (`implementation`'s mid-cycle checks) stays with the agent, alongside the koto meta-commands — leaving the realistic near-term yield well below the ~37-site inventory's raw count suggested.
