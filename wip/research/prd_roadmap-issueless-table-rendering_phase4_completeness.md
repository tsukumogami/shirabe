# Completeness Review

## Verdict: FAIL

The PRD frames the problem well and closes both of the BRIEF's Open Questions, but several requirements are underspecified in ways that force an implementer to guess at load-bearing values, one pair of requirements contradicts, and two requirements have no acceptance criterion.

## Issues Found

1. **R5 names a "fixed character ceiling" but never fixes it.** Every downstream artifact refers back to it — the third acceptance criterion says "no description cell exceeds the character ceiling", R7's diagnostic fires on it, and Known Limitations depends on it — yet no number appears anywhere in the PRD. An implementer picking 80 and an implementer picking 400 both satisfy the text, and both produce a passing test suite against their own choice. The value is a product decision (how much of a feature body a reader should see in a table cell), not an implementation detail. Fix: state the ceiling as a number in R5, and have the acceptance criterion cite the same number.

2. **R1's definition of the key text is ambiguous and contradicts R13.** R1 says the key column carries "the same text the issueless dependency diagram already uses for that feature's node label". In `crates/shirabe/src/populate.rs:241` that text is `truncate_label(strip_label_decoration(&f.label))` — and `truncate_label` (line 734) does two things beyond stripping decoration: it caps the label at 40 characters at a word boundary, and it rewrites `[` to `(`, `]` to `)`, and backtick to space. The issue-creating renderer, by contrast, uses bare `strip_label_decoration` (line 326). So "the same text the diagram uses" means a truncated, character-substituted label, which directly contradicts R13's "feature labels SHALL round-trip verbatim into the rendered table" and would make a long-labelled feature's key differ from what R3's dependency cells need to reconcile against. Fix: name the transform explicitly — decoration-stripped only, or decoration-stripped-and-truncated — and reconcile whichever is chosen with R13.

3. **The PRD never says whether the description ceiling applies to issue-creating mode.** `concise_description` is the shared helper, called at `populate.rs:210` (issue-creating) and `populate.rs:578` (issueless). R5 says "the description cell SHALL be bounded" without qualifying the mode. R14 pins issue-creating mode's key column, dependency-cell resolution, and validation posture but is silent on its description cells. The BRIEF's Scope Boundary puts "the description-row derivation shared by both populate modes" explicitly *In*. Meanwhile the acceptance criterion "the issue-creating mode's existing tests pass unchanged" pulls toward not touching it. An implementer has to guess whether to bound in the shared helper (both modes change) or at the issueless call site only. Fix: say which, and if issue-creating mode is bounded too, add an acceptance criterion for it and reword R14.

4. **R8 and R12 contradict each other on the comma-bearing-label case, and no requirement says what the cell contains.** R12 requires that a roadmap populated in issueless mode produce no error-level finding from `shirabe validate`. Phase 2 established that `extract_deps` splits Dependencies cells on commas with no escaping and that FC06 is error-level, so a comma-bearing label produces exactly such a finding. R8 only requires a diagnostic and explicitly forbids changing the exit status — it says nothing about what the renderer writes into the cell. Known Limitations claims R8 "surfaces it as a diagnostic rather than silently emitting a document that fails validation", but a diagnostic plus a still-broken cell *is* emitting a document that fails validation. Three behaviors are all consistent with the current text: emit the label anyway, fall back to `F<n>` for that reference, or omit the reference. Fix: pick one, state it as a requirement, and scope R12 to labels that don't trip the limitation.

5. **R4 and R13 have no acceptance criterion.** Nothing in the AC list checks that dependency cells carry no parenthetical annotation (R4), and nothing checks that a label containing a shell metacharacter or backtick round-trips into the table unmodified (R13). R13 is the security invariant; leaving it unverified means a regression in it lands silently. The comma-label criterion tests R8, not R13.

6. **Duplicate feature labels are not addressed anywhere.** Two features sharing a label produce two rows with the same key, which makes every dependency reference to that label ambiguous under R3 and gives FC06 two candidate rows. R2 handles the empty-label edge but not the collision edge. This is more likely than the comma case in a long roadmap (the report that motivated this work covered 21 features). Fix: add a requirement — disambiguate, or diagnose per R8's pattern — and an acceptance criterion.

7. **Done-row strikethrough is not carried into any requirement.** The current renderer wraps every cell of a Done feature's row in `~~` (`populate.rs:584`) and its description row in `~~_..._~~` (line 587); the validator strips those markers in `crates/shirabe-validate/src/table.rs:438`. R1 says the key column "SHALL carry the feature's label" with no mention of the wrapper, so an implementer reading R1 literally could drop it and lose the visual Done signal, and nothing in the acceptance criteria would catch it. Fix: state that existing row decoration is preserved, or add a criterion covering a Done row.

8. **The diagram's node ids staying `F<n>` appears only as prose in D1.** "The `F<n>` handle survives where it was actually load-bearing: the dependency diagram's node ids are unchanged" is an assertion in a trade-off narrative, not a requirement, and no acceptance criterion checks it. Since R1 redefines what `F<n>` means elsewhere in the same renderer, an implementer could reasonably propagate the change into `render_issueless_diagram` and break FC07's node-id expectations. Fix: promote it to a requirement.

9. **Nothing states what happens to roadmaps already populated with `F<n>` keys.** After this change, re-running populate on an existing issueless roadmap rewrites its reserved sections wholesale. Whether that re-population is part of this work, is left to authors, or should happen for the repo's own roadmaps is neither a requirement nor an Out of Scope entry — it is simply absent. The BRIEF's journeys all describe fresh populations, so the upgrade path has no coverage at either altitude. Fix: add an Out of Scope line or a requirement, whichever matches the intent.

10. **The truncation marker and the counting unit are unspecified.** R5 says "an ellipsis marker" without saying whether that is `...` or `…`, and "character ceiling" without saying whether characters means Unicode scalar values or bytes. Both matter for R15's byte-identical determinism criterion and for writing the regression test that the last-but-one acceptance criterion demands. `truncate_label` already sets a precedent (`chars().count()`), which is worth matching explicitly.

## Suggested Improvements

1. **Add a requirement-to-criterion mapping.** Fifteen requirements and fifteen criteria in unlabeled prose form make it hard to see that R4 and R13 fall through the gap. A short table, or `(R5)` tags on the criteria, would make the coverage checkable at a glance and would have surfaced issues 5 and 8 during drafting.

2. **Give R7's and R8's diagnostics a stated shape.** R7 requires the diagnostic to name the feature "and state how the author can control the summary", but the corresponding acceptance criterion only checks that a diagnostic names the feature — the remedy clause, which is the part that makes the diagnostic useful rather than noise, goes unverified. Specifying the message shape (feature label, what happened, the `**Functional outcome:**` remedy) would make both requirement and criterion testable.

3. **Add a user story behind R8.** The four stories cover the label-keyed table, the reviewer, the unsummarizable-body author, and the contributor reading the docs. Nobody in the story list is the author whose label contains a comma or is empty — R2 and R8 exist without a story motivating them, which is why their behavior stayed underspecified (issues 4 and 6). A fifth story covering the author with an awkward label would anchor both.

4. **Fold R11 into the process, not the requirement list.** "The finding SHALL be recorded in the pull request that lands this work" is a delivery instruction rather than a property of the product, and it sits oddly among R1-R10. D4 already carries the substance. This is stylistic, not a gap.

## Summary

The PRD's framing, decisions, and limitations are strong — both Open Questions the BRIEF deferred are closed with recorded reasoning (D1 for the key-column contradiction, D2 for description bounding), and the Out of Scope section is specific enough to hold. The failure is at the requirement level: the description ceiling has no value, the key column's exact text is defined by reference to a helper that truncates and substitutes characters in a way R13 forbids, the ceiling's applicability to issue-creating mode is left open despite the helper being shared, and R8 and R12 disagree about whether a comma-bearing label may produce a document that fails validation. Two requirements have no acceptance criterion, and duplicate labels, Done-row strikethrough, and the fate of already-populated roadmaps have no coverage at all.
