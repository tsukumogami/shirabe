### The `multi-pr` PLAN mode

- **Declared:** `execution_mode` is a PLAN frontmatter field with a closed enum `{single-pr, multi-pr, coordinated}`, defined in `skills/plan/references/plan-format.md:42-45`.
- **Owned by:** `/work-on`, not `/execute`. Confirmed three independent ways:
  1. `skills/work-on/SKILL.md:125-135` — "`single-pr` or `coordinated`" hand off to `/execute`; "`multi-pr`" runs in place inside `/work-on`.
  2. `skills/explore/SKILL.md:55,70` and `crystallize-framework.md:36-38` — "a `multi-pr` PLAN does not qualify [for `/execute`]; `/execute` refuses that mode."
  3. `docs/designs/current/DESIGN-execute-skill.md` Decision Outcome — "multi-pr: not owned by `/execute`; the `/work-on` dispatcher runs it in place, one issue at a time, against the repo-persisted PLAN."
- **What would change if the boundary moved:** Folding `/work-on` into `/execute` removes the one case (`multi-pr`) where `/execute`'s finished-plan machinery is deliberately *not* used, so `/execute` would need to gain a "run in place, one issue at a time, no shared branch, no cross-issue carry-forward" mode of its own — currently a `/work-on`-only code path (`skills/work-on/SKILL.md:132-136`). Migrating finishing logic into `/work-on` instead leaves multi-pr's ownership unchanged but raises the question this table flags repeatedly: multi-pr chains currently have **no cascade step at all** in `/work-on`'s own koto template (confirmed empty grep for "cascade" in `skills/work-on/koto-templates/work-on.md`), so "finishing logic in `/work-on`" is not a relocation for multi-pr — it would be new capability, not moved capability.

### `/plan` and `/scope` outputs

- Neither `/plan` nor `/scope` emit a PLAN field that *names* an executor. `execution_mode` (`single-pr`/`multi-pr`/`coordinated`) is a mode, not a skill name — `plan-format.md:42-45` is explicit that "It does **not** determine [tracking level]," and nothing in `plan-format.md`'s Required/Optional field list (searched the whole file) contains a field like `executor:` or `entry_point:`. The routing from mode to skill is entirely done by prose in `/work-on` and `/execute`'s own SKILL.md files and by `/explore`'s routing tables — not by anything the PLAN document itself carries. This means a boundary redraw does not require a PLAN schema migration; it only requires updating the prose that interprets `execution_mode`, in exactly the files tabled above.

### `shirabe validate` and lifecycle/merge-gate checks

- `--lifecycle` / `--lifecycle-chain` (implemented in `crates/shirabe-validate/src/lifecycle.rs`) are mode-agnostic in the Rust code itself — they check chain *state* (PLAN status, upstream transitions), not which skill produced that state. The assumption that ties them to `/execute` specifically lives entirely in **documentation layered on top**: the doc comments in `main.rs`/`lifecycle.rs` (stale, name `/work-on`) and the design section in `skills/execute/SKILL.md:564-649` (current, names `/execute`).
- `--merge-gate` and `--coordination-body` (`skills/execute/SKILL.md:61,308-375,525,699-701,760-761`) are used exclusively by `/execute`'s `coordinated` mode for cross-repo merge-last sequencing. Nothing in `/work-on` calls either flag (confirmed: no `--merge-gate` or `--coordination-body` hits anywhere under `skills/work-on/`). These are pure `/execute`-mode machinery with no multi-pr equivalent, because multi-pr issues are independent by design (no merge-order DAG to gate).
- **Net finding:** the CLI itself has no hardcoded skill-name coupling — it is agnostic. All the coupling other than the stale doc comments is in the two skills' own SKILL.md prose and the tests that assert against specific script paths (`assert-child-template.sh`, `check-bash-floor.sh`'s suite table). This matters for pricing either direction: the CLI binary itself would need zero changes for a boundary redraw; the cost is entirely in skill markdown, koto templates, shell scripts, CI workflow `paths:` filters, and evals.

## Implications

- The cost of either direction is dominated by **rename/re-prose work across ~15-20 files**, not by any single hard architectural blocker. Nothing found makes either direction structurally impossible.
- **Folding `/work-on` into `/execute`** breaks one explicit, deliberately-written prohibition (`phase-5-produce-file-an-issue.md:32`, "Do not name `/execute` here: it takes a PLAN path and has no issue mode") and retires an entire CI-tested cross-skill contract (`assert-child-template.sh` + its test + its silent path-coverage gap in `check-execute-scripts.yml`). It also directly contradicts a prior explicit design decision (`DESIGN-execute-skill.md` Decision 2's rejected "Routing — hard-remove `/work-on` PLAN input," rejected specifically because it "breaks existing invocations and `/work-on`'s own evals" — the same argument would need to be re-litigated in reverse).
- **Migrating finishing logic into `/work-on`, keeping it standalone**, is arguably the smaller documentation-surface change (fewer explicit prohibitions to invert), but it inherits an unresolved gap this research surfaces independent of either direction: **multi-pr chains, which are `/work-on`'s own exclusive territory today, have no cascade/finalization-guard mechanism at all.** Whoever picks this direction is not just relocating `/execute`'s existing cascade machinery — for the multi-pr case they are building the first version of it, since `/work-on`'s template never called it.
- Either direction should budget time to **fix the "work-on cascade" naming fossil** (`skills/roadmap/SKILL.md` x5, three Rust doc comments, one already-wrong extension README path) as part of the same PR, since a boundary redraw is the natural moment to correct comments that already describe the *previous* boundary rather than leaving three generations of naming in the tree.

## Surprises

1. **The repo has already done this exact move once, in the other direction, and left naming fossils behind.** `docs/designs/current/DESIGN-execute-skill.md` documents extracting the plan-level orchestrator, `work-on-plan.md`, and `run-cascade.sh` out of `/work-on` and into the newly created `/execute`. That migration is why `docs/decisions/DECISION-cascade-trigger-mechanism-2026-06-06.md` (which predates the split and calls the mechanism "the work-on cascade" throughout) is now describing something that lives under `skills/execute/`. The term "work-on cascade" survived the move into five places in `skills/roadmap/SKILL.md` (lines 78, 83, 315, 319, 350) and three doc comments in the Rust CLI (`crates/shirabe/src/main.rs:277-278,286-288,1284-1285`; `crates/shirabe-validate/src/lifecycle.rs:1681`), none of which were updated when the cascade moved.
2. **One of those stale references cites a path that has never existed on disk.** `crates/shirabe-validate/src/lifecycle.rs:1681` says "The cascade script in `skills/work-on/scripts/run-cascade.sh`" — verified via `find . -iname "run-cascade*"` that this file has only ever existed at `skills/execute/scripts/run-cascade.sh`. Whether this is a copy-paste artifact from drafting the comment before the file was placed, or a comment that was simply never touched during the `DESIGN-execute-skill.md` migration, it's a live inaccuracy in shipped source today, independent of this exploration.
3. **`.claude/shirabe-extensions/README.md` and the file it documents (`work-on.md`) disagree with each other on a path.** `work-on.md` (the file actually `@`-imported into `/work-on`'s context) correctly says the default verification fallback includes `skills/execute/scripts/run-cascade_test.sh`. The README describing that same file says `skills/work-on/scripts/run-cascade_test.sh` — a path that does not exist. Since the README is explicitly "not imported" (per its own first paragraph) it doesn't affect runtime behavior, but it would mislead a human reader trying to understand shirabe's own verification map.
4. **`skills/roadmap/SKILL.md` may be describing a capability multi-pr chains don't actually have.** It claims (line 350) that for a ROADMAP-rooted multi-pr chain, "the final per-feature PR in the chain runs the work-on cascade." But `handle_roadmap_deletion` (the function that actually deletes a Done ROADMAP) exists only inside `skills/execute/scripts/run-cascade.sh` and is invoked only from `skills/execute/koto-templates/execute.md:706`. `/work-on`'s own koto template has zero cascade references. If this claim is accurate in practice, it must be happening through some manual/fallback path ("the implementing agent following the lifecycle script," per `plan-format.md:341`) rather than an automated one — which would mean ROADMAP deletion for multi-pr chains is not actually automated today, contrary to what `roadmap/SKILL.md` states as fact.
5. **The `check-execute-scripts.yml` CI workflow does not trigger on changes to the file its own test asserts against.** `assert-child-template_test.sh` (run by that workflow) exists specifically to catch a broken `skills/work-on/koto-templates/work-on.md` path, but the workflow's `paths:` filter is `skills/execute/scripts/**` only — a PR that renames or moves `work-on.md` without touching anything under `skills/execute/scripts/` would not re-run this check on that PR (it would presumably still fail on a later PR that does touch `skills/execute/scripts/**`, or on `main` after merge via other CI, but not synchronously with the breaking change).
6. **`/scope`'s test fixtures already contain a fictional PRD/DESIGN/PLAN about fixing state-shape violations shared between `/work-on` and `/execute`'s templates** (`skills/scope/scripts/testdata/prd.md.fixture:305,350`; `design.md.fixture:693,722,910`). These are synthetic test data for `/scope`'s own scripts, not live specs, but their content is suspiciously on-topic for this exact exploration — worth a glance if anyone wants a second, independently-written description of the same two templates' inconsistencies.

## Open Questions

- Is the `roadmap/SKILL.md` claim about multi-pr ROADMAP deletion (line 350) actually exercised anywhere (an eval, a test, a real repo), or is it aspirational prose that has never been true since the `/execute` split? This determines whether "give multi-pr a finalization/cascade path" is in scope for this redraw or is a pre-existing, separately-filable defect.
- Does the R5 Finalization-Not-Done Guard (`skills/execute/SKILL.md:564-649`, wired via `.github/workflows/lifecycle.yml`) actually cover multi-pr chains today via its whole-tree `--lifecycle .` scan, even though the *prose* describing the guard is written entirely in terms of `/execute`'s cascade? If the CLI-level mechanism is mode-agnostic (as the CLI-source review suggests), the guard may already protect multi-pr chains mechanically while the documentation simply fails to say so — in which case this is a documentation gap, not a functional one.
- If `/work-on` folds into `/execute`, does `/explore`'s "file an issue, then `/work-on <issue-number>`" recommendation (label-reference.md, phase-5-produce-file-an-issue.md, explore evals) get replaced by "file an issue, then `/execute <issue-number>`," or does `/execute` need an issue-number mode distinct from its PLAN-path mode? The explicit prohibition at `phase-5-produce-file-an-issue.md:32` ("`/execute` accepts nothing else [but a PLAN path]") suggests the current authors considered and rejected an issue-accepting `/execute` — that rejection's reasoning (if recorded anywhere) would bear directly on this choice, but I found no DECISION or BRIEF file arguing it explicitly; it reads as an assumed constraint rather than a debated one.

## Summary
The boundary is load-bearing in roughly twenty places — routing prose in `/explore`, `/plan`, `/scope`, and `/roadmap`, a hardcoded cross-skill path assertion in CI (`assert-child-template.sh`), a bash-floor suite table, a merge-gate whose own comments name `/execute` specifically, and eval scenarios in four skills that assert the current hand-off shape — so either direction is a real, multi-file migration, not a rename. The bigger finding is that this exact move already happened once before (`/execute` was carved out of `/work-on` per `DESIGN-execute-skill.md`), and that migration left stale "work-on cascade" naming behind in `roadmap/SKILL.md`, three Rust doc comments, and a wrong path in `.claude/shirabe-extensions/README.md`, one of which cites a script location that has never existed on disk. The open question with the most leverage is whether `/work-on`'s multi-pr mode already has *any* automated finalization path today, because if it doesn't, "migrate finishing logic into `/work-on`" isn't a relocation for that mode — it's new construction, and the roadmap skill's claim that ROADMAP deletion already works for multi-pr chains needs to be checked, not assumed.
