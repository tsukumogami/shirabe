# Architecture Review

## Verdict: FAIL

The chosen structure (positional key table, one bounded derivation, a pure warnings function) is the right shape and most of its factual claims check out, but two PRD requirements have no correct mechanism behind them (R9's dependency ordering, and R17's diagnostic being emitted from a mode that has no fallback), and one component change as specified will panic on input R7 requires it to drop.

## Incorrect Claims

1. **"Comparison for the duplicate check is on the stripped label, byte-equal ... the same equality FC06 applies when it matches a dependency token against the key set."** FC06 does not compare stripped labels. `check_fc06` (`crates/shirabe-validate/src/checks.rs:637`) builds its key set from `Row.key`, which `classify_row` fills via `extract_entity_key` (`crates/shirabe-validate/src/table.rs:414`): strikethrough is stripped, an `ISSUE_REF_PATTERN` match anywhere in the cell *replaces* the whole key with `#N`, and otherwise `normalize_feature_ref` unwraps `[label](url)` to `label`. Dependency tokens go through `extract_deps` with the same normalization. So two labels that are byte-distinct after `strip_label_decoration` (`[Foo](#a)` and `Foo`) collapse to one FC06 key, and a label containing `#12` becomes the key `#12`. The design's predicate is *stricter than nothing* but is not the validator's equality, so the stated guarantee ("the fallback and FC06 agree about what counts as a duplicate") does not hold. The practical fallout is ambiguity rather than an error-level finding — both sides normalize identically, so FC06 still resolves — but the rationale for byte-equality should be restated honestly or the predicate should normalize the same way.

2. **"`render_deps_cell` ... resolves each `Feature N` to `keys[id-1]`."** The current function does not index; it does a guarded lookup, `features.iter().find(|f| f.id == id)` (`crates/shirabe/src/populate.rs:834`), and silently drops an id that names no feature. That drop *is* R7/AC10. Implemented literally as `keys[id-1]`, a roadmap with `**Dependencies:** Feature 99` panics instead of dropping the token. The rewrite is only equivalent as `keys.get(id - 1)` or by keeping the `find` and indexing off the found feature's position.

3. **"the two passages in `skills/roadmap/references/roadmap-format.md`."** Three passages present `F<n>` as the *table row key* and all three fall under R21: lines 184-186 (the Reserved Sections `## Roadmap Issues: optional` bullet), lines 370-372 (the FC16 paragraph — "`## Roadmap Issues: optional` with `F<n>` rows"), and lines 374-380 (the "Dependencies cells in issueless mode" section). Line 222 also says `F<n>`, but that one is about diagram nodes and correctly stays under R19.

Claims that were checked and are correct: every cited line number (`populate.rs:73`, `:94`, `:153`, `:187`, `:556`, `:766`, `:831`; `table.rs:444`; `main.rs:466`); `first_sentence` returning the whole input with no terminator (`populate.rs:806`); `Feature.id` being a positional 1-based counter assigned by `parse_features` regardless of the heading's stated number (`crates/shirabe-validate/src/features.rs:80-105`), which makes `keys[id-1]` sound *as an alignment*; `references/issues-table.md:136-146` already specifying the feature label as the roadmap key form, so it needs no edit; "four existing issueless unit tests" encoding `F<n>` (`populate.rs:1270`, `:1304`, `:1375`, `:1663`, plus `bare_feature_deps_strips_to_keys_or_none` at `:1257` which dies with the function); and the empty-body reproduction, which I ran against `target/debug/shirabe` on a two-feature fixture whose second feature has no body — it renders `| __ | | | |` and `shirabe validate --visibility=public` returns exactly two FC05 errors and exit 2. The placeholder row `| _No description in the feature body._ | | | |` does satisfy `is_italic_cell`, including under strikethrough (`strip_strikethrough` runs first in `classify_row`).

Also verified, and worth recording because the design leans on it without saying so: FC07 is a complete no-op over issueless output. `node_set_pass_roadmap`, `edge_pass_roadmap`, and `class_vs_status_pass` all filter on `ISSUE_KEYED_NODE_ID` (`^I[0-9]+$`) on the diagram side and on `#N` tokens in the Issues column on the table side, so `F<n>` nodes and `needs-*` Issues cells contribute nothing to any of the three passes. R19 and R3 therefore cannot collide, and no FC07 notice is reachable. This is load-bearing for R22 and deserves a sentence in the design rather than being left implicit.

## Issues Found

1. **`render_warnings` printed from `run_inner` emits diagnostics that are false in issue-creating mode.** The component table has both `run_issueless` and `run_inner` printing the output of a single `render_warnings(&features)`, and that function emits both truncation lines (R16) and key-fallback lines (R17). But Decision C2 and R24 keep issue-creating mode on plain stripped labels — no fallback happens there. A roadmap with a comma in a label, populated *with* issues, would print `warning: feature 4 "...": key falls back to F4 (label contains a comma)` while the table it wrote carries the comma-bearing label. That is worse than silence: it tells the author the tool did something it didn't do, for the one mode where the resulting row genuinely can break FC06. Fix: split the function (`truncation_warnings(features)` and `key_fallback_warnings(features)`), print both from `run_issueless` and only the truncation half from `run_inner` — or, reading the PRD's requirements preamble strictly ("every requirement applies to `--no-issues` unless it names issue-creating mode"), print nothing from `run_inner` and say so.

2. **R9's "resolved local keys first, *in feature order*" has no mechanism, and cannot get one without breaking R24.** `render_deps_cell` pushes resolved keys in the order `feature_refs_in` returns ids, and that function documents and tests first-seen *source* order (`populate.rs:936`, test at `:1553`). `**Dependencies:** Feature 3, Feature 1` renders `Metrics, Foundation`, not feature order. The design reuses the function unchanged and never mentions ordering. The awkward part is that fixing it is not free: R9 is issueless-scoped, R24 freezes issue-creating mode's Dependencies-cell resolution byte-for-byte, so a sort inside the shared function changes the frozen mode's output for any out-of-order dep list. This is a genuine strain on Decision A2/C2 — the shared renderer cannot satisfy both — and the design should either sort the ids before the call in the issueless path only (cheap, keeps the function shared and pure), or record that R9's ordering clause is not being implemented and why.

3. **The `keys[id-1]` formulation drops R7.** Covered as incorrect claim 2; restating it as an issue because it is the one change in the component table that can turn a rendering defect into a panic. Specify `keys.get(id - 1)` explicitly in the design, and add the AC10 case (`Feature 99` in a five-feature roadmap) to the issueless test set, not just the issue-creating one.

4. **A fallback key can collide with a literal label.** `key_fallback_reason` tests emptiness, `,`, `|`, and duplication *among stripped labels*. It does not test whether the `F<n>` it is about to mint collides with another feature's label. A roadmap where feature 1 is labelled `F2` and feature 2 has an empty label produces two rows both keyed `F2`: FC06 still passes (the key exists), but a dependency on either is ambiguous, which is exactly the failure the duplicate clause exists to prevent. One extra clause in the predicate — fall back also when the stripped label equals any other feature's `F<n>` form — closes it, and the two-consumer structure means the warning follows for free.

5. **Documentation scope is short by one file and one passage.** Beyond the roadmap-format.md undercount (incorrect claim 3), `skills/roadmap/SKILL.md:358-360` describes issueless mode as rendering "a feature-keyed table ... with Dependencies cells as bare feature keys" — the rule being replaced. R21 doesn't name SKILL.md, but the design's own stated outcome is "the three documents describing the table agree," and after step 4 that file still disagrees. The design's component table also omits the in-file doc comments that assert the old rule and must move with the code: the `run_issueless` doc (`populate.rs:147-152`), the `render_issueless_table` doc (`:176-186`, which spells out "The first column carries the feature key (`F1`, `F2`, ...) so the row key equals the bare dependency token"), and `render_deps_cell`'s own heading, which calls itself "an issue-creating-mode Dependencies cell" and stops being true the moment both modes call it.

6. **Step 2 does not compile as scoped.** The step lists four issueless tests to update and the deletion of `bare_feature_deps`. It misses `render_deps_cell_maps_features_to_row_keys_and_keeps_cross_repo` (`populate.rs:1582`), which calls `render_deps_cell(&f4.dependencies, &features)` directly and needs the new third argument, and it should say the `bare_feature_deps_strips_to_keys_or_none` test (`:1257`) goes with the function. Step 1 I checked against every existing assertion and it is genuinely green: no current test asserts `concise_description("")` or feeds a body long enough to truncate. Step 3 is also safe — the three existing `.stderr(contains(...))` assertions in `crates/shirabe/tests/populate_cli.rs` (lines 342, 457, 475) are substring predicates on error paths, so added warning lines don't disturb them.

7. **R22's "unconditionally" is not established by construction, and the design's mitigation won't find the gap.** The placeholder fixes the empty case, but a feature body whose derived text *begins* with `_` renders `| __text..._ | | | |`, which `is_italic_cell` rejects for exactly the same reason `__` was rejected, re-opening the FC05 failure this work exists to close. The PRD records the `|`-in-body case as a known limitation but says nothing about a leading underscore. Round-trip tests over four hand-picked fixtures cannot cover it. This one is cheap to close and, unlike the label case, is not blocked by R23 — R23's verbatim guarantee covers label text reaching the key column, not body text reaching a description cell, so neutralizing a leading `_` (or escaping `|`) in the derived description is permitted. Worth an explicit decision either way rather than silence.

8. **Two behaviour changes are missing from Consequences.** Removing `bare_feature_deps` does not lose anything, but it *gains* something the design never mentions: cross-repo tokens. `bare_feature_deps` deliberately collapses `tsukumogami/koto#65` to `None` — its doc comment (`populate.rs:283-286`) and its test both record that as intentional — while `render_deps_cell` preserves it verbatim. That is R6 compliance and it's the right outcome, but it is a user-visible change to every issueless roadmap with a cross-repo dependency and belongs in the Positive list next to the key-column change. Separately, on strategy-derived roadmaps (`### ED1:` headings, which `parse_features` supports and numbers positionally), an `F<n>` fallback key names a numbering scheme that appears nowhere in the document. Cosmetic, but the `F<n>` form is being defended as "the handle that survives," and on those roadmaps it is a handle to nothing.

## Strawman Check

- **Decision A (key resolution site):** genuine. A1's rejection rests on a real property — R2's uniqueness clause makes resolution a function of the whole list, so both call sites would rebuild the same index — and A3's cross-crate objection is correct (`Feature` lives in `shirabe-validate` and the validator consumes it). Missing the cheap middle option: a `KeyTable` newtype or a resolver closure, either of which would have surfaced the positional-alignment hazard that issue 3 is about.
- **Decision B (diagnostics):** genuine. B1 and B2 are both options a competent implementer would actually reach for, and B3's cost (double derivation) is admitted rather than hidden. Missing the idiomatic `&mut Vec<String>` out-parameter, which beats B2 on churn and B3 on double work — its absence is what leaves the double derivation as an accepted cost.
- **Decision C (scope of the fallback):** the most honest of the three. C1 is argued on merit and rejected explicitly on PRD scope with the one-line seam documented; C3 is closer to a strawman (nobody duplicates a renderer) but it is the real alternative to threading a parameter, so listing it is fair.

## Summary

The architecture is close to right and most of it survives checking: the key table is positionally sound because `parse_features` numbers features 1..n regardless of heading text, `render_table` passing plain stripped labels really does keep issue-creating output byte-identical, the placeholder really does clear the FC05 finding I reproduced, and FC07 is structurally unreachable for issueless output so R19 and R3 cannot collide. What fails is coverage of the PRD. R9's feature-order clause has no mechanism and cannot get one inside the shared renderer without violating R24 — that tension needs deciding, not inheriting. R17's diagnostic, as wired, fires from a mode that per R24 never falls back, telling authors the tool did something it didn't. And `keys[id-1]` as written converts R7's silent drop into a panic. Fix those three, extend the doc edits to SKILL.md and the third roadmap-format.md passage plus the module's own doc comments, add the `F<n>`-collides-with-a-literal-label clause and a decision on the leading-underscore description, and the design is sound.
