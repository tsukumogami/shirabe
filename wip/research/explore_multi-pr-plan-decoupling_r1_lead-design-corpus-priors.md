# Lead: What has the existing design corpus already decided about PLAN execution modes and GitHub issue/milestone coupling?

## Findings

### The current fused rule, and where it actually lives

The single-pr/multi-pr decision is not governed by any of the eight designs
named in the assignment brief. It's governed by **`docs/designs/current/DESIGN-roadmap-plan-standardization.md`**, Decision 6 ("Surfacing the single-pr/multi-pr decision and the value guard") — a design not in the original reading list but the actual parent of the logic now sitting in `skills/plan/SKILL.md` ("Execution Mode Decision") and `skills/plan/references/phases/phase-3-decomposition.md` step 3.6.

Decision 6's problem statement names the exact defect: *"The single-pr/multi-pr decision is buried and mechanism-driven... Its 'Roadmap input forces multi-pr' row reaches the right outcome by mechanism, not by the usable-value principle."* Its chosen fix: lift the rule onto the SKILL surface, "de-conflated from the decomposition-strategy decision" (work-slicing vs. delivery-slicing), and re-anchor the roadmap-is-multi-pr outcome on **value** rather than **mechanism**: *"A roadmap input is always multi-pr — not because the input is a roadmap, but because each feature is a cohesive deliverable that lands observable incremental value on its own (P1 again)."* (`skills/plan/SKILL.md:160-163`, restating Decision 6.)

This is a real prior decision, and it is a partial answer that stops short of the current proposal. It de-conflated *decomposition strategy* from *execution mode*, and re-anchored the roadmap special-case from "mechanism" to "value." But it did **not** de-conflate the three things the current exploration wants split apart: whether a plan **can** land in one PR, whether it **should**, and how work is **tracked**. All three still live inside one binary `execution_mode` decision, driven by one value principle (P1, "usable value is the unit of work," `references/workflow-principles.md`), with no repo-level preference surface. The live rule, verbatim from `skills/plan/SKILL.md:144-163`:

> "**Default: single-pr.** ... **Escape to multi-pr only when a named condition forces it:** 1. A hard constraint forces multiple PRs... 2. Each PR is independently useful... A roadmap input is always multi-pr..."

Condition 1 ("hard constraint forces multiple PRs") is close to what the exploration calls the **can** gate — near-deterministic, decomposition-derived. Condition 2 ("each PR is independently useful") and the roadmap default are closer to the **should** gate — a judgment call the current design treats as intrinsic to the decomposition rather than as an org preference. There is no notion of **tracking** (issues/milestones) as a separate axis anywhere in this rule; multi-pr and "creates GitHub issues + a milestone" are the same event by construction (see next section).

**Status: decided and implemented**, current as of the most recent /plan-area work. Nothing in the corpus has revisited it since.

### Multi-pr is definitionally coupled to issue/milestone creation, and that coupling is why the human-approval gate exists

`docs/decisions/DECISION-multi-pr-posture-detection-2026-06-06.md` states the coupling as background fact, not as something under debate: *"multi-pr requires human approval (GitHub issues + milestone are created on the transition), single-pr auto-fires when `/shirabe:plan` finishes authoring."* The Draft→Active gate is auto for single-pr and human-approved for multi-pr **because** multi-pr's transition is the moment GitHub issues and a milestone get created — a remote, side-effecting action. Cardinality (single-pr vs multi-pr) and tracking (GitHub issues/milestone) are fused at the mechanism level: today there is no way to get multi-pr cardinality without also getting issue/milestone creation, or vice versa.

This is the strongest piece of evidence that the current proposal is a real decoupling, not a restatement of something already separated. If tracking becomes a repo-level, independently-set preference, the Draft→Active approval-gate logic (asymmetric by mode) built on this design would need to move to being keyed on "does this run create issues" rather than "is this multi-pr" — those are currently the same predicate and the decision record treats them as such.

**Status: decided and implemented.** No design revisits this coupling or proposes decoupling it.

### The closest prior instance of "tracking is optional, decoupled from a CLAUDE.md-level preference stack" is scoped to ROADMAP issue-filing, not PLAN cardinality

`docs/designs/current/DESIGN-roadmap-issueless-preference.md` (superseded default per `docs/decisions/DECISION-populate-issueless-default-2026-08-10.md`, and refined by `docs/designs/current/DESIGN-populate-issueless-default.md`) is the one place in the corpus that already does almost exactly the pattern the exploration wants: a `## Roadmap Issues: optional|required` CLAUDE.md header, resolved on a `flag > CLAUDE.md-header > default` stack, that governs **whether GitHub issues get filed**, fully decoupled from the validator (which never gates on it) and largely decoupled from the roadmap's structural shape. The full stack, current default: `flag > ## Roadmap Issues: header > issueless default` (`references/fixes/claude-md-conventions.md:64-74`). Automatic (non-human-invoked) population is *always* issueless regardless of the header — only a human-typed `/roadmap populate` without a flag consults the header.

But this preference governs **ROADMAP feature population** (one issue per roadmap feature, filed by `shirabe roadmap populate`), not **PLAN execution_mode** (single-pr/multi-pr/coordinated for the implementation layer). It's a genuine precedent for the *mechanism* the exploration wants (a named CLAUDE.md header, flag>header>default resolution, "the automatic run is always the safe mode regardless of header," a superseding decision record when the default flips) but it does not touch the PLAN-level cardinality question at all. Grepping `references/fixes/claude-md-conventions.md` (the canonical list of every convention header) confirms there is **no existing header for single-pr/multi-pr preference** — only `Repo Visibility`, `Planning Context`, `Default Scope`, `Execution Mode` (which is autonomy: auto|interactive, unrelated to PR cardinality despite the name collision), `Roadmap Issues`, and `Release Notes Convention`. The exploration's "should" and "tracking" gates, if bound to repo-level preferences, would be genuinely new headers, not a rediscovery of one that exists.

**Status: decided and implemented, but scoped to a different artifact (ROADMAP feature issues, not PLAN execution_mode).** Directly reusable as mechanism precedent; does not pre-empt or answer the current question for PLAN cardinality.

### `coordinated` mode is a live precedent for — and a live rejection of — bundling a tracking axis onto cardinality via a flag

`docs/designs/current/DESIGN-capstone-orchestration.md` Decision G explicitly confronted a structurally similar question and answered it the *opposite* way from what the current exploration proposes. Coordinated mode adds cross-repo tracking machinery (a coordination PR, a two-node merge-order DAG, gate nodes) on top of multi-pr cardinality: *"A coordinated PLAN is always multi-PR but adds what `multi-pr` lacks: a coordination PR that merges last, cross-repo per-repo grouping, and the two-node merge-order DAG with gates."* The rejected alternative is close to a decoupling design:

> *"Alternative — an orthogonal `coordinated: true` flag over `multi-pr`. Rejected: splits the coordinated effort's identity across two fields and permits invalid combinations (`single-pr` + coordinated); a single enum has no invalid state and gives the validator one branch."*

This is a **direct prior rejection of flag-based decoupling** for a structurally adjacent problem (adding a tracking/coordination dimension on top of cardinality), on the grounds that a single enum is easier to validate and has no invalid-state problem. It is not the same axis as the current exploration (cross-repo coordination vs. single-repo GitHub-issue tracking are different tracking mechanisms), so it doesn't directly forbid the proposal, but it is a real prior argument the exploration's synthesis should confront: *why does a `should` + `tracking` decoupling avoid the "permits invalid combinations" problem that sank the orthogonal-flag alternative for coordination?* An honest answer will probably rest on coordinated mode's flag being cardinality-adjacent (it *is* a cardinality value, `single-pr | multi-pr | coordinated`) while tracking (issues/milestones) is not a cardinality value at all — but that argument needs to be made explicitly, because the corpus has one clean precedent of "we tried the orthogonal-flag shape here and rejected it."

**Status: decided and implemented** (coordinated ships as the third `execution_mode` enum value). This is the single most direct point of tension between the design corpus and the current proposal.

### DESIGN-plan-skill-rework.md hard-codes "roadmap ⇒ multi-pr" as an enforced rejection, independent of the value re-anchoring

`docs/designs/current/DESIGN-plan-skill-rework.md` (Phase 7 roadmap-enrichment branch) enforces the roadmap-is-multi-pr rule mechanically: *"Enforce multi-pr: if `--single-pr` was passed, reject with an error explaining roadmap features are independently scoped."* This is downstream plumbing for the same rule Decision 6 of roadmap-plan-standardization re-anchored on value — it doesn't add a new decision, but it is a second place (beyond `SKILL.md`/phase-3) where "roadmap input forces multi-pr" is load-bearing code, not just prose. Any decoupling design that wants to make "should be multi-pr" a repo preference rather than an input-type-derived constant has to account for this enforcement point too, since today it treats the roadmap case as un-overridable by flag.

**Status: decided and implemented.**

### Not relevant to this lead, despite adjacent names

- **`DESIGN-chain-cardinality.md`** — "cardinality" here means **document lineage** (one `upstream:` pointing to many parents/children across BRIEF/PRD/DESIGN/ROADMAP chains), not PR/plan cardinality. A false cognate; contains nothing about single-pr/multi-pr.
- **`DESIGN-doc-vs-github-state-reconciliation.md`** (FC09) — validates that a doc's claimed issue/PR state matches live GitHub state after the fact. Doesn't touch how execution_mode gets chosen or how issues get created; only reconciles drift once they exist.
- **`DESIGN-completion-cascade.md`** — post-merge lifecycle transitions (PLAN deletion, DESIGN/PRD/ROADMAP status cascades). Downstream of execution_mode, doesn't decide it.
- **`DESIGN-execute-skill.md`** and **`DESIGN-execute-friction.md`** — own how an *already-decided* `execution_mode` gets executed (koto orchestration for single-pr/coordinated, dispatcher pass-through for multi-pr; branch targeting, pause-before-finalize, PR templating). They consume the enum `/plan` produces; they don't decide it. Useful only as confirmation that `execution_mode` is a load-bearing dispatch key consumed by multiple downstream skills, so changing its shape (e.g., splitting into separate can/should/tracking fields) has a multi-consumer blast radius: `/plan`, `/work-on`'s dispatcher, `/execute`, the validator's lifecycle checks (L01/L02, FC14-style branch for coordinated), and the CLI all branch on this one field today (`DESIGN-capstone-orchestration.md` Decision G: "`/plan`, `/work-on`, the validator... and the CLI all branch on this one field").

## Implications

- Any decoupling design must explicitly supersede or amend Decision 6 of `DESIGN-roadmap-plan-standardization.md` — that's the actual current owner of the single-pr/multi-pr rule, not any of the eight documents named in the assignment. Citing it (rather than re-deriving the same "de-conflate mechanism from principle" reasoning from scratch) will save real work, since it already did half the job the current exploration wants: it separated decomposition-strategy from execution-mode and moved the roadmap case from mechanism-justified to value-justified. It stopped one level short of a repo preference.
- The exploration's "should" gate (org-level review-ergonomics preference) is not free to invent from nothing — it has to reconcile with P1 ("usable value is the unit of work," `references/workflow-principles.md`), which is currently treated as a universal principle, not a tunable. Making "should" a repo preference means either (a) P1 becomes the *default* that a repo preference can override, or (b) P1 stays universal and only the *threshold* for what counts as "independently useful" becomes tunable. The corpus doesn't currently distinguish these, and Decision 6's language ("anchored on usable value... not mechanism") reads as treating P1 as non-negotiable, which is in tension with making "should" configurable.
- The "tracking" gate has a ready-made mechanism precedent (`## Roadmap Issues:` header, flag>header>default stack, automatic-runs-always-safe rule, supersession-by-decision-record pattern) from `DESIGN-roadmap-issueless-preference.md`/`DESIGN-populate-issueless-default.md`. A PLAN-level `## Plan Issues:` (or similarly named) header following the identical shape is the path of least resistance and has a track record of two designs plus a decision record refining it in production.
- The "can" gate (near-deterministic from decomposition) has no direct precedent to build on or contradict — the corpus's only "hard constraint forces multiple PRs" language (`skills/plan/SKILL.md:150-154`) is prose-judged, not decomposition-derived in any mechanical sense. This is genuinely open territory, not something to reconcile against a prior decision.
- The coordinated-mode Decision G rejection of an orthogonal flag is the one place the exploration should proactively address rather than silently step around, even though it targets a different axis (cross-repo coordination, not GitHub issue/milestone tracking). A reviewer familiar with that decision will ask "why is this decoupling safe when we already rejected the analogous one?" — the exploration's synthesis needs a one-paragraph answer ready.

## Surprises

- The eight documents named in the assignment brief turned out to be the *wrong* primary source for the fused rule. The actual owner (`DESIGN-roadmap-plan-standardization.md`) wasn't in the list at all, and is a large, mostly-unrelated design (roadmap/plan table-and-diagram standardization) whose Decision 6 is a small, easy-to-miss slice of a much bigger document.
- `## Execution Mode:` — the CLAUDE.md header name closest in spelling to "execution_mode" (the PLAN frontmatter field this exploration is about) — governs something completely unrelated: autonomy (`auto|interactive`), not cardinality. Anyone searching the corpus by header name for "is there already an execution-mode preference" will find this header and could easily mistake it for prior art on the cardinality question. It is not; it's a namespace collision worth flagging explicitly so a future design doesn't accidentally overload it.
- The multi-pr↔issue/milestone coupling isn't incidental plumbing — it's the explicit *reason* the Draft→Active approval gate is asymmetric between modes (`DECISION-multi-pr-posture-detection-2026-06-06.md`). Decoupling tracking from cardinality doesn't just add a new preference; it removes the stated justification for an existing, shipped, human-approval gate and requires that gate's condition to be re-derived from "does this run create GitHub artifacts" rather than "is this multi-pr."

## Open Questions

- Does the exploration intend the "should" preference to override P1 outright, or to parameterize what counts as "independently useful" under P1? The corpus doesn't currently support either reading over the other.
- If tracking (issues/milestones) becomes independently configurable, what happens to the Draft→Active human-approval gate when cardinality is multi-pr but tracking is off (no issues created), or cardinality is single-pr but tracking is somehow on? `DECISION-multi-pr-posture-detection-2026-06-06.md`'s gate logic has no answer for that cell of the matrix because the matrix doesn't exist yet in the shipped design.
- Should a PLAN-level tracking preference reuse the `## Roadmap Issues:` header's name/shape/values (`optional|required`) for consistency, or does PLAN-level tracking need a richer vocabulary (e.g., issues without a milestone, issues with a milestone, no GitHub artifacts at all)? The roadmap precedent is binary; PLAN execution already has three cardinality values plus whatever tracking granularity multi-pr's "issues + milestone" bundle implies.

## Summary

The corpus's real prior decision on this exact question is `DESIGN-roadmap-plan-standardization.md` Decision 6 (not in the assigned reading list), which already separated decomposition-strategy from execution-mode and re-anchored roadmap's multi-pr outcome on value rather than mechanism — but stopped short of making "should" a repo preference, and never touched tracking as a separate axis at all. Tracking (GitHub issues + milestone) is currently fused to multi-pr cardinality by construction, and that fusion is the explicit stated reason the Draft→Active gate is human-approved for multi-pr and automatic for single-pr (`DECISION-multi-pr-posture-detection-2026-06-06.md`) — decoupling them removes that gate's justification and requires re-deriving its trigger condition. The `## Roadmap Issues:` header (`DESIGN-roadmap-issueless-preference.md` / `DESIGN-populate-issueless-default.md`) is a ready-made, production-proven mechanism precedent for the "tracking" gate specifically, while `DESIGN-capstone-orchestration.md` Decision G is a direct prior rejection of an orthogonal-flag shape for a structurally adjacent problem (coordinated mode) that the exploration's synthesis should explicitly distinguish itself from rather than ignore.
