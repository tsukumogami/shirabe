# Lead: Exactly which of `/work-on`'s finishing obligations are written as skippable prose rather than enforced as gated koto states, and what would each look like as a state?

## Findings

### 1. The koto state-machine surface of `/work-on`, `pr_creation` and later reachable through it

Working backward from the terminals to find every state that can reach `pr_creation`, the finishing spine is `verification` (`skills/work-on/koto-templates/work-on.md:592`) → `finalization` (`:630`) → optionally `deferral_approval` (`:663`) → `pr_precheck` (`:695`) → `pr_creation` (`:752`) → `ci_monitor` (`:777`) → `done` (`:820`)/`done_blocked` (`:826`).

- **`verification`** (`:592-629`). `accepts`: `verification_outcome` (enum `passed|failed|cannot_verify`, required, `:593-596`), `commands_run` (string, required for all outcomes, `:597-604`), `detail` (`:605-609`). No `gates:` block — this state relies entirely on self-reported evidence plus the enum's fail-closed shape. Transitions: `passed` → `finalization` (`:611-614`); `failed` → `implementation` (`:615-618`); `cannot_verify` → `done_blocked` with `failure_reason` (`:619-628`).
- **`finalization`** (`:630-662`). `gates`: `summary_exists` — `type: context-exists`, `key: summary.md` (`:632-634`). `accepts`: `finalization_status` (enum `ready_for_pr|deferral_requested|issues_found`, required, `:636-646`). Transitions: `issues_found` → `implementation` (`:650-651`); `ready_for_pr` **and** `gates.summary_exists.exists: true` → `pr_precheck` (`:653-657`); `deferral_requested` → `deferral_approval` (`:659-661`).
- **`deferral_approval`** (`:663-694`). `gates`: `summary_exists` again (`:671-673`, same key, re-checked because this state sits downstream of a state that can cycle). `accepts`: `approval_decision` (enum `approved|rejected`, required, `:675-678`), `deferral_detail` (string, `:679-683`). Transitions: `approved` + `gates.summary_exists.exists: true` → `pr_precheck` (`:685-689`); `rejected` → `done_blocked` with `failure_reason` (`:690-694`).
- **`pr_precheck`** (`:695-751`). Has a `default_action` (koto runs `git rev-parse --abbrev-ref HEAD`, captures as `BRANCH`, `:718-724`) and a `gates` block: `on_feature_branch_pr` — `type: command`, `test "$(git rev-parse --abbrev-ref HEAD)" != "main"` (`:726-728`). `accepts`: `precheck_status` (enum `override|blocked`, `:730-735`), `detail` (`:736-737`). Transitions: gate exit 0 → `pr_creation` (`:739-741`); exit 1 + `precheck_status: override` → `pr_creation` (`:742-745`); exit 1 + `precheck_status: blocked` → `done_blocked` (`:746-750`).
- **`pr_creation`** (`:752-776`). `accepts`: `pr_status` (enum `created|shared|creation_failed_retry|creation_failed_escalate`, required, `:753-756`), `pr_url` (`:757-759`). Transitions: `created` → `ci_monitor`; `shared` → `done`; `creation_failed_retry` → self-loop; `creation_failed_escalate` → `done_blocked` (`:760-776`).
- **`ci_monitor`** (`:777-819`). `gates`: `ci_passing` — a `type: command` gate over `gh pr checks ... bucket` (`:782-790`). `accepts`: `ci_outcome` (enum `passing|failing_fixed|failing_unresolvable`, required, `:791-794`), `rationale` (`:795-797`). Transitions: `passing` + gate exit 0 → `done`; `failing_fixed` → `done` (agent's direct observation overrides the gate, per comment at `:806-809`); `failing_unresolvable` → `done_blocked` (`:812-815`); a bare fallback `done` (`:816`).
- **Terminals**: `done` (`:820-822`), `done_already_complete` (`:823-825`), `done_blocked` (`:826-835`, `failure: true`, `accepts: failure_reason`), `skipped_due_to_dep_failure` (`:836-839`, `skipped_marker: true`).

This is the enforced half: every state from `verification` through `ci_monitor` has a typed `accepts` schema the koto engine mechanically validates (unknown fields rejected, required fields checked, types checked), and three of the six (`finalization`, `deferral_approval`, `pr_precheck`, `ci_monitor` — four, not three) additionally carry a `gates:` block the engine evaluates independently of what the agent claims.

### 2. The prose surface

The pattern: obligations that resolve to a fact about a file's structure, a git ref, or a `gh`-observable field (title/body shape, `Fixes #N`, merge-state, commit message, summary heading structure) are gateable today and mostly just aren't gated. Obligations that resolve to a judgment call (self-review quality, whether cleanup was "thorough," whether `/try-it` is warranted) are not gateable in koto's four gate types (`command`, `context-exists`, `context-matches`, `children-complete`) and would need self-reported evidence at best, exactly like `finalization_status` today.

### 4. How `/execute` enforces the same obligations

`skills/execute/koto-templates/execute.md`'s `pr_finalization` (`:317-364`) and `plan_completion` (`:429-455`) states are `/execute`'s analogues, and they show a materially tighter pattern for the obligations `/work-on` shares:

- **PR title/body conformance.** `pr_finalization`'s prose (`:640-668`) cites the same `references/pr-body-conformance.md` mechanical rule and walks through building the Conventional-Commits title from `{{PLAN_SLUG}}` and assembling the two-part body via `--body-file`/heredoc (never inline interpolation, `:663-668`) — same non-koto-gate enforcement as `/work-on` (CI + hook), but the state's own `accepts` requires `finalization_status: updated|update_failed` (`execute.md:318-322`), so a failed edit cannot silently pass.
- **DRAFT-vs-READY ordering.** Unlike `/work-on`, which has no ordering gate around PR readiness, `execute.md` structurally splits "assemble body" (`pr_finalization`) from "mark ready" (`plan_completion`, step 2, `:751-754`) so `gh pr ready` cannot fire before the completion cascade runs — encoded as separate states with separate accepted evidence (`cascade_status: completed|partial|skipped`, `execute.md:430-434`) rather than one state's prose sequencing.
- **Merge-state cleanliness.** `execute.md`'s `ci_monitor` gates block includes a **second** gate `/work-on` lacks entirely: `merge_state_clean: type: command, command: "[ \"$(gh pr view --json mergeStateStatus --jq .mergeStateStatus)\" != \"DIRTY\" ]"` (`execute.md:373-375`), with `accepts.ci_outcome` including a fourth value `dirty_merge_state` (`:378-381`) that routes to a dedicated `escalate_dirty_merge_state` state (`:418-427`) rather than being folded into `failing_unresolvable`. `/work-on`'s `ci_monitor` (`work-on.md:777-819`) has only `ci_passing` — the rebase/clean-merge-state obligation that is pure unenforced prose in `phase-6-pr.md:7` for `/work-on` is a named gate plus a named enum value plus a dedicated escalation state in `/execute`.
- **Lifecycle-chain finalization.** `plan_completion`'s cascade (`execute.md:700-756`) runs `run-cascade.sh`, which internally invokes `shirabe validate --lifecycle-chain --mode=ready` at both a pre-probe and a post-verify point and returns a JSON `cascade_status` the agent reports as evidence (`:704-706`, `:730-745`) — the agent never hand-waves "the chain is finalized"; it parses a script's deterministic exit-code-derived verdict. This is not a `type: command` koto gate (the script's exit code is not read by a `gates:` block; the JSON verdict is submitted as `accepts` evidence), but it is a machine-checked precondition one layer down, closer to the `pr_precheck` pattern (a read, captured, that the agent's evidence must match) than to unstructured prose.

None of `/execute`'s equivalents gate the design-doc-diagram-update obligation or the `Fixes #N` obligation — `/execute` doesn't touch per-issue design docs (that's `/work-on`'s per-child concern) and its own `Fixes #<N>` handling (`execute.md:653`) is exactly as advisory as `/work-on`'s. The worked precedent `/execute` offers is specifically for merge-state cleanliness and finalize-ordering, not for the full obligation list.

### 5. The `finalization` state's actual scope

Confirmed: `finalization` (`work-on.md:630-662`) runs strictly **before** the PR exists. The sequence is `verification` → `finalization` → (`deferral_approval` →) `pr_precheck` → `pr_creation`. `pr_precheck`'s own comment block (`:695-712`) states it is "the single edge into `pr_creation`" and "the template's only structural guarantee that a pull request is not opened from the default branch, at the point where opening one happens" — meaning no PR exists at `finalization` or `deferral_approval` time; `pr_creation` is the first state that creates one (`gh pr create`, referenced in its prose at `:1186`).

`finalization`'s scope, per its `gates`/`accepts` (only `summary_exists` and `finalization_status`) and its prose (`:1129-1146`) plus `phase-5-finalization.md`, is entirely about the **implementation**: cleanup, a full local test/build/lint run, writing `summary.md`, and deciding whether every acceptance criterion is met. Nothing in the state touches PR content, title, body, or GitHub state. The claim that it finalizes the implementation rather than the PR is confirmed by the template, not refuted.

### 6. Gate idiom in this repo

`references/default-action-conversion.md` and the two templates establish these rules for adding a new gated state:

- **The core question for `default_action`**: "Does the command's risk live in a bad success, or only in a bad failure?" (`default-action-conversion.md:12`). Never automate a step whose success is itself an irreversible, externally-visible event (creating/publishing/closing a PR, posting a comment, marking ready) — this is why `gh pr create` and `gh pr ready` stay agent-invoked prose in both templates (`work-on.md:1188`, `execute.md` step 2 comment at `:750-754`) even though the branch-name read one state earlier (`pr_precheck`) is a `default_action`.
- **Two shirabe-specific filters on top of koto's rule**: (1) the command must exit non-zero on failure — a command that always exits 0 can never surface a diagnosis through the failure path (`:40-49`, citing `extract-context.sh`'s `Exit codes: 0 - Always` as the counter-example that stays agent-run); (2) the command must leave a trace another command (the gate) can check independently — "if the only evidence the step ran is the step's own exit code, converting it buys automation and sells assurance" (`:51-55`).
- **Three authoring constraints**: a `fallback` must name the evidence field and value, not just "run this yourself" (`:62-66`); any command body longer than one clause must move into a script under the skill's `scripts/` directory, because `scripts/check-template-interpolation.sh` rejects any `command:` containing `$NAME`/`${NAME}` (unable to distinguish an author's template-variable typo from a legitimate shell variable) — and a script must be reached via a declared template variable (e.g. `PLUGIN_ROOT`), never `${CLAUDE_PLUGIN_ROOT}` directly, since koto doesn't resolve shell variables and the linter rejects that field shape (`:68-83`); every transition out of a converted state must repeat the gate's exit-code field in every branch so koto's requirement that sibling `when` blocks share a field is satisfied (`:85-109`).
- **The repo's linter, `scripts/validate-template-mermaid.sh`**, imposes a fourth mechanical constraint relevant to any new gate: **Check 4** — "a gate name used by more than one template carries the same command in all of them" (`validate-template-mermaid.sh:154-160`, implemented via `scripts/lib/koto-gates.sh`). This is exactly why `pr_precheck`'s gate is named `on_feature_branch_pr` rather than reusing `on_feature_branch` — the comment at `work-on.md:709-712` explains the rename is deliberate so the check doesn't wrongly conflate two gates with different jobs under one shared name. Any new gate reusing a name that already exists in `execute.md` or `work-on.md` must carry an identical command string, or the linter fails CI.
- Two other worked precedents on this repo's default_action ledger: `pr_precheck` itself ("a read, captured, gated ahead of the step it feeds") and three others in `execute.md`/`scope.md` (`default-action-conversion.md:176-181`), plus a design doc (`DESIGN-koto-default-action-adoption.md`) recording thirteen candidates that were examined and deliberately left as agent-run prose — useful negative-precedent reading for anyone about to propose converting one of the obligations from §2/§3.

### 7. What a child receives

Per the workspace's own prior research (`wip/research/explore_work-on-standalone-completeness_r2_lead-koto-materialization.md`, Findings 1-3, backed by koto engine source citations), a `/execute`-materialized `/work-on` child is seeded directly at the compiled template's `initial_state` from disk-level koto events (`WorkflowInitialized`/`Transitioned`) — there is no subprocess, no prompt construction, and no reference anywhere in koto's source to "SKILL.md" or a slash command. The only text a child agent receives per tick is the compiled template's own `directive`/`details`, split from each `## <state>` markdown section (`work-on.md`'s body, e.g. `:841-1227`). Reference files that a state's directive tells the agent to read (e.g. `phase-6-pr.md`, `phase-5-finalization.md`) are not loaded by koto itself — whether the agent actually opens them is up to the agent's own tool calls, but the *pointer* to them is present in what the child receives. `work-on/SKILL.md` is never reachable by a child at all: koto has no code path that opens it, and nothing in `/execute`'s dispatch invokes `/work-on` as a Claude Code skill for its children.

Classifying each §2 obligation by reachability:

- **Reachable to a child** (cited from the template's own per-state prose, directly or one hop via a file the template names): everything in `phase-6-pr.md` (cited directly at `work-on.md:1180`/`:1194`) and everything in `phase-5-finalization.md` (cited directly at `:1131`) — rebase/self-review/design-doc-update/push/PR-body/`Fixes #N`/CI-loop obligations, and auto-skip/cleanup/final-verification/summary-format/commit-message/`/try-it`/no-hedge-language obligations.
- **Reachable but two hops removed**: `phase-6-design-diagram-update.md`, cited only from inside `phase-6-pr.md:14`, not from the template directly — still technically reachable (the agent would follow the reference chain if it reads `phase-6-pr.md` fully), but one link more fragile than the direct citations, and its own contract's silent-skip permission (`:69-72`) compounds that fragility.
- **Unreachable to a child**: the "Finalization and No Silent Deferral" section and the full Definition-of-Done procedure as stated in `SKILL.md:54-120` are duplicated in the template's own prose closely enough that the *content* the agent needs is delivered via `phase-5-finalization.md` and the `verification` state's directive — but the specific `SKILL.md` framing (R4/R5/R6 requirement-ID cross-references, and the explicit "removed the `deferred_items_noted` terminal" history) is not. A child gets the operational instructions but not the requirements-traceability narrative that only lives in `SKILL.md`. The one live risk case: `work-on.md:1084`'s verification-state prose says "See the `## Definition of Done` section of SKILL.md for the full procedure" — this is a pointer *from the template itself* into a file a child cannot load, meaning the child sees an instruction to consult a resource it has no path to open (see Surprises).

## Implications

The obligations that would be cheapest to convert to a gated state are the ones already resolving to a `gh`-observable or git-observable fact: merge-state cleanliness (direct copy of `execute.md`'s `merge_state_clean` gate into `work-on.md`'s `ci_monitor`), the `Fixes #N` closing keyword (a `type: command` gate reading `gh pr view --json body`), and summary.md's structural shape (a gate or a stricter `context-matches` check beyond bare existence). The obligations that resolve to judgment calls (self-review quality, `/try-it` relevance, whether cleanup was thorough) cannot become gates under koto's four gate types without becoming self-reported evidence fields at best — which is exactly the "prose an agent may skip" status quo, just with a name in the `accepts` schema. Any PRD built on this enumeration should treat "gateable" and "judgment-call, evidence-field-only" as two different remediation tracks rather than aiming to gate everything uniformly.

## Surprises

- **The Auto-Skip label rule and the `summary_exists` gate appear to be in direct tension.** `phase-5-finalization.md:7-9` instructs skipping summary creation for `docs`/`config`/`chore`/`validation:simple`-labeled issues, but `finalization`'s only transition to `pr_precheck` on `ready_for_pr` unconditionally requires `gates.summary_exists.exists: true` (`work-on.md:653-657`), with no alternate branch for a legitimately-skipped summary. Nothing in the template's `finalization` prose (`:1129-1146`) or in `PRD-work-on-retry-clearing.md` (which specifically enumerates `summary_exists` as a stale-artifact gate) mentions this interaction. Either the auto-skip prose is dead instruction the agent must ignore in practice (writing a minimal summary.md regardless of label), or there's an undocumented gap where the gate silently overrides the prose's stated intent.
- **A template state's own directive can point a child at a resource the child cannot reach.** `work-on.md:1084` tells the agent in the `verification` state's own prose to consult `SKILL.md`'s Definition-of-Done section — but per §7, a materialized child never loads `SKILL.md`. This is a live instance of the exact failure mode the lead is investigating (an obligation stated as prose an agent "may" follow), except here it's not even skippable by choice — a child literally cannot follow it, regardless of diligence.
- **`phase-6-design-diagram-update.md`'s own contract explicitly authorizes silent skipping** ("log warning, skip diagram update, continue to Push Branch," `:28`; "Log error, abort diagram update, continue PR without it," `:72`) — this isn't merely an obligation an agent might skip against instructions; the instructions themselves say skipping silently is the correct behavior on any validation hiccup.
- **The mechanical PR-body rule is enforced entirely outside koto** — not by a `type: command` gate in either template, but by a CI workflow and a client-side PreToolUse hook that intercepts `gh pr create`/`gh pr edit` before they run (`pr-body-conformance.md:138-143`). This means "gated" in this repo already has two distinct meanings — koto-engine-gated (a `gates:` block the state machine evaluates) and tool-hook/CI-gated (enforced outside the workflow engine entirely) — and a PRD proposing new koto gates should be explicit about which kind it means for each obligation, since the PR-body case shows the non-koto kind can already be just as hard to bypass.

## Open Questions

- Is the Auto-Skip/`summary_exists` tension a known, accepted behavior (agents always write a trivial summary regardless of label) or an actual latent bug nobody has hit because most issues don't carry summary-skippable labels through to a clean `finalization`?
- Should the design-doc-diagram-update obligation be pulled up to be cited directly from the template (closing the two-hop gap) as a low-cost first step, independent of whether it ever becomes gated?
- For obligations classified as judgment calls (self-review, `/try-it` relevance) — does the PRD intend to leave them as ungated prose permanently, or is there an appetite for weaker structural pressure (e.g. a required evidence field that doesn't gate a transition but does get surfaced in the batch view, the way `failure_reason` is)?

## Summary

`/work-on`'s enforced spine runs `verification` → `finalization` → `deferral_approval` → `pr_precheck` → `pr_creation` → `ci_monitor`, each with a typed `accepts` schema and four of them with independent `gates:` blocks, while the bulk of its finishing obligations — rebase/merge-cleanliness, PR-body content beyond CI's own mechanical check, the `Fixes #N` keyword, design-doc-diagram updates, code cleanup, summary content shape, and commit-message convention — live only as prose in `phase-6-pr.md` and `phase-5-finalization.md`, cited directly from the template's per-state directives (so children do receive them) except for the design-diagram update, which is two reference-hops away and whose own contract permits silent skipping. `/execute`'s `pr_finalization`/`ci_monitor`/`plan_completion` states show a concrete precedent for gating two of these (merge-state cleanliness via a `merge_state_clean` command gate, and finalize-ordering via a separate `plan_completion` state with `cascade_status` evidence backed by a deterministic script) that `/work-on` currently lacks entirely. The `finalization` state itself is confirmed to run before any PR exists, and its `summary_exists` gate checks only artifact presence, not the summary's prescribed shape — leaving the enumeration's most actionable finding that a meaningful minority of these obligations resolve to `gh`- or git-observable facts and are cheaply gateable, while the rest are irreducibly judgment calls that can at most become named evidence fields.
