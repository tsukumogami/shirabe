## Implications

The MECHANICAL bucket (26 of 53, roughly half) is the strongest immediate `default_action` candidate: branch derivation, `git checkout`/`push`, PR existence checks and creation, `jq` transforms for task-branch injection, the two preflight/assertion scripts, and the final `gh pr ready` call are all context-free and already written as literal, copy-pasteable shell in the template — no prose interpretation step separates "read the instruction" from "know exactly what to run." Converting these to `default_action` would remove them from the agent's turn budget entirely on the happy path, which is exactly the target state described in the lead.

The MIXED bucket (11) is where a naive "make everything default_action" pass would break something: several of these commands only look mechanical until you notice the agent is meant to *read* the output and choose a submission value (`status: completed` vs `override`; `ci_outcome: dirty_merge_state` vs other). A `default_action` here would need to either (a) still hand the raw output back to the agent for interpretation — which is possible, since `default_action` can populate evidence fields, not just fire-and-forget — or (b) stay agent-run. The two `run-cascade.sh`/`shirabe validate --lifecycle-chain` invocations are worth calling out specifically: they're single commands wrapping genuinely complex internal logic (see below), so making *those specific calls* into `default_action` is comparatively low-risk even though they're classified MIXED, because the complexity is already fully encapsulated in the script/binary, not in agent judgment.

The JUDGMENT bucket (2) is small and precisely where the target state's "falls back to instructing the agent only when a command fails" framing doesn't apply cleanly — these two spots (`OUTCOME=` and the PR-body heredoc) are not commands with a failure mode to fall back from; they are inherently prose-authoring and result-inspection steps. `default_action` doesn't help here regardless of design.

`run-cascade.sh` is itself a preview of what a heavier `default_action` script-backed step could look like: internally it already runs `git rev-parse --show-toplevel`, two `shirabe validate --lifecycle-chain` probes (pre/post), `shirabe finalize-chain`, `shirabe transition`, `git add`/`rm`/`commit`/`push`, `gh issue view` (via `check_issue_closed`), and extensive `jq`/`awk` — all invoked as ONE agent-facing command. That the project already built this pattern (deterministic multi-step logic behind a single script entry point) for the hardest part of the workflow suggests the natural next step isn't necessarily "convert every template line to `default_action`" but "keep composing script-backed single-command steps and promote the ones with no judgment gate to `default_action`."

## Surprises

1. **Koto is already running agent-instructed shell itself, today** — just as gate predicates (`type: command`), not as `default_action` for the state's own action. The `ci_passing`, `merge_state_clean`, and `impact_classified` gates are koto executing `gh`/`test` commands autonomously on every `koto next` call. The core question's framing ("zero occurrences of `default_action`") is accurate for the *action* mechanism, but the *gate* mechanism already gives koto command-execution authority in this template. Any `default_action` design should account for the fact that gates and actions could double-run the same command (e.g., `ci_passing`'s `gh pr checks` query is nearly identical in shape to what a `default_action` for ci_monitor might run) — there's a de-duplication opportunity, not just a new capability to add.

2. **The exact literal example from the lead's framing is real and present almost verbatim**: execute.md:353's prose — "then run `git rev-parse --abbrev-ref HEAD` to get the current branch and `gh pr list --head <current-branch> --json number --jq '.[0].number'` to find any open PR on it" — is precisely the "hand the agent mechanical shell commands inside prose instructions" pattern the lead describes, almost word for word.

3. **Some "mechanical" commands are deliberately duplicated three times** (the `PLAN_SLUG=$(basename {{PLAN_DOC}} .md | sed 's/^PLAN-//')` derivation appears at execute.md:393, 440, 484, 530, 546 — five times total) because koto templates have no shared-state/variable-persistence-across-blocks primitive other than context or template vars, and `PLAN_SLUG` is already a declared template variable specifically to avoid this (per the frontmatter comment at execute.md:14-22) — yet the *derivation* shell one-liner is still repeated in prose at each site rather than only referencing `{{PLAN_SLUG}}` directly. This is a strong signal that a `default_action` (or even just a template-level `{{PLAN_SLUG}}` substitution instead of re-deriving it) would remove real duplication, not just move it.

4. The settled-branch recording block (execute.md:359-372) is unusually defensive/wordy specifically *because* it's hand-written agent-facing shell with subtle correctness properties (branch-name injection safety, `koto context add` vs the nonexistent `context set`, stdout-vs-stderr error semantics). The prose around it (execute.md:374-388) is nearly as long as the script itself, explaining exactly why each line matters — this is exactly the kind of fragile, footgun-prone hand-authored shell that `default_action` (validated at template-compile time, per the frontmatter's own reasoning about `{{PLAN_SLUG}}`) is designed to make impossible to get wrong.

## Open Questions

- Does koto's `default_action` support populating evidence fields from command output (needed for the MIXED-classified commands where the agent currently reads output to choose an enum value), or is it strictly fire-and-run-then-fall-through-to-prompt on any output? This determines whether the MIXED bucket (11 commands) is in scope for conversion or only the pure MECHANICAL bucket (26) is.
- Do the gate commands (`ci_passing`, `merge_state_clean`, `impact_classified`) and a hypothetical `default_action` for the same state risk redundant `gh`/`test` calls, and does koto's execution model (`src/engine/advance.rs` step 5, per the lead's context) sequence gates before or after a state's `default_action` fires?
- Is there an appetite to also collapse the repeated `PLAN_SLUG` derivation one-liner across all five sites into a single template-variable reference, independent of the `default_action` question — it's a smaller, orthogonal cleanup already implied by the same frontmatter comment that motivated declaring `PLAN_SLUG` as a variable in the first place.

## Summary

`/execute`'s koto template and SKILL.md hand the agent 53 distinct shell-command instructions across execute.md, SKILL.md, and references/cross-issue-context.md — 26 purely mechanical (branch/slug derivation, git/gh plumbing, jq transforms), 11 mixed (mechanical command, judgment-required output), 2 pure judgment (batch-outcome decision, PR-body authoring), and 14 koto-protocol calls, plus 3 gate commands koto already executes itself as validation predicates (the closest existing precedent to `default_action`, though used for gating rather than acting). The main implication is that roughly half the inventory (the MECHANICAL bucket) is immediately convertible to `default_action` with low risk, while the MIXED bucket needs koto's evidence-population semantics clarified before conversion, and the JUDGMENT bucket is out of scope entirely; the biggest open question is whether `default_action` can write evidence fields from command output or only fire-and-fall-through.
