# Lead: What did rounds 1 and 2 miss? Is the round 1+2 inventory complete for the user's question?

## Findings

**Verdict up front: rounds 1 and 2 correctly inventoried the only surface where `default_action` is actionable, but they are not a complete inventory of "all scenarios where commands are hardcoded in the text instructions of the workflow" — the user's literal brief. That broader surface is roughly 3-4x bigger than what got counted, spread across 18 skills rounds 1/2 never opened.**

### 1. `shirabe/CLAUDE.md`'s `koto-templates/` is stale documentation

`CLAUDE.md:256-265` documents a Directory Structure with a repo-root `koto-templates/` entry ("Koto YAML workflow templates"). That directory does not exist and, per git history shape, never held anything CLAUDE.md describes at the root — the real templates live two levels down at `skills/execute/koto-templates/{execute.md,execute.mermaid.md}` and `skills/work-on/koto-templates/{work-on.md,work-on.mermaid.md}`. This is a documentation bug, not command-surface — but it matters to this exploration because it's exactly the kind of thing a shallow "grep the top-level tree" pass would trust and get wrong. Nothing else claims koto templates exist anywhere but these two per-skill directories (confirmed by `find`, and by a repo-wide grep for `initial_state:` and `*.koto.md` finding zero hits outside `skills/execute/` and `skills/work-on/`).

### 2. Eighteen other skills carry real, uninventoried command surface

Rounds 1/2 scoped to `skills/execute/**` and `skills/work-on/**`. There are 20 skills total: `brief, charter, comp, decision, design, execute, explore, inflight, plan, prd, private-content, public-content, release, review-plan, roadmap, scope, strategy, vision, work-on, writing-style`. None of the other 18 are koto-backed (no `koto-templates/` dir, no `initial_state:`, zero `koto next`/`koto init` references anywhere outside execute/work-on) — so `default_action` genuinely cannot apply to them. But the user's brief asked about hardcoded commands in workflow text generally, and several of these 18 carry meaningful, previously-uncounted command instructions:

- **`/inflight`** (`skills/inflight/SKILL.md`, 148 lines) — entirely missed by both rounds, not mentioned once in the R1/R2 context. It's a thin CLI relay: a `!`-injected line runs `shirabe work-summary render` automatically, but the skill also instructs the agent, in prose, to manually run a specific mechanical command to recover a missed PR: `` shirabe work-summary track <pr-url> [<pr-url> ...] `` (SKILL.md, "Recovering a PR the hook missed" section). That's a real agent-typed command outside the execute/work-on surface.
- **`/release`** (`skills/release/SKILL.md`) — explicitly **not** koto-driven ("`/release` is not a koto-driven skill, so intermediates belong in `wip/`", line ~225 context). It hardcodes multiple mechanical shell blocks the agent runs directly: `LAST_TAG=$(git describe --tags --abbrev=0 --match 'v*' ...)` range derivation (line 37), `gh release create "v<version>" --draft --title ... --notes-file wip/release-notes-<version>.md` (line 225), `gh workflow run <workflow-file> -f version=... -f tag=... -f ref=main` (line 245), and a skill-only-mode fallback telling the user to run `git tag -a v<version> -m "..." && git push origin v<version>`. This is the single largest block of literal, non-koto, agent-run shell outside execute/work-on.
- **`/roadmap`** — `SKILL.md:432-486` hardcodes both invocation forms of `shirabe roadmap populate` (issue-creating and issueless), plus a mid-body (non-frontmatter-injected) `bash ${CLAUDE_PLUGIN_ROOT}/scripts/skill-preflight.sh roadmap --mode issues` gate call that the prose explicitly says is *not* seen by `scripts/check-skill-injection.sh` (which only reads column-0 `!`-injected lines) — a structurally distinct preflight-invocation pattern from the one every skill gets automatically.
- **`/scope`** — `SKILL.md:203` has the identical structural pattern: a mid-body `bash ${CLAUDE_PLUGIN_ROOT}/scripts/skill-preflight.sh scope --mode coordinated` gate call, same "not injected, not covered by check-skill-injection.sh" caveat.
- **`/plan`** — `SKILL.md:429` hardcodes `gh issue list --search "Design: <design-doc-path>" --json number,title,state` in prose.
- **`/explore`** — `SKILL.md:143` hardcodes `gh issue view 42 --repo owner/repo --json title,body,labels` for cross-repo issue lookups.
- **`/design`** — `references/lifecycle.md:24` hardcodes `shirabe transition <path> <target> [--superseded-by <doc>]` with prose describing it as also driving `git mv`.

### 3. `shirabe transition` and `shirabe validate` are hardcoded across nearly every content-authoring skill, not just execute/work-on

This is the biggest structural finding. Grepping skill prose for the two CLI verbs round 1 already catalogued inside execute/work-on shows they are copy-pasted as literal "run this to finalize" instructions into **every** artifact-lifecycle skill: `vision`, `strategy`, `roadmap`, `brief`, `prd`, `design`, `plan`, `comp`, plus `charter`/`scope` (their parent-skill wrappers). Sampled instances:

- `skills/vision/SKILL.md:86-90` — Phase-0 routing tells the agent to "execute the lifecycle transition via `shirabe transition <vision-path> <status>`" when the input path plus a lifecycle verb is detected, and again at line 208-209 to transition Draft→Accepted after approval.
- `skills/strategy/references/phases/phase-5-finalize.md:110-113` — a literal fenced `shirabe transition docs/strategies/STRATEGY-<topic>.md Accepted` block.
- `skills/comp/references/phases/phase-0-setup.md:41-45` — cites `shirabe validate` rejecting a COMP under public visibility as the reason competitive docs can't live in a public repo.

This same "transition to Accepted via `shirabe transition <path> Accepted`" pattern recurs in `brief`, `prd`, `design`, `roadmap`'s finalize phases (confirmed by grep hit counts: `shirabe transition` appears in 23 files across `vision/strategy/roadmap/brief/prd/design/plan/comp` alone, `shirabe validate` in 48 files across the same set plus `charter/scope/execute/work-on`). None of this is koto-driven — these are plain phase-file skills — so `default_action` cannot absorb it, but it is unambiguously "commands hardcoded in the text instructions of the workflow" per the user's literal question, and it is roughly the same command repeated ~8-10 times independently rather than centralized once.

### 4. `shirabe/scripts/**` — full classification

The complete script inventory (30 files) is CI/dev tooling except one runtime path:

- **Runtime, agent-facing**: `scripts/skill-preflight.sh` — this is the script every skill's `!`-injected first line invokes (`!`bash ${CLAUDE_PLUGIN_ROOT}/scripts/skill-preflight.sh <skill> 2>&1 || true``), confirmed present in `inflight`, `roadmap`, `scope`, and (per round 1/2) `execute`/`work-on`. It sources `scripts/lib/preflight-read.sh` and `scripts/lib/preflight-resolve.sh` at runtime. This is command surface that runs automatically via Claude Code's own `!`-injection mechanism — not something the agent types — so it's a different category from the "agent runs this manually" surface the exploration cares about, but it is real command execution wired into every skill invocation, and round 1/2 didn't discuss it because it isn't koto-related and doesn't route through `koto next`.
- **CI/dev/test tooling** (confirmed by grep for CI workflow references and by file naming): `bash-floor-canary.sh`, `check-bash-floor.sh` (+test), `check-evals-exist.sh`, `check-no-duplicate-rule-list.sh`, `check-no-fixture-design-leak.sh`, `check-sentinel.sh`, `check-skill-injection.sh` (+test), `check-skill-requires.sh` (+test), `check-template-interpolation.sh` (+test), `check-tool-diagnostic-discards.sh` (+test), `ci-gate-expression_test.sh`, `run-evals.sh`, `settled-branch-read_test.sh`, `validate-template-mermaid.sh` (+test), plus `lib/koto-gates.sh` (round 1's finding, confirmed) and `lib/preflight-probe.sh`/`preflight-report.sh` (+tests) and `lib/tool-routes.tsv`, which are library/data files rather than standalone gates.
- **Notable side-finding**: `scripts/check-template-interpolation.sh` (lines 1-30) is explicitly `default_action`-aware — its header comment says it flags shell-interpolation defects "in a gate command or a **default_action command**," and its test file `check-template-interpolation_test.sh` has a literal `default_action:` fixture (line 109). This means shirabe's own template-linting CI tooling already understands and validates the `default_action` field syntactically, even though (confirmed) zero actual shirabe templates use it. The validation infrastructure is not a blocker to adoption — it's already there and dormant.
- **Per-skill scripts, not top-level**: `plan-to-tasks.sh` lives at `skills/plan/scripts/plan-to-tasks.sh`, not under `skills/execute/scripts/` — but it is invoked by `/execute`'s own koto template (`skills/execute/koto-templates/execute.md:437-486`, `${CLAUDE_PLUGIN_ROOT}/skills/plan/scripts/plan-to-tasks.sh {{PLAN_DOC}}`) and by `skills/execute/SKILL.md:224`. This confirms the lead brief's claim about it but corrects its location — it's cross-skill-owned infrastructure, not execute's own script. `assert-child-template.sh` and `run-cascade.sh` are genuinely under `skills/execute/scripts/`, matching the brief. `extract-context.sh` is under `skills/work-on/references/scripts/` (not `skills/work-on/scripts/`), matching round 1's note that `phase-2.5-worktree-discipline.md` and other execute-owned material got misfiled under `work-on/references/`.

### 6. No other repo in the workspace ships koto templates with hardcoded commands the way shirabe does

`public/koto/plugins/koto-skills/skills/koto-author/koto-templates/koto-author.md` is the one koto template outside shirabe (koto's own "author a koto template" dogfood skill). It does not use `default_action` — grepping the whole `koto` repo for `default_action` finds it only in koto's own source (`src/engine/advance.rs`, `src/cli/next.rs`, etc.), design docs, and two *reference/documentation* files (`references/template-format.md`, `references/batch-authoring.md`) that describe the feature — never inside an actual `.md` template body. So koto's own dogfood example doesn't demonstrate `default_action` usage either; there's no existing template anywhere in the workspace to point to as a working precedent. The rest of the `initial_state:` hits under `public/koto/test/functional/fixtures/templates/*.md` are koto's own engine test fixtures (`hello-koto.md`, `multi-state.md`, `skip-if-*.md`, etc.) — synthetic, not representative of real workflow command patterns.

### 7. Runtime-generated commands and eval fixtures

`inflight`'s `!`-injected line and the standard `skill-preflight.sh` injection are the only "generated at runtime rather than written literally" pattern found — the command text itself is literal in the skill file, but *when* it executes is runtime-determined by Claude Code's `!` mechanism rather than by the agent choosing to type it. `skills/inflight/evals/fixtures/preflight-liveness/` contains synthetic `SKILL.md`/`requires.tsv` fixtures that mirror the preflight-gate pattern for testing `skill-preflight.sh` itself — test scaffolding, not real workflow surface, correctly excludable.

## Implications

- The round 1+2 inventory is the right and complete answer to the *narrower* question the exploration context frames — "what mechanical commands inside execute/work-on's koto templates could `default_action` absorb" — because `default_action` is structurally inert outside a koto-backed template, and execute/work-on are the only two koto-backed skills in the workspace.
- It is **not** a complete answer to the user's literal brief ("all scenarios where commands are hardcoded... the main skill file and references"), which asked about the whole `skills/` tree. That surface includes at minimum: `/inflight`'s `work-summary track` instruction, `/release`'s four non-koto shell blocks, `/roadmap`'s two `shirabe roadmap populate` forms plus its own mid-body preflight-gate pattern, `/scope`'s matching mid-body preflight-gate pattern, `/plan`'s `gh issue list` call, `/explore`'s `gh issue view` call, `/design`'s `shirabe transition` call, and the `shirabe transition`/`shirabe validate` pattern replicated independently across eight artifact-lifecycle skills.
- If the deliverable is scoped to "what can `default_action` fix," rounds 1/2 stand as-is. If the deliverable is scoped to the user's original words, it needs a second section covering the 18-skill surface above, explicitly labeled as non-actionable-by-`default_action` (since none of those skills are koto templates) but real hardcoded-command surface nonetheless — probably framed as a candidate for a shared reference/script rather than koto automation, since the `shirabe transition`/`shirabe validate` duplication across 8 skills is itself worth flagging independent of the koto question.

## Surprises

- `shirabe/CLAUDE.md`'s Directory Structure section is simply wrong about where `koto-templates/` lives — a two-line staleness bug in the skill's own root documentation that nobody flagged.
- `/inflight` is a fully agent-facing, non-koto skill with a real "run this exact command" recovery instruction, and it wasn't mentioned anywhere in the R1/R2 context handed to this lead — total blind spot, not a partial one.
- `check-template-interpolation.sh` already validates `default_action:` syntax and has a test fixture for it, meaning the CI-tooling side of adopting `default_action` in shirabe templates requires zero new work — the gap is purely "no template author has used the field," not "the linter doesn't understand it yet."
- The mid-body (non-`!`-injected) preflight-gate pattern in `roadmap` and `scope` is a second, structurally distinct hardcoded-command mechanism that the standard `check-skill-injection.sh` gate explicitly does not see (per the skills' own prose) — a self-documented blind spot in the existing lint coverage, separate from the koto question entirely.

## Open Questions

- Does the user want the `shirabe transition`/`shirabe validate` duplication across 8 non-koto skills addressed at all, or is that explicitly out of scope since it can't use `default_action`? The exploration context frames the question around koto's capability, which would exclude it, but the original brief's wording ("all scenarios") wouldn't.
- Should `/release`'s hardcoded `git`/`gh` blocks be flagged as a candidate for eventual koto migration (giving it a template) rather than as a fix within its current non-koto form?

## Summary

Rounds 1 and 2 correctly and completely inventoried the only surface where koto's `default_action` is actionable — `execute`/`work-on`, the sole two koto-backed skills — but that is a fraction of the user's literal question. Eighteen other skills carry real hardcoded-command surface the earlier rounds never opened, most notably `/inflight` (missed entirely), `/release`'s four non-koto shell blocks, and a `shirabe transition`/`shirabe validate` pattern copy-pasted independently across eight artifact-lifecycle skills (vision, strategy, roadmap, brief, prd, design, plan, comp). None of that 18-skill surface can be fixed by `default_action` since none of those skills are koto templates, but it is unambiguously in scope for "all scenarios where commands are hardcoded in the text instructions of the workflow."
