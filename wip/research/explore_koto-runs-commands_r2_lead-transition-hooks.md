# Lead: Is there a mechanism in koto -- or a plan for one -- that would take koto's own retry bookkeeping out of the agent's hands?

## Findings

**1. The eight blocks are one template, copy-pasted verbatim.** `work-on.md:1046-1060` (verification's `failed` outcome), `phase-3-analysis.md:80-93` (`scope_changed_retry`), `phase-4-implementation.md:150-162` (`scope_expanded_retry`), `phase-4a-scrutiny.md:48-60`, `phase-4b-review.md:46-58`, `phase-4c-qa.md:44-57` (all three panels' `blocking_retry`), and `phase-5-finalization.md:82-94` (`issues_found`) are byte-identical in shape: a `for KEY in scrutiny_results.json review_results.json qa_results.json summary.md` loop calling `koto context remove <WF> "$KEY"`, checking both the remove's exit status and a follow-up `koto context exists`, hard-`exit 1` with a fixed four-line warning if either signal is bad, then a single `koto next --with-data`. Even the surrounding explanatory paragraphs ("The block stops if **either** signal fires...", "The rule that falls out...") are copied verbatim across five of the seven files. The only per-site differences are the `OUTCOME_FIELD` variable, the outcome value being submitted, and which "stop" outcome the warning names (`cannot_verify`, `blocking_escalate`, `scope_changed_escalate`, `deferral_requested`). This is template stamped by hand, not logic that differs per phase.

**2. Context is the one artifact koto never gave epoch scoping to, and the other three got it years before this problem showed up.** `src/session/context.rs` defines `ContextStore` as a flat `session -> key -> bytes` map (`Manifest.keys: BTreeMap<String, KeyMeta>`, `KeyMeta` carrying only `created_at`/`size`/`hash`). `ctx_exists` (`src/session/local.rs:578`) is a raw file-existence check with zero knowledge of state, epoch, or visit count. Compare that to evidence and gate overrides, which are both epoch-scoped by construction: `src/engine/persistence.rs:722` (`derive_evidence`) and `:796` (`derive_overrides`) each scan the event log backward for the most recent `Transitioned`/`DirectedTransition`/`Rewound` event targeting the current state and only consider events after that index -- literally the same 15-line "find epoch_start_idx" block duplicated in both functions (and a third time as the named helper `epoch_slice`/`entry_slice` at `persistence.rs:1064-1112`, used by the dashboard's blocked-classification and by `derive_last_gate_evaluated`). `DESIGN-gate-override-mechanism.md` states the override design outright: "Override events must be sticky within the current epoch (the span of events from the most recent state-entry to the next state transition or rewind)." Gate outputs (`GateEvaluated`), decisions, and overrides all reset automatically on re-entry into a state. Context does not reset on anything, ever, short of an explicit `koto context remove`.

**3. The raw data to epoch-scope context already exists in the event log, unused.** `koto context add`/`koto context remove` each append `ContextAdded`/`ContextRemoved` events (`src/cli/context.rs:40-46`, documented at `docs/reference/session-feed.md:625-674`). Neither payload carries a `state` field, but none of the epoch machinery needs one -- `epoch_slice` works purely positionally, by comparing event sequence position against the last state-entry event's index. `evaluate_context_exists_gate` and `evaluate_context_matches_gate` (`src/gate.rs:118-190`) don't use this at all; they call `store.ctx_exists`/`store.get` directly against the flat store, bypassing the event log entirely. An epoch-scoped context-exists gate is a matter of asking "is there a `ContextAdded` for this key in `epoch_slice(events, current_state)` with no later `ContextRemoved` in the same slice" instead of asking the flat store -- reusing an existing, already-tested helper, no new event schema.

**4. `context_assignments` -- shirabe's own answer to "let koto write context automatically" -- is a documented, diagnostics-recommended template field that does nothing.** Filed today as koto issue **#204** by the current user: `context_assignments` is used at `work-on.md:101, 187, 219, 264, 317, 351, 372, 423, 428` (19 total occurrences per the issue) to write `failure_reason` on `done_blocked`-routing transitions, e.g.:
```yaml
- target: done_blocked
  when: {status: blocked}
  context_assignments:
    failure_reason: "context_injection blocked: ${evidence.detail}"
```
Neither `TemplateState` nor `Transition` (`src/template/types.rs:54-91`, `:136-140`) declares the field. It parses because `#[serde(deny_unknown_fields)]` is deliberately absent from `TemplateState` (compile-cache forward-compat), compiles clean, and is silently dropped -- "Searching `src/` for `context_assignments` returns only comments and one string literal." Yet koto's own W5 lint (`types.rs:1242`) *recommends* it as a remedy ("write it via default_action / context_assignments"), and the doc comment at `types.rs:1074` and a `TODO(issue-8/W5)` at `types.rs:~1230` both acknowledge "the runtime context-assignment surface lands in a later phase" -- it was designed, named in diagnostics, adopted by the only downstream consumer, and never built.

**5. The self-referential-call question, answered definitively -- and it's worse than the locking-code reading below predicted: it deadlocks.** My own read of the locking code said this should work mechanically:
   - The state-file flock at `src/cli/mod.rs:3836-3848` is acquired only `if state_is_batch_scoped(...)` -- "Non-batch workflows intentionally skip the lock." None of `analysis`/`implementation`/`scrutiny`/`review`/`qa_validation`/`finalization` are batch-scoped parent states, so a `koto next` invocation for any of them holds no state-file lock at all by that path.
   - `ContextStore::add`/`remove` (`src/session/local.rs:514-620`) take their own independent per-key and manifest flocks, decoupled from that state-file lock.

   That reasoning is **corrected by an empirical probe the orchestrator ran against shipped koto 0.11.6** (`wip/research/explore_koto-runs-commands_r2_lead-empirical-probe.md`, P11-P13): a `default_action` command that invokes `koto context add`/`context list`/`context remove` -- against its own session OR an unrelated one -- times out at the action's 30-second cap, exit -1. So do read-only commands (`koto status <other-session>`) and whole-store scans (`koto workflows`, which enumerates every session). Only `koto version` (no session-store access) returns cleanly, in 0.06s. The same `koto context add` run from a normal shell finishes in 30ms. The conclusion the probe draws, which I did not independently re-locate in code: the outer `koto next` holds a lock with workspace-wide scope for the duration of its whole advance loop (not the narrow, batch-only, per-state-file flock I found), and any nested koto process that touches the session store -- any session, read or write -- blocks on it until the timeout kills the process group. I looked for a second, unconditional lock to confirm the exact acquisition site and found `acquire_state_flock` in `src/engine/persistence.rs:399` (a *blocking* `LOCK_EX`, used by `append_event_idempotent` for the idempotency read-then-write window) as a candidate for the same-session case, but it does not explain the cross-session and read-only blocking the probe observed, so the actual lock is still unidentified -- flagged as an open question below rather than asserted.

   Locking aside, there is a second, independent reason `default_action` could not safely absorb this even if the lock problem were fixed: **failure propagation**. `ActionResult` (`src/engine/advance.rs:35-50`) has exactly three variants -- `Executed{exit_code,...}`, `Skipped`, `RequiresConfirmation{...}` -- and the advance loop's step 5 match (`advance.rs:286-310`) treats `Executed` and `Skipped` identically: "Continue to gate evaluation," regardless of `exit_code`. A `default_action` running the retry-clearing loop that hit a remove failure (the exact "unreadable store" scenario the block's dual-signal check exists to catch) would still fall through to gate evaluation on stale context, silently. So two independent defects rule out the naive "make it a `default_action`" fix, either one sufficient on its own: it deadlocks every time (confirmed), and even without the deadlock it has no mechanism to fail closed on a partial clear (confirmed by the `ActionResult` match arms).

## Implications

The eight blocks aren't eight instances of the agent making a judgment call -- they're eight instances of the agent hand-simulating a piece of state-machine bookkeeping (epoch-scoped presence) that koto already implements for every other kind of per-state data (evidence, gate overrides, gate-evaluated output) and simply never extended to context. Two remediation paths, not mutually exclusive:

- **Epoch-scope `context-exists`/`context-matches` gates** (add `scope: epoch` on `Gate`, default `session` for backward compat; when set, `evaluate_context_exists_gate` derives presence from `epoch_slice`-filtered `ContextAdded`/`ContextRemoved` events instead of the flat store). This removes all eight blocks outright -- no `koto context remove` call needed anywhere, because a fresh entry into `scrutiny`/`review`/`qa_validation`/`finalization` (all four retries route through `implementation` first, i.e. always arrive from elsewhere, which closes the epoch under both `AnyEntry` and `ArrivalFromElsewhere` boundaries) automatically makes the prior round's write invisible to the gate, with no risk of a silently-swallowed failure because there's no remove call to fail. `analysis`'s own `scope_changed_retry` self-loop also closes its epoch under `AnyEntry`, so `plan_artifact`'s gate on `plan.md` would need `scope: epoch` too if this path is taken -- note this is the one key `phase-4a-scrutiny.md` explicitly says must NOT be cleared on a panel retry ("`plan.md` is deliberately NOT in the list"), so the two behaviors (epoch-reset on self-loop for analysis's own gate, persistence across the panel states) are consistent with per-gate opt-in but would conflict under any all-context blanket epoch-reset.
- **Implement `context_assignments`** (issue #204) and extend it to express removal, not just writes -- e.g. a sibling `context_removals: [key, ...]` list on `Transition`, applied by the engine atomically with the transition write, before the target state's gates are next evaluated. This is a smaller, template-author-controlled version of the same idea and doesn't touch gate semantics at all; it just moves the `for KEY in ...; koto context remove` loop from agent-issued shell into engine-executed transition metadata, with the engine's own persistence layer (not a spawned subprocess `koto context remove` that can silently fail without stopping anything) responsible for it succeeding or the transition itself failing.

Either one is a real koto change, not a shirabe-side workaround. Round 1 already established `koto init`, `koto next`, `koto workflows`, `koto rewind` are agent-issued and can't become actions -- this block is different: it's a case where the entire operation (four removes + two-signal existence check + conditional exit) is pure bookkeeping around state that koto itself owns, with no judgment content at all. It's the strongest candidate found so far for "koto should just do this," but the only currently-shipped mechanism that could do it (`default_action`) can't safely absorb it because of the swallowed-failure problem in point 5.

## Surprises

- Issue #204, exposing the exact gap this investigation independently arrived at from the koto side (`context_assignments` unimplemented, W5's own remedy pointing at dead code), was filed by the same user today, hours before this exploration -- worth flagging to the user/lead since it may already be slated for action outside this workflow.
- `derive_evidence` and `derive_overrides` duplicate the identical 15-line epoch-boundary scan rather than both calling the named `epoch_slice`/`entry_slice` helper in the same file. Not this lead's problem to fix, but it means "the epoch concept" currently exists as three near-identical hand-written copies plus one named helper, not one canonical primitive -- a fourth copy for context would fit the current pattern but a design that instead unifies all four onto `epoch_slice` would be the better foundation to build epoch-scoped context gates on top of.
- The dual-signal check in every block (`remove`'s exit status OR a follow-up `exists`) has a real, previously-documented justification: `session/local.rs`'s `remove` deletes the content file, then the per-key lock, then the manifest, in that order, so it can fail after the gate-relevant effect (content file gone) already landed, and separately `ctx_exists` can't distinguish "key absent" from "store unreadable." Epoch-scoping the gate off the event log sidesteps this whole class of failure mode -- an event-log read failure is a different, already-fatal error path for `koto next` generally, not a silent pass.

## Open Questions

- Where exactly is the workspace-wide lock the empirical probe found, and is its scope deliberate? Not `src/cli/mod.rs:3836-3848` (batch-only, non-blocking, per-state-file -- doesn't explain cross-session blocking) and not conclusively `src/engine/persistence.rs:399`'s `acquire_state_flock` (same-session, and only invoked when `append_event_idempotent` runs -- doesn't explain `koto version`-vs-everything-else or the cross-session block on its own). This needs someone to either instrument the binary or grep more exhaustively than this pass did; it's the load-bearing fact for "action can't call koto" and neither round has pinned the acquisition site.
- If `scope: epoch` is added to `Gate`, does it also need to apply cross-state -- e.g., should `finalization`'s gate on `summary.md` see a `summary.md` write from `implementation`'s epoch, or only from `finalization`'s own most recent epoch? The current blocks clear `summary.md` proactively from *other* states' retry loops specifically because the finalization gate has no epoch concept today; with epoch scoping the gate would naturally require `summary.md` to be (re)written during finalization's own epoch, which changes who is responsible for writing it, not just when it's considered stale. Needs a look at whether `summary.md` is currently ever written from a state other than `finalization` itself.
- Whether `context_removals` on `Transition` (if built) fires before or after the target state's gates run in the same `koto next` call matters for whether it can fully replace the shell blocks or only partially -- the current blocks clear-then-`koto next` in one shot; the engine would need to apply removals as part of the same transition-commit that the evidence submission triggers, ahead of the *next* tick's gate evaluation.

## Summary
The eight blocks are one identical shell template hand-copied seven times because koto's context store is the only per-state artifact (versus evidence, gate overrides, gate-evaluated output) that isn't epoch-scoped, even though the event log already carries the `ContextAdded`/`ContextRemoved` events needed to epoch-scope it with the exact `epoch_slice` mechanism koto already uses for the other three. The self-referential `koto context remove` call is doubly ruled out as a `default_action`: an orchestrator probe against shipped 0.11.6 confirms it deadlocks on a workspace-wide lock the outer `koto next` holds across its whole advance loop (site not yet pinned down -- not the batch-only flock I initially checked), and even absent that, `ActionResult::Executed` ignores exit code, so a failed clear would silently fall through to gate evaluation on stale context anyway. Koto issue #204, filed today, independently confirms the more template-native fix (`context_assignments`) is designed-but-unimplemented and recommended by koto's own diagnostics for exactly this kind of write -- and unlike a `default_action`, it would be applied by the engine itself, not by a nested CLI call, so it isn't exposed to the lock problem at all.
