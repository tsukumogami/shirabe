# Clarity Review

## Verdict: FAIL

The problem statement, user stories, and decision records are unusually concrete, but four requirements (R5's unnamed ceiling, R8's undefined trigger, R3's partial-resolution gap, and the unaddressed delivered-feature strikethrough) would send two developers to materially different tables, and several acceptance criteria can't be checked without a value the PRD never supplies.

## Ambiguities Found

1. **R5 / AC #5**: "the rendered cell SHALL NOT exceed a fixed character ceiling" -> The ceiling is never given a value anywhere in the PRD. One developer picks 120 characters, another picks 400, and both satisfy R5 while producing visibly different roadmaps. AC #5 ("No description cell in the generated table exceeds the character ceiling") then references a constant that doesn't exist in the document, so a reviewer has nothing to check against. This is the single largest fork point in the PRD. -> Name the number in R5 (for example "SHALL NOT exceed 200 characters"), or state explicitly that the value is a design decision and rewrite AC #5 to bind to whatever DESIGN fixes, with the design doc named.

2. **R5**: "truncated at a word boundary with an ellipsis marker" -> Four sub-questions have no answer. Is "character" a byte, a Unicode scalar, or a grapheme cluster (matters the moment a label or body carries non-ASCII)? Does the ellipsis count toward the ceiling or sit outside it? Is the marker `...` or `…` -- a test asserting one fails against the other? And what happens when the first word already exceeds the ceiling, so there is no word boundary to cut at? -> Specify the unit, state that the marker is included in the budget (or isn't), fix the literal marker, and give the no-boundary fallback (hard cut at the ceiling).

3. **R8 vs AC #8**: R8 fires "when a feature label contains a character that prevents the emitted dependency cell from reconciling against the table's keys"; AC #8 fires when "a feature label containing a comma" is present. -> Two mismatches. First, the character set is undefined: comma is the only one named anywhere, but a pipe (`|`) breaks the markdown table row outright and a newline would too, so a developer must guess whether those are in scope. Second, the trigger conditions differ. R8's condition is relational -- the diagnostic fires only when that label actually appears in some other feature's dependency cell and fails to reconcile. AC #8's condition is unconditional -- any comma-bearing label emits the diagnostic, whether or not anything depends on it. A roadmap with one comma-bearing leaf feature passes under R8's reading and fails under AC #8's. -> Enumerate the offending characters explicitly, and pick one trigger: either "any label containing one of these characters" (simpler, matches AC #8) or "only when the label appears in a dependency cell" (matches R8). Then make both statements say the same thing.

4. **R3**: "a cell with no resolvable reference SHALL read `None`" -> Two readings. (a) The cell is `None` when the feature declares no dependencies at all. (b) The cell is `None` when it declares dependencies but none of them resolve to a row. Under (b), a feature depending on one real feature plus one typo'd name gets a mixed cell -- and R3 never says what happens to the typo'd token. Does it survive verbatim (it isn't cross-repo, so the verbatim clause doesn't cover it), get dropped silently, or drag the whole cell to `None`? Silently dropping an edge is exactly the class of defect listed in Out of Scope ("plural dependency forms dropping edges"), so getting this wrong here reintroduces the neighbouring bug. -> Add a sentence covering the partial-resolution case: state what an unresolvable non-cross-repo token renders as, and whether it also triggers the R8 diagnostic.

5. **R3 / AC #3**: "Cross-repo references SHALL be preserved verbatim" and "A feature with only a cross-repo dependency renders that reference verbatim" -> "Cross-repo reference" is used four times and never defined or exemplified. A developer writing the fixture for AC #3 has to invent the syntax, and a reviewer verifying it has to guess whether the invented form is the one meant. -> Show one literal example of a cross-repo dependency as it appears in a feature's `Dependencies:` line and as it must appear in the rendered cell.

6. **R1, R2, AC #1** (delivered features): The shared spec strikes a delivered feature's rows (`| ~~<entity row>~~ | ~~<deps>~~ | ... |`), and the current renderer already does this via its terminal-feature branch. The PRD never mentions delivered or terminal features. -> AC #1 says "every entity row's first cell is that feature's label", which reads as failing for a delivered feature whose cell is `~~Foundation layer~~`. R2's fallback is likewise unclear: `F3` or `~~F3~~`? And R3's "the same text their own rows carry in the key column" would, read literally, put strikethrough markers inside other features' dependency cells. -> Add a sentence stating that strikethrough decoration on delivered rows is orthogonal to the key form, that the R2 fallback is struck on the same terms, and that dependency cells name the undecorated label.

7. **R1**: "the feature's label, with any trailing issue-link decoration stripped -- the same text the issueless dependency diagram already uses for that feature's node label" -> The requirement gives two definitions and asserts they agree. If the diagram's label helper does anything else (collapses whitespace, trims a leading marker, truncates), the two clauses diverge and a developer must decide which is normative. The decoration form itself is never shown. -> Make one clause normative ("the same text the issueless dependency diagram uses for that feature's node label") and demote the other to a parenthetical description, or show a before/after pair: input label, rendered key.

8. **R2**: "the key column SHALL fall back to `F<n>` for that row" -> What `n` indexes is assumed but never stated: 1-based position among all features in the Features section, presumably, but a developer could reasonably read it as position among rendered rows (which differs if any feature is skipped). "Empty after decoration is stripped" also leaves whitespace-only labels unaddressed. -> State the index basis explicitly and say that a label that is empty or whitespace-only after stripping triggers the fallback.

9. **R7**: "stating how the author can control the summary" -> No required content, so any message satisfies it; "how the author can control the summary" is exactly the kind of clause a reviewer can't fail. AC #7 only checks that the feature is named, so the second half of R7 is untested. -> Require the diagnostic to name `**Functional outcome:**` as the remedy, and extend AC #7 to check for that string.

10. **R9 / AC #12**: "The `--no-issues` help text SHALL describe the table the renderer actually produces." -> This restates the goal rather than stating a testable condition; a one-word help string arguably "describes" the table. AC #12 ("describes the label-keyed table") narrows it but still rests on reviewer judgment. -> List the specific facts the help text must state (key column carries the feature label, dependency cells name labels, descriptions are bounded), so the check is a presence test.

11. **R11 / AC #15**: "The finding ... SHALL be recorded in the pull request that lands this work" / "The pull request states whether the description defect was a regression or an uncovered path, with the evidence." -> This is a process requirement sitting in Functional Requirements, and "with the evidence" is unbounded -- a reviewer can't say what quantity of evidence discharges it. D4 already states the answer and the reasoning, so the requirement is really "copy D4's conclusion into the PR body". -> Either say that directly ("the PR body SHALL state that the earlier fix covers issueless mode and never bounded the result, per D4") or move R11 out of Requirements into a delivery note.

12. **R12**: "no new notice-level finding relative to the current renderer's output" -> The baseline is a moving target that the PRD doesn't pin. A reviewer months from now cannot reconstruct "the current renderer's output" to diff against. -> Name the baseline concretely: a committed fixture roadmap plus its recorded `shirabe validate` output at the pre-change commit.

13. **R14**: "a change to that helper SHALL be assessed against both" -> "Assessed" describes an activity, not an outcome; nothing distinguishes a done assessment from an undone one. AC #11 ("issue-creating mode's existing tests pass unchanged") is the real, binary criterion. -> Rewrite R14's second sentence as the outcome: a shared-helper change SHALL leave issue-creating mode's rendered output byte-identical for the existing fixtures.

14. **R13**: Has no acceptance criterion at all, and its "Feature labels SHALL round-trip verbatim into the rendered table" sits in tension with R1, which strips decoration from those same labels before rendering. -> Scope the verbatim claim ("after decoration stripping, no further transformation is applied to label text") and add an AC covering a label carrying shell metacharacters.

15. **AC #14**: "Regression tests cover the key column, the dependency cells, the description ceiling, and both diagnostics." -> "Cover" admits one smoke test per area or twenty; not binary. -> The cases are already enumerated in ACs 1-10; replace this with "each of AC 1-10 has a corresponding test".

16. **Goals, bullet 2**: "No roadmap the tool writes contains a description cell that is a wall of prose." -> "Wall of prose" is subjective. It would be fine as a goal if R5 pinned it numerically, but R5 doesn't (item 1). -> Fixing R5 fixes this by reference.

17. **Goals, bullet 3**: "finds out when they populate, and knows what to change" -> "Knows what to change" isn't observable. -> Same fix as item 9: the diagnostic names the remedy.

## Suggested Improvements

1. **Add a worked example section**: The PRD would be substantially harder to misread with one before/after block -- a two-feature roadmap fragment (one with `**Functional outcome:**`, one with a bullet-list body and a cross-repo dependency) alongside the exact table it must render. That single addition disambiguates items 2, 5, 6, and 7 at once, and gives the implementer a fixture.

2. **Split R5 into two requirements**: one for the ceiling (value, unit, what counts) and one for the truncation mechanics (word boundary, marker, no-boundary fallback). They're separately testable and currently share a sentence.

3. **Reconcile R8 and AC #8 in the document, not in review**: The mismatch between R8's relational trigger and AC #8's unconditional one is the kind of thing that surfaces as a failing test at the end of implementation. Pick one and edit both.

4. **Give the diagnostics required substrings**: Both R7 and R8 ask for a diagnostic "naming the feature" plus prose. Specifying the required substrings (feature label; `**Functional outcome:**` for R7; the offending character for R8) turns two judgment-call ACs into string assertions.

5. **Move R11 out of Functional Requirements**: A requirement on PR body text isn't a property of the built artifact, and it's the only requirement in the section that can't be exercised by a test.

6. **Writing style -- minor**: No banned words appear (checked: tier, robust, leverage, comprehensive, holistic, facilitate, and the wider AI-tell list). Contractions are used, specifics are named (`concise_description`, FC06, file paths), and sentence-length variation is genuinely good. Three small things: em dashes run to nine across the document and several sit inside requirement text where a colon reads cleaner (R1's "-- the same text...", D4's "-- the issueless renderer calls..."); R13's trailing clause "which is the existing security invariant of the populate module" turns a requirement into an assertion and should be its own sentence; and D3's "It is left as a separate question" is a passive nominalization -- "we're leaving it as a separate question" is more direct.

## Summary

This PRD is well above the usual bar for specificity -- the problem statement names the exact heuristic that fails and why, the decision records argue their alternatives with evidence rather than assertion, and the user stories each derive a test case. What holds it back is that four requirements leave real forks open: R5 never gives the character ceiling that three acceptance criteria depend on, R8 and AC #8 disagree about when the diagnostic fires, R3 doesn't say what happens to a dependency cell that partly resolves, and nothing in the document addresses how the key form interacts with the strikethrough the spec already requires for delivered features. All four are small edits, but until they land, two developers reading this would ship different tables and a reviewer couldn't objectively fail either one.
