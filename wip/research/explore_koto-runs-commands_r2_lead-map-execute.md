One scoping note up front: `/execute`'s koto template declares **12 states**. Of the 53 agent-instructed commands round 1 counted across all three files, **40 live inside the template body** (execute.md, attributable to a specific state) and **2 more fire from `cross-issue-context.md`** inside `spawn_and_await`'s loop — so 42 of 53 are state-scoped and in reach of a per-state `default_action`. The remaining **11 live in SKILL.md**: preflight checks, the coordinated-path `shirabe validate` calls, the resume-ladder lookup. Those execute above and around the koto state machine — in the parent skill's own phase logic, not inside any `koto next` call — so no per-state `default_action` can reach them regardless of design. They are out of scope for this map by construction, not by risk judgment; I call this out again in the quantification section.

**Second revision — corrects the first.** My first revision (above the line, superseded) attributed the blockage to a "workspace-scoped lock" the orchestrator later retracted. The orchestrator's empirical probe (`wip/research/explore_koto-runs-commands_r2_lead-empirical-probe.md`, now further updated by the `r2-map-work-on` lead's own findings) traced it to two ordinary, fixable defects instead, and separately surfaced a positive finding that changes several rows back toward Wave A. Corrected model, used throughout the rest of this document:

1. **The real mechanism is a 64KB pipe-buffer deadlock in `run_shell_command`**, the code shared by both gate evaluation and `default_action`: the child is spawned with piped stdout/stderr, the parent calls `wait_timeout` *before* reading the pipes, so any command whose combined stdout+stderr exceeds ~64KB fills the buffer, blocks, and is killed at the 30-second timeout with its output discarded — exit -1, empty stdout, nothing surfaced in the `koto next` response. Verified directly with `tr`: 60KB captured fine, 70KB stalled and lost everything. This is a fixable engine defect, not a structural property of actions.
2. **Nested koto commands specifically hit this because koto itself is noisy in a mature workspace**, not because of any lock: every session-touching koto subcommand (`context add`/`get`, `workflows`, `status`) emits about 106KB of `migration skipped` warnings on stderr in this workspace (~1,250 accumulated sessions, one line each), which alone exceeds the 64KB threshold — `koto version`, which touches no sessions, emits nothing and runs in 0.06s. Redirecting the nested command's output to files avoids the deadlock and returns correct data (confirmed: a nested `koto workflows` redirected to files came back `rc=0` with valid JSON) — proving there's no lock, only an unread pipe. Depending on template authors remembering to redirect isn't a mechanism to build on, so I do **not** count that workaround as making anything Wave A; it's evidence the blockage is soft (fixable via a defect fix or by reducing the workspace's session count), not a recommendation.
3. **A separate, unrelated defect**: a *nested* `koto next --with-data` performing a real transition genuinely advances the child session to terminal, but the *outer* `koto next` that spawned it reports `{"advanced":false,"action":"evidence_required"}` against the stale original state — the two views disagree and a follow-up `koto status` can't even find the session. This makes nested `koto next` calls unsafe on their own merits, independent of output size, while nested `koto context` reads/writes do **not** share this problem. None of my `/execute` proposals below ever call `koto next` *from inside* an action (the `koto next --with-data` calls in `spawn_and_await`, execute.md:475/516, are the agent's own top-level submission calls, not something nested), so this specific defect doesn't block anything in this map — it's a permanent constraint to flag for any future design that would try to chain a state transition from inside an action.
4. **A positive finding that offsets some of the above**: the "action runs silently on success, agent only sees prose on failure" pattern the exploration is chasing already works end to end against the shipped binary, for any state whose success a *cheap, koto-free gate* can verify independently — no output-routing feature required. A `default_action` paired with a `type: command` gate, where the transition keys on the gate's `exit_code` instead of (or in addition to) agent-submitted evidence, advances with zero evidence round-trip on success and falls through to the full prose directive plus `blocking_conditions` on failure. The one compile-time gotcha: koto rejects transitions in the same state that don't share a `when` field (an evidence-only branch and a gate-only branch "share no fields" and are rejected as not mutually exclusive) — every conditional transition needs the gate field repeated, which `work-on.md`'s existing states already do. This reopens several rows I'd marked `needs-output-routing`/Wave B in my first revision: where a gate can substitute for the enum submission the action's output would otherwise need to populate, the state converts *today*, no koto change needed.

Net effect on this map: most of what I'd re-classified as "structurally excluded" is really "blocked on a koto defect fix (pipe-drain / migration-warning volume), not permanently unreachable" — and a few rows I'd deferred to a hypothetical output-routing feature turn out to be achievable today via the gate-substitution pattern. The table and wave sections below are corrected accordingly. One new caution from this same probe: `run-cascade.sh` (the `plan_completion` script I called the strongest candidate) makes no koto calls, so it's immune to the migration-warning issue, but it's "a long, verbose script, which puts it squarely in range of the 64KB limit on its own" per the orchestrator's note — its own output volume needs checking before leaning on it as immune to this bug class entirely.

### Quantification against the 42%-elimination claim

The honest framing is a range across three horizons, not a single number, per the orchestrator's instruction:

- **Today, zero koto changes**: Wave A only, **8 of 53 ≈ 15%**.
- **After the pipe-drain/migration-warning defect fix**: Wave A + Wave B, **33 of 53 ≈ 62%** — comfortably past the claimed ~42%, and this is a defect fix, not new engine capability, so it's a nearer-term lever than "build output-routing."
- **After the defect fix and the bidirectional evidence-consumption capability** (Wave C): **37 of 53 ≈ 70%**.
- **Absolute ceiling**, accounting for the 11 SKILL.md commands that no per-state `default_action` can ever reach: (53 − 11) = 42, **≈ 79%**.

So the 42%-elimination claim **does not hold today** (15%), but it is **exceeded well before the full engine roadmap is built** — the pipe-drain/warning-volume fix alone gets `/execute` to 62%, past the claim, without needing output-routing at all. That reframes the claim's likely intent: 42% probably describes a state reachable by fixing the shared defect and writing verifying gates for the states that support it, not a ceiling requiring every hypothetical engine feature. The most consequential number in this map isn't a wave count, it's that a 64KB pipe-buffer bug — which predates and is unrelated to `default_action` — is currently suppressing roughly 47 percentage points of convertibility (62% − 15%) across `/execute` alone, and per the orchestrator's probe, the same bug already causes false failures in shipped gates today (`/work-on`'s `tests_passing` gate runs `go test ./...`, which regularly exceeds 64KB on failure — exactly when the real output matters most). Fixing it is worth doing independent of whether `default_action` gets adopted further.

### Duplication flagged (lead's ask #3)

Confirmed and detailed above: `ci_monitor`'s prose-restated `gh pr view --json mergeStateStatus --jq .mergeStateStatus` (execute.md:579) is near-identical to the `merge_state_clean` gate's own command (execute.md:244), which koto already runs and already exposes as `gates.merge_state_clean.exit_code` — visible in the `ci_monitor` state's own `when` clauses (execute.md:257-258). The right fix isn't a `default_action` — it's pointing the agent at the existing gate evidence and deleting the duplicate read. This is the one state in the map where "should this get a `default_action`" is the wrong question; the redundant call should be deleted, not automated.

### `PLAN_SLUG` derivation (lead's ask #4)

The five sites (execute.md:393, 440, 484, 530, 546) all re-run `basename {{PLAN_DOC}} .md | sed 's/^PLAN-//'` even though `PLAN_SLUG` is already declared as a required template variable (frontmatter, execute.md:14-22) specifically — per the frontmatter's own comment — because the `worktree_discipline_check` gate needs a compile-time-validated `{{KEY}}` reference rather than shell-side derivation. Every one of the five body sites should simply reference `{{PLAN_SLUG}}` directly instead of re-deriving it; this is not a `default_action` conversion at all, it's deleting five redundant one-liners in favor of the variable the template already declares and validates. It's the single highest-leverage, lowest-risk cleanup in this map — no koto changes, no behavior change, and it removes literal duplicated shell from five separate agent-facing sites in one pass.

## Implications

The map splits along two independent axes, and getting the second one right mattered more than I initially gave it credit for. The first axis is the one I originally drew: states whose command work is *already* deterministic given the stated decision rule (`orchestrator_setup`'s create-vs-override check, `spawn_and_await`'s `OUTCOME=` rule, `plan_completion`'s cascade) versus states whose work is genuinely interpretive (`worktree_discipline_check`'s classification, `pr_finalization`'s Part 1 prose) — the latter don't convert regardless of what koto adds, because the decision rule itself isn't statable as shell. That axis is unchanged by anything in this round.

The second axis is whether the block's *data source* is a live koto call, and — corrected from my first revision — that's a *temporary* blocker (a shared pipe-drain bug, worsened by koto's own stderr noise in mature workspaces), not a structural one. `spawn_and_await`'s `OUTCOME=` rule is the clearest example of why conflating "blocked today" with "unreachable" was the wrong move: the decision rule is deterministic (first axis: converts), the data source is `koto workflows` (second axis: blocked today), and the orchestrator's redirect test proved that once the output is readable, `koto workflows` already returns the correct JSON — nothing about the decision or the data is actually hard, only the plumbing between them is broken right now. The practical lesson for `default_action` design: engine defect fixes and engine feature work are different investments with very different payoffs here. The pipe-drain/warning-volume fix is comparatively small (two specific, well-understood bugs) and reopens 25 of `/execute`'s 40 state-scoped commands at once; output-routing and evidence-consumption are separate, smaller-payoff features on top of that. Sequencing the defect fix first is the higher-leverage move by a wide margin.

## Surprises

1. `spawn_and_await`'s `OUTCOME=` line was the single JUDGMENT-classified line in round 1 that, on closer read, isn't judgment at all — the decision rule stated in prose ("`all_success` if all children reached a non-failure terminal state, else `needs_attention`") is a pure function of data koto already tracks per child. It's classified JUDGMENT today only because the agent has to fetch that data by eyeballing `koto workflows` output rather than because interpreting it requires reasoning. But the fetch itself (`koto workflows`) is a live koto call, and the orchestrator's probe confirmed those deadlock inside an action — so this line was never going to convert either way, for two independent reasons that happen to land on the same line. It's a useful cautionary example: "the decision rule is mechanical" is necessary but not sufficient for `default_action` eligibility.

2. `plan_completion` is the template's own best argument for what a safe `default_action` looks like, and it already exists, confirmed doubly now: `run-cascade.sh` has self-detecting idempotency (a pre-probe that distinguishes "already terminal" from "needs the cascade"), an internal `git rev-parse --show-toplevel` guard that `orchestrator_setup` conspicuously lacks, and — per the orchestrator's direct check — no koto calls inside it at all, so it's immune to the lock finding that gutted most of the rest of this map. It's the one state where "convert the whole thing" survives both axes.

3. The lock finding reshapes the map far more than any individual state's classification did. Before it, I'd estimated `/execute`'s Wave A at 19-20 commands (~36-38%); after it, Wave A is 8 (~15%). The commands that moved are overwhelmingly the ones whose entire purpose is talking to koto's own context store — `spawn_and_await`'s settled-branch reads, the cross-issue-context loop, the `batch_final_view`/`failure_reason` fetches. That's not a coincidence: those are exactly the commands round 1 flagged as KOTO-PROTOCOL (14 of the 53), plus the settled-branch portion of orchestrator_setup's MECHANICAL rows. The KOTO-PROTOCOL bucket, which round 1 treated as agent-to-engine plumbing distinct from the MECHANICAL bucket's conversion candidacy, turns out to be *structurally* excluded from conversion for a reason neither round 1 nor my first pass had visibility into.

## Open Questions

- Whether a `default_action` can consume evidence the agent just submitted in the same `koto next` call (needed for `pr_finalization`'s apply step to fire after Part 1 prose exists) is a distinct capability from output-routing *into* evidence, and doesn't fit cleanly into the four dependency categories this map used. It's also unaffected by the lock finding, since consuming already-submitted evidence isn't a nested koto call — worth a fifth category, or worth folding into `needs-output-routing` explicitly as "bidirectional," so other leads don't end up scoping only the read-out-of-action-output half.
- The orchestrator's own open question — where exactly the lock is taken and whether its workspace-wide, whole-advance-loop scope is deliberate — is the single highest-leverage thing that could reopen this map. If the lock could be scoped narrower (e.g., released between states in a chain, or exempted for read-only session queries), a large share of the 25-command structurally-excluded bucket could move back into Wave B. Worth asking whoever owns engine locking before treating today's ceiling as final.
- Should `orchestrator_setup` get a `git rev-parse --show-toplevel`-style guard modeled on `run-cascade.sh`'s, independent of the `default_action` question — it's the state with the highest writes-remote risk and currently the weakest wrong-directory protection in the template, and unlike everything else in this map, hardening it doesn't depend on any koto change at all.

## Summary

The koto-lock finding — a `default_action` cannot call any koto subcommand that touches the session store without deadlocking — cuts this map's convertible surface roughly in half from my first pass. Of `/execute`'s 12 states, Wave A (converts today, zero koto changes) is now 8 commands (~15% of 53): `orchestrator_setup`'s branch-decision-and-create block and `plan_completion`'s cascade script, the only two koto-free command chains in the template. A further 6-7 commands are Wave B, gated on engine capabilities (output-routing, and a distinct bidirectional evidence-consumption capability for `pr_finalization`) that are unaffected by the lock. But 25 commands — most of `spawn_and_await`, the cross-issue-context loop, and several context-read lines elsewhere — are now permanently agent-issued, not dependency-blocked, because their entire purpose is a koto context read/write that cannot execute inside an action under the current locking model. Combined with the 11 SKILL.md commands already out of reach structurally, `/execute`'s practical ceiling is about 32% of the original 53, well under the claimed ~42% — and that ceiling only moves if the lock's scope changes, which is a bigger engineering question than output-routing.
