## Prior findings — closed or not

**1. R21 had no acceptance criterion.** Closed. The AC block now includes: "`scripts/validate-template-mermaid.sh`, `scripts/check-template-directives.sh` and `scripts/check-template-interpolation.sh` all pass against the edited templates (R21)." All three scripts exist at the named paths in this worktree (verified by `find`). This is a direct, deterministic pass/fail check with zero remaining ambiguity.

**2. R6/R7/R8 would pass a hollow evidence value.** Substantially closed, not merely relocated. The new AC reads: "Every evidence-carried obligation's field is typed to a concrete referent — a path, a commit identifier, or a named command's output — and submitting a placeholder or empty value for it fails the state rather than satisfying it. Demonstrated per field, not asserted (R7, R7a)." The load-bearing change is "demonstrated per field, not asserted": a tester must actually attempt to submit an empty/placeholder value against each evidence field and observe the state reject it. A wrong implementation that keeps the field as a bare `required: true` string (today's actual koto schema types in `skills/work-on/koto-templates/work-on.md` are only `enum`, `string`, `command`, `context-exists` — there is no built-in `path` or `commit-id` type) would fail this demonstration outright, because a placeholder string satisfies `required: true` and the AC would then be unsatisfiable as written. That is a genuine falsifiability gain, not a relabeling. The residual gap — a well-formed but *irrelevant* referent (e.g., a real commit SHA that isn't actually the cleanup commit) could still pass a naive "is this a valid commit identifier" check — is real, but it is the same residue the PRD itself names in Known Limitations ("the remainder become evidence fields whose honesty depends on the run... this feature narrows the gap rather than closing it"). Disclosed residue is different from a silently hollow criterion; I treat this as adequately closed with a documented limitation, not as a repeat of the original failure.

**3. R16's routing-claim search had no reproducible query.** Substantially closed. R16 is now split as claimed: R16a requires a committed inventory (file, line, prior text, new text) and explicitly requires the two previously-missed spots (`README.md`, the pipeline-model reference) to appear in it; R16b requires the inventory to record the exact command that produced its candidate set, so a reviewer can re-run it. Combined with the PRD's own operational definition of "routing claim" (a statement directing a reader/agent to one entry point vs. the other, as opposed to an occurrence that merely names the mode as a value/schema field/fixture), two reviewers re-running the same command and applying the same definition should converge on the same residue. This is a real improvement over "manually triage ~890 hits with no query and no definition." One caveal remains and is worth naming rather than treating as disqualifying: the check validates that the *command's own hits* are all accounted for, not that the command's search terms have full recall over the corpus — a command with too-narrow search terms could still miss an unknown-unknown routing claim phrased without the searched string, and re-running that same narrow command would never surface it. This is a bound inherent to any lexical-search-based completeness check (the completeness reviewer's territory more than testability's), and the AC mitigates the one concretely known instance of it (README/pipeline-model) by naming those files outright.

## Observations

The document's own Known Limitations section does real work here: by naming "classification is a judgment itself" and "evidence honesty depends on the run" as accepted residue, it keeps the corresponding acceptance criteria from reading as guarantees they can't deliver. That is the right way to handle a hole that can't be fully closed by a checkbox — better than the alternative of an acceptance criterion that implies more certainty than the mechanism provides.

Two small, non-blocking things worth a future pass: the AC for R6/R7/R8 refers to "the classification table," a term the PRD never defines or locates (R8's own text says the classification is "recorded with the obligation," which reads as distributed annotation rather than one centralized table) — a downstream design or plan doc should settle which artifact a tester is meant to open. And AC1/AC3's "no cascade-related text" phrase was flagged as soft in the prior round and is unchanged; it's bounded enough by surrounding prose to survive this review, but a concrete negative check (e.g., "the run's output does not name the cascade script, the words cascade or chain, or reference a BRIEF/PRD/DESIGN/PLAN") would remove the last bit of interpretive room.
