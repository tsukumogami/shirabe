# Lead: What does run-cascade.sh require as input, what does it do step by step, and exactly how does it behave when the document chain is absent or partial?

## Findings

### 1. Invocation contract

`skills/execute/scripts/run-cascade.sh:12` — `Usage: run-cascade.sh [--push] <plan-doc-path>`. The PLAN path is a required positional argument; there is no way to invoke the script with zero arguments (`run-cascade.sh:719-721` calls `usage` and exits 1 with no JSON at all if `$#` is 0) and no way to point it at a DESIGN/PRD/BRIEF/issue instead of a PLAN — the only flag is `--push` (`run-cascade.sh:725-728`; `--help`/`-h` also exits 1 via `usage`, and any other `-*` is an "Unknown option" error, `run-cascade.sh:732-735`).

Environment/working-tree expectations, all fatal precondition failures on exit 1 with JSON on **stderr** (not stdout):
- Must run inside a git work tree: `REPO_ROOT=$(git rev-parse --show-toplevel …)` or exit 1 with `{"cascade_status":"skipped","steps":[],"error":"not a git repository"}` (`run-cascade.sh:750-753`).
- Must resolve a `shirabe` binary: `$SHIRABE_BIN` env var, else `shirabe` on `$PATH`, else `$REPO_ROOT/target/{release,debug}/shirabe`, else exit 1 (`run-cascade.sh:759-771`).
- The PLAN path must exist as a file (`run-cascade.sh:774-777`) and pass `validate_upstream_path`: resolves inside `$REPO_ROOT`, is a regular file (not a symlink), and is tracked by git (`run-cascade.sh:103-132`, called at `:779-782`).
- `--push` requires the current branch to already have a configured upstream (`git push` with no arguments, `run-cascade.sh:1051`) — confirmed by `scenario_push_failure_still_reports` (test file, ~line 2157), whose fixture has a bare origin with no tracking branch and gets a `push` step at `failed` rather than a script crash.

Output: for every run that reaches the cascade body (success, partial, or the internal "skipped" verdict), one JSON object goes to **stdout**: `{"cascade_status": "completed|partial|skipped", "steps": [...]}` (`run-cascade.sh:26-41`, `emit_result` at `:472-477`). Two classes of run never reach that: a usage error (`usage()`, exit 1, no JSON anywhere) and the setup/precondition failures above (exit 1, JSON on **stderr**, carrying an extra `"error"` key not present in the normal envelope). `execute.md:709-710` captures stdout into `RESULT` and reads `.cascade_status` with `// empty`, so a precondition failure (JSON on stderr, nothing on stdout) makes `CASCADE_STATUS` the empty string, which the `case` at `execute.md:720-728` correctly falls through to the `*)` (failure) arm on, since it only matches `completed|skipped` explicitly (`execute.md:731`: "Match the two good verdicts rather than testing for partial").

Exit codes (`run-cascade.sh:43-47`): 0 whenever the cascade actually ran (completed/partial/skipped verdict); 1 only for usage errors or the setup/precondition failures (PLAN missing, path validation, not-a-git-repo, shirabe unresolvable) — never for a failure inside the cascade itself. A `partial` verdict still exits 0.

### 2. Step sequence

1. **Argument parsing / setup** (`run-cascade.sh:717-790`): parse `--push`, resolve `REPO_ROOT`, resolve `SHIRABE_BIN`, validate the PLAN path.
2. **Pre-cascade lifecycle probe** (`run-cascade.sh:806-812`, `lifecycle_probe` at `:369-402`): runs `shirabe validate --lifecycle-chain <PLAN_DOC> --format json --mode=ready`. Expects **non-zero** exit (chain is mid-PR, not yet terminal). If the probe instead passes cleanly, the chain is already terminal, the script emits a single `lifecycle_pre_probe: skipped` step, calls `emit_result "skipped"`, and **exits 0 immediately** — no transitions, no `git rm`, no commit (`:806-811`).
3. **Read PLAN metadata**: derive `PLAN_SLUG` from the filename (`basename … | sed 's/^PLAN-//'`, `:818`) — this assumes the filename literally has a `PLAN-` prefix; used only if the chain later hands off a ROADMAP node.
4. **`shirabe finalize-chain <PLAN_DOC>`** (`:820-841`): a separate binary subcommand that walks the PLAN's `upstream:` frontmatter chain and, in `Mode::Apply`, actually applies each tactical node's terminal transition in-process (DESIGN→Current + `git mv` into `current/` + strip `## Implementation Issues`; PRD→Done; BRIEF→Done). It reports the PLAN itself as a `delete_plan` node but never deletes or transitions it (`crates/shirabe-validate/src/finalize.rs:59-66`). stdout/stderr are captured separately without letting `set -e` abort (`run-cascade.sh:833-840`).
5. **PLAN Active→Done flip** (`:851-860`): `shirabe transition $PLAN_DOC Done`, an "ephemeral, in-process" marker so the audit trail shows Done atomically with the deletion; failure here is logged as a warning and does **not** stop the script.
6. **Translate the finalize-chain report into cascade steps** (`:862-967`): on `finalize-chain` exit 0, parse `.nodes[]` in order, `git add` each transitioned path into `STAGED_FILES`, and dispatch on `action`: `transition_design`/`transition_prd`/`transition_brief` → `add_step … ok`; `roadmap_handoff` → deferred to `handle_roadmap` after the loop; `stop` (VISION/STRATEGY/cross-repo) → just logged, no step; `error` (unrecognized node mid-walk) → `ANY_FAILED=true` + a `failed` step, but the loop **keeps going** for any node already processed. On `finalize-chain` exit ≠0 (a refused transition), no report exists on stdout — a single synthetic `failed` step is added and `ANY_FAILED=true` (`:957-967`).
7. **`git rm -f` the PLAN** (`:969-1006`): always attempted, independent of whether step 6 failed. On success, appended to `STAGED_FILES` **only if `ANY_FAILED` is still false** (`:999-1001`) — this is the PR #353 gate discussed below.
8. **`handle_roadmap`** (`:497-606`), invoked from inside step 6 if a `roadmap_handoff` node was recorded: finds the `**Downstream:**` line referencing the PLAN's slug, walks up to the enclosing `### Feature N:` heading, rewrites that feature's `**Status:**` to `Done` and its `**Downstream:**` to name the DESIGN (or `_none (chain folded)_` if none survived), then checks whether *every* feature in the ROADMAP is `Done`. If not finding the feature entry at all, that is a **failure**, not a skip (`:486-493`, `:508-513`).
9. **`handle_roadmap_deletion`** (`:608-690`), called from inside `handle_roadmap` only when every feature is `Done`: idempotent no-op if the file is already gone; re-verifies all-Done; then scans for every `https://github.com/...` issue URL in the file and calls `check_issue_closed` on each. Gating conditions: (a) file missing → no-op; (b) any feature not Done → no-op, ROADMAP stays; (c) any referenced issue not `CLOSED` → `delete_roadmap: skipped`, names the open URL, ROADMAP stays; (d) all closed → `shirabe transition <roadmap> Done` (best-effort, warns but proceeds on failure) then `git rm -f` → `delete_roadmap: ok` and the path enters `STAGED_FILES`; a failed `git rm` → `ANY_FAILED=true` + `failed` step.
10. **Atomic finalization commit** (`:1010-1045`), only under `--push` and only if `STAGED_FILES` is non-empty: `git commit -q -m "chore(cascade): post-implementation artifact transitions"`, captured and guarded (not left to `set -e`), sets `COMMIT_LANDED=true` on success or `ANY_FAILED=true` + a `failed` `commit` step on failure.
11. **Push** (`:1051-1059`): attempted only if the commit landed; `git push` (no args, relies on an existing tracking branch), captured/guarded the same way, `ok`/`failed` step either way.
12. **Post-cascade lifecycle verification** (`:1093-1125`): runs only if `COMMIT_LANDED`. Picks an anchor document via `resolve_anchor` (`:340-367`) — the first of DESIGN > PRD > BRIEF > ROADMAP still on disk among everything the run staged — and re-runs the same `shirabe validate --lifecycle-chain … --mode=ready` probe in `post` mode, expecting a clean pass. If no anchor survives, records a `skipped` step (not a failure) rather than an anchor-less failure.
13. **Emit result** (`:1127-1156`): `partial` if `ANY_FAILED`; else `skipped` if `finalize-chain`'s report had exactly one node (only the PLAN, no upstream chain, `:1140-1148`); else `completed`.

### 3. The absent/partial-chain behaviour — the core question

**(a) No PLAN at all.** The script cannot even start: `PLAN_DOC` is a required positional argument (`run-cascade.sh:719-721,743-746`), and if a path is given but the file doesn't exist, that's a precondition failure — exit 1, JSON error on **stderr**, no stdout, no partial-tree side effects at all (`:774-777`). There is no mode of this script that accepts "no document at all" as input; it always needs *some* tracked PLAN file path to operate on.

**(b) A PLAN exists but has no resolvable upstream.** Two distinct sub-cases, confirmed by two different tests:
- *No `upstream:` field at all* (`scenario_missing_upstream`, test file ~714; `scenario_push_plan_only_commits_deletion`, ~2047): `finalize-chain` returns a one-node report (just the PLAN, `crates/shirabe-validate/src/finalize.rs:523-547` — `read_upstream_entries` returns an empty Vec so nothing more is discovered). The script proceeds cleanly: `git rm` the PLAN, append it to `STAGED_FILES` (nothing failed), commit + push that single deletion, skip the post-verify (`no recorded chain document survived to verify against`), and report `cascade_status: "skipped"`. The worktree ends up **clean** and the commit/push both land — this is a genuinely clean, no-noise pass-through, exactly the shape the PRD context is asking whether already exists, and it *does already exist* for this sub-case.
- *`upstream:` points at a path that doesn't resolve* (`scenario_partial_chain`, ~759): `classify_node`'s `validate_node_path` (`crates/shirabe-validate/src/finalize.rs:690-696`) fails because the file doesn't exist, `finalize-chain` exits 1 with a structured stderr error, the outer script sets `ANY_FAILED=true` and reports `cascade_status: "partial"` with one synthetic `failed` step. This is a real failure, not a clean no-op.

**(c) A PLAN has a DESIGN but no PRD or BRIEF.** Handled fine as a shorter chain: the DESIGN transitions to Current, its own (empty) `upstream:` yields no further nodes, and the chain reports `completed` (see `scenario_design_roadmap`/`scenario_plan_roadmap_no_design`, test file ~509-625, which cover a DESIGN or an even shorter PLAN→ROADMAP chain with no DESIGN at all — the "chain folded" case explicitly called out in code comments at `run-cascade.sh:546-558` and `finalize.rs`'s doc comments).

**(d) A node in the chain is at an unexpected status.** `run_transition` (the underlying transition engine) refuses the edge and returns a `TransitionError`; `finalize.rs:597-610` wraps it into a `WalkError` carrying the engine's exit code (1 tool / 2 lifecycle-violation / 3 I/O) and a message naming the node, its type, and the attempted `from -> to`. Because this happens **before** the report is ever emitted on stdout, `finalize-chain` exits non-zero and the walk cannot be reconstructed — the outer script records exactly one generic `failed` step (`run-cascade.sh:957-967`), sets `ANY_FAILED=true`, still `git rm`s the PLAN (its `git rm` succeeds and is logged `ok`, `:983-984`), but because `ANY_FAILED` is already true the append to `STAGED_FILES` is skipped (`:999-1001`). If nothing was staged earlier either, `STAGED_FILES` stays empty, so the commit block's `${#STAGED_FILES[@]} -gt 0` gate is false: **no commit runs, even though `git rm` already modified the git index and working tree.** This is exactly the "leaves a partially-staged tree" scenario — confirmed by `scenario_refused_walk_publishes_nothing` (test file ~2383), whose assertions include `git status --porcelain` being non-empty after the run and `HEAD` not moving. `cascade_status` is `partial`; exit code is still 0.

**Which case PR #353 is about**: case (b)'s clean sub-case (no-upstream PLAN). The commit message (`git log -1 7cd13d1`) states directly: "`run-cascade.sh` appended every artifact it transitioned to `STAGED_FILES` but never the PLAN it deleted, so a chain whose only action was that deletion — a PLAN with no resolvable upstream — staged the removal under `--push` and never committed it." Before PR #353, case (b)'s no-upstream sub-case left a dangling `git rm` staged forever under `--push`, never committed — this is now fixed by `run-cascade.sh:999-1001`'s conditional append. The PR also fixed a second, related bug: a ROADMAP feature not found was previously a `skipped` step (leaving `ANY_FAILED` false), which combined with the same "PLAN-only STAGED_FILES" hazard to let a never-finalized chain commit, push, and report `completed`; it is now a `failed` step (`run-cascade.sh:508-513`, `crates/shirabe-validate` comments at `finalize.rs`... actually in `run-cascade.sh:486-493`), pinned by `scenario_roadmap_feature_not_found` (test ~2519).

### 4. What "partial" means to this script

Two structurally different `partial` shapes exist, and the commit message's phrase — "a walk that stops on an unrecognized node still publishing and verifying what it reached and reporting partial" — is the **second** one, not case (d) above:

- **Refused walk (finalize-chain exits non-zero)**: nothing published. `scenario_refused_walk_publishes_nothing` (test ~2383) pins this: `HEAD` does not move, no `commit` or `push` step exists at all, `git status --porcelain` is non-empty (the refused walk's half-applied rename/deletion sits staged, uncommitted), and no `lifecycle_post_verify` step is recorded (there's nothing to verify). Recovery is `git reset --hard HEAD`, fix the offending node, re-run.
- **Per-node "error" (finalize-chain exits 0 but one node's action is `error`)**: the unrecognized-prefix node stops the walk (`finalize.rs:725-731`, `crates/shirabe-validate/src/finalize.rs`), but every node processed *before* it in the loop already ran `git add` + entered `STAGED_FILES` (`run-cascade.sh:902-920`). So when the loop hits the `error` action it just sets `ANY_FAILED=true` and adds a `failed` step (`:933-940`) — it does **not** unwind the earlier successes. `STAGED_FILES` is therefore already non-empty from those earlier nodes, so the commit/push/post-verify all fire normally, and the post-verify anchors on whatever legitimate DESIGN/PRD/BRIEF/ROADMAP survived. `scenario_push_earlier_failure_not_rescued` (test ~1919) is the pinning test: PLAN→DESIGN→(unrecognized "NOTE-" node) commits and pushes the DESIGN transition, `lifecycle_post_verify` reports `ok`, and yet `cascade_status` stays `partial` — the comment there explicitly warns against "the tempting 'clear the false failure this fix is about' edit."

What a caller sees for this second shape: `cascade_status: "partial"`, a `commit: ok` step, a `push: ok` step, a `lifecycle_post_verify: ok` step, and one `failed` step naming the unrecognized node. `execute.md:715` and `:740` describe recovery for exactly this shape: "the walk stopped partway and published what it had reached. The remote already carries that commit, so recovery is a follow-up commit or a revert, not a reset." `execute.md`'s `plan_completion` state (`:715`) still halts and does not run `gh pr ready` on any `partial`, regardless of shape.

### 5. Staging discipline

`STAGED_FILES` (`run-cascade.sh:77-80`) is a bash array recording every path the cascade `git add`ed or `git rm`ed, used for three purposes: (1) gating whether the commit block runs at all (`${#STAGED_FILES[@]} -gt 0`, `:1010,1061`), (2) feeding `resolve_anchor` for the post-verify seed (`:340-367`), and (3) nothing else — it is explicitly *not* "files that will exist after the commit" (comment at `:78-80`), since it also holds deleted paths (PLAN, a deleted ROADMAP).

The PLAN's own `git rm` is the one append site that is conditionally gated: `if [[ "$ANY_FAILED" == "false" ]]; then STAGED_FILES+=("$PLAN_DOC"); fi` (`:999-1001`). Every other append site (`transition_design`/`_prd`/`_brief` at `:904,911,917`, `handle_roadmap`'s feature edit at `:604`, `handle_roadmap_deletion`'s ROADMAP delete at `:684`) is unconditional, because those sites only run at all when the corresponding node/step itself already succeeded — the load-bearing exception is specifically the PLAN, whose `git rm` always runs (step 7 in section 2) regardless of whether an earlier node failed. Without the `ANY_FAILED` guard, a refused-walk run (case (d) above, or the per-node "error" shape) would let the bare PLAN deletion alone open the commit gate and publish a half-walked chain (git log message for #353, and `scenario_refused_walk_publishes_nothing`'s "killing assertion").

Invariant a **new caller** (a single-issue run) must respect to use this script safely:
- It must supply a real, git-tracked, existing document path as the positional argument — the script has no "no document" mode; the caller decides what document represents "done" for that unit of work.
2. The document's on-disk lifecycle status must currently make the **pre-cascade probe fail** in `--mode=ready` (i.e. the chain must look "mid-PR, not yet terminal") — if it's already at rest, the script is a clean no-op (`cascade_status: skipped`) with zero transitions.
3. The caller must be on a branch with, if `--push` is used, an already-configured upstream remote tracking branch — the script does a bare `git push`.
4. The caller must not treat `commit`/`push` step absence as proof nothing was published (execute.md:733 warns of exactly this): a refused-walk `partial` publishes nothing, but a mid-walk-error `partial` can publish and push a partial chain, both under the same `cascade_status`.
5. `STAGED_FILES`'s conditional gate assumes the PLAN's `git rm` is the *only* site that can run unconditionally after a failure; a new caller adding another unconditional delete/rewrite after a failure point would need the same `ANY_FAILED` guard or it reintroduces the #353 bug for its own artifact type.

### 6. Coupling to `/execute`

The script itself (`run-cascade.sh`) is fairly caller-agnostic in its bash — it takes a bare file path, not a plan-object, PR number, or session ID — but several things a plan-level caller like `/execute` gets "for free" would have to be independently supplied by a single-issue caller:
- **A PLAN-shaped input document.** `finalize-chain`'s debug assertion (`crates/shirabe-validate/src/finalize.rs:495-499`) checks the input resolves to the `Plan` format (only enforced in debug builds — release is silent but relies on the caller passing a real PLAN), and the whole chain-walk contract (`delete_plan` first node, ephemeral Active→Done flip, etc.) assumes the seed is a PLAN document specifically, not a bare issue.
- **PLAN filename convention.** `PLAN_SLUG=$(basename "$PLAN_DOC" .md | sed 's/^PLAN-//')` (`:818`) assumes the filename is literally `PLAN-<slug>.md`; this slug is only used to search a ROADMAP's `Downstream:` field, so it silently does nothing useful if the naming convention isn't followed, rather than erroring.
- **A shared branch with a draft PR already open.** The script has no knowledge of GitHub PRs at all (aside from `check_issue_closed`'s `gh issue view` for ROADMAP issue closure) — `execute.md`'s `plan_completion` state (`execute.md:700-757`) is what sequences "cascade BEFORE `gh pr ready`" and defines the DRAFT-vs-READY ordering (#117); a single-issue caller must independently decide when in its own PR lifecycle to invoke the cascade and whether/when to flip the PR ready, since the script does not do that.
- **An orchestrator that halts on `partial`.** The script's own contract is silent about what the caller should do next; `execute.md:713-741` supplies all of the case-by-case recovery guidance (failed commit vs. failed push vs. refused-with-no-commit vs. refused-with-commit vs. failed post-verify). A single-issue caller reusing this script needs to reimplement or share that same decision table, or a `partial` verdict will be mishandled (e.g., marking something "ready" that shouldn't be).
- **Working tree cleanliness / no other agent activity.** The script assumes it's the only actor touching the tree during its run (it does `git add`/`git rm`/`git commit`/`git push` without any pre-check that the tree was clean beforehand) — a single-issue caller invoking this mid-implementation, with other uncommitted changes present, would have those changes swept into the same commit, since `git commit` with no pathspec commits the whole index, not just `STAGED_FILES`'s bash-tracked entries. (This is implicit in the code, not stated as an assumption anywhere, but it's real: line 1039's `git commit -q -m …` has no `--` pathspec limiting it to the array's contents.)

### 7. Its tests

`skills/execute/scripts/run-cascade_test.sh` is 2749 lines (not 661) and defines 33 scenarios (grep for `^scenario_`), run against a real built `shirabe` binary (`build_shirabe_binary`) over temp git repos with a bare `origin`. Coverage relevant to this lead:

- **Case (b), no-upstream sub-case**: `scenario_missing_upstream` (dry-run, asserts `cascade_status: skipped`) and `scenario_push_plan_only_commits_deletion` (Scenario 24, `--push`: asserts the worktree ends clean, `HEAD` advances with a commit that deletes only the PLAN, the push reaches origin, `cascade_status` stays `skipped`, exactly one `commit ok` and `push ok` step, and `lifecycle_post_verify` is present but `skipped` with a null target) — this is the scenario PR #353 fixed and is now fully pinned.
- **Case (b), unresolvable-path sub-case**: `scenario_partial_chain` (Scenario 5) — PLAN's upstream names a nonexistent DESIGN, asserts `cascade_status: partial` with ≥1 failed step carrying a detail message.
- **Case (c)** (short/folded chains): `scenario_plan_roadmap_no_design` (PLAN→ROADMAP, no DESIGN at all — asserts `completed`, no `transition_design` step, and that the ROADMAP's `Downstream:` field is rewritten to not dangle) and `scenario_design_roadmap`/`scenario_design_prd_roadmap`/`scenario_brief_no_upstream` for other short-chain shapes.
- **Case (d) / refused-node partial, "nothing published" shape**: `scenario_refused_walk_publishes_nothing` (Scenario 27) — pins exit 0, `cascade_status: partial`, exactly one failed `transition_design` step whose detail matches `"finalize-chain exited"` (explicitly distinguished from the other error shape "so the fixture doesn't drift"), `HEAD` unmoved, no `commit`/`push`/`lifecycle_post_verify` steps, remote unchanged, PLAN still present in HEAD (so `git reset --hard HEAD` is a valid recovery), and `git status --porcelain` non-empty (the half-applied work is left staged).
- **"Partial but published" shape** (the PR #353-highlighted case): `scenario_push_earlier_failure_not_rescued` (Scenario 22) — PLAN→DESIGN→unrecognized-prefix node; asserts `cascade_status` stays `partial` even though `lifecycle_post_verify` itself reports `ok`, specifically warning against "clearing ANY_FAILED on a passing post-verify."
- **ROADMAP-not-found-as-failure**: `scenario_roadmap_feature_not_found` (Scenario 28) — asserts `partial` (not `completed`), a `failed` `update_roadmap_feature` step, no commit/push, and — the "killing assertion #2" — that the *published* tree (via `git archive HEAD`) still fails `shirabe validate --lifecycle . --mode=ready`, i.e., a chain that never finalized cannot silently merge green.
- **No scenario directly exercises case (a)** (invoking the script with zero PLAN path / no PLAN file existing at the given path beyond the basic "not found" precondition) as a "single-issue, no document at all" scenario — there is no test modeling a bare-issue caller with nothing to hand the script, because today nothing calls it that way.

## Implications

The PRD's stated requirement — "an ordinary issue run with no document chain must pass through cleanly rather than failing or emitting noise" — is **already true** for one specific shape: a PLAN document that exists but has no upstream chain (case b's no-upstream sub-case), and that shape is now well-tested and was the exact subject of PR #353. It is **not true at all**, and not close to true, for a genuinely document-less single-issue run: the script has a hard requirement for a tracked, existing document path as its sole positional argument, with no flag or mode to say "there is no document, just no-op." Making the cascade reachable from `/work-on` for an issue with zero documents behind it therefore requires either (a) synthesizing/pointing at some document (which doesn't exist for a bare issue and would be invented purely to satisfy this script), or (b) adding an actual "no anchor document" early-exit path to the script/caller contract before it ever reaches `finalize-chain`. That is genuinely new work, not a documentation gap.

Separately, any new caller reusing this script inherits its "commits the whole index" and "no tree cleanliness precheck" behavior, and its coupling to PLAN-shaped inputs and PLAN filename conventions (the `PLAN-` prefix strip for slug lookup). A single-issue caller with a lighter-weight upstream (e.g. a DESIGN or PRD directly, no PLAN) is not something `finalize-chain`/`run-cascade.sh` currently accepts as the seed — the seed's format is asserted to be `Plan` (debug-only) and its "delete" semantics (Active→Done→`git rm`) are PLAN-specific by design.

## Surprises

- The `--push` gate fix in PR #353 was narrowly about the PLAN's own `git rm` never entering `STAGED_FILES`; the "no document chain" no-op behavior it produces (clean commit-and-push of just the PLAN deletion, `cascade_status: skipped`) was a side effect of getting the staging discipline right, not a designed "onboarding ramp" for callers with no documents.
- `partial` is not one failure mode but (at least) two observably different ones with opposite recovery stories — "nothing published, reset the tree" vs. "partially published, follow up or revert" — and the script's JSON gives no top-level flag distinguishing them; the caller has to infer it from whether `commit`/`push` steps are present, which `execute.md:733` calls out explicitly as an easy trap ("Checking for a failed commit or push step is NOT sufficient either").
- The pre-cascade probe's "no-op" detection (`cascade_status: skipped` from a clean `--mode=ready` pass) is a *different* skipped-shape than the "one-node report" skipped detection (`CASCADE_SKIPPED`, `run-cascade.sh:1142-1148`) — both produce the same string in the JSON, but one exits before touching `finalize-chain` at all and the other runs the full commit/push pipeline for just the PLAN deletion.

## Open Questions

- Should a single-issue `/work-on` cascade invocation synthesize a throwaway PLAN-like document just to satisfy this script's input contract, or should the script gain a real "no anchor document, no-op" mode that doesn't require any file at all? The current code offers no precedent for the latter.
- If a single-issue caller does have *some* document (e.g., a DESIGN with no PLAN wrapper), does it make more sense to seed `finalize-chain`/`run-cascade.sh` on that document directly (relaxing the `Plan`-format assumption), or to always synthesize a minimal PLAN?
- Does the "commits the whole index, not just STAGED_FILES-tracked paths" behavior (section 6) pose a real risk for a single-issue run where other uncommitted work might coexist in the tree at cascade time, and if so, does that need hardening as part of this feature?

## Summary
`run-cascade.sh` requires a real, git-tracked PLAN-shaped document path as its only positional argument — there is no mode that accepts "no document at all," so today a genuinely document-less single-issue run cannot invoke it at all, only fail its precondition checks. For a PLAN that exists but has no upstream chain, the script already behaves exactly as the PRD wants — clean commit-and-push of just the PLAN deletion, reported as `cascade_status: skipped`, with no noise — and that is precisely the case PR #353 fixed (previously the deletion sat staged forever under `--push`), pinned by `scenario_push_plan_only_commits_deletion`. Making the cascade reachable from a truly document-less single-issue run is therefore genuinely new work, not something already covered: it needs either a synthesized anchor document or a new early-exit path in the script/caller contract, plus care around the two distinct `partial` shapes (nothing published vs. partially published-and-pushed) that a new caller must handle identically to `/execute`'s existing decision table.
