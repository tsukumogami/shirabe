# Testability Review: PRD-work-on-standalone-completeness

## Verdict

FAIL

## Requirement coverage map

R1→AC2, R2→AC1, R3→AC1, R4→AC3, R5→AC4, R6→AC5, R7→AC5, R8→AC5, R9→AC7, R10→AC6, R11→AC8, R12→AC9, R13→AC8, R14→AC10, R15→AC11, R16→AC12, R17→AC13, R18→AC14, R19→AC15, R20→AC16, R22→AC17.

**R21 is uncovered.** No acceptance criterion cites R21 ("Template authoring SHALL follow the repository's existing rules for gates and default actions, including the constraints its own linter imposes"), and no AC bullet's prose covers it either — confirmed by grepping every `R\d+` reference in the Acceptance Criteria section. This is not a hard requirement to check: `scripts/validate-template-mermaid.sh` already exists and already runs in CI (`.github/workflows/validate-templates.yml`) against exactly the two templates this feature edits (`work-on.md`, `execute.md`). The PRD names the exact mechanism ("the constraints its own linter imposes") but never turns it into a checkbox, so a reviewer using only the Acceptance Criteria section as the completion contract has no prompt to run it.

## Required changes

1. Add an acceptance criterion for R21: run `scripts/validate-template-mermaid.sh` (or whatever the repository's template linter is called) against both edited templates and require a clean pass. This is cheap to add and closes a fully-testable requirement that currently has no criterion at all.
2. Strengthen the R6/R7/R8 criterion (AC5) to check evidence-field *substance*, not just presence: require that an evidence-carried obligation's field can be shown empty/placeholder-resistant (e.g., a minimum-content check, or a companion gate that flags an evidence value matching a known-hollow pattern), or explicitly acknowledge in Known Limitations that evidence-field honesty is untested by design — the PRD already gestures at this limitation in prose but the AC doesn't reflect it, so as written the AC promises more than the mechanism (bare `required: true`) delivers.
3. Give R16's AC a reproducible query, or explicitly delegate the boundary-drawing to a named artifact: e.g. "the enumerated surface list in [doc X] is the authoritative set; grep for the routing phrase and confirm every hit in that list is fixed and no new hit outside it is a routing claim" would let two reviewers converge. As written, "a repository-wide search... returns none" cannot be run by two different testers and be expected to agree, because "routing claim" (~30 lines) and "the string multi-pr" (~890 lines) are different searches and the PRD doesn't say which one the AC means.
4. For R19's AC, either name the retention mechanism this feature is expected to use (so a tester has something concrete to check for on the new states regardless of the sibling defect's status), or state explicitly how a tester should proceed if the sibling defect has not yet landed when this feature's states are added.
5. Tighten AC1/AC3's "no cascade-related text" language with a concrete negative check (e.g., specific phrases that would constitute a leak, or a rule that the no-anchor path must not reference the cascade script, term, or file by name) so it stops being a pure judgment call between reviewers.

## Observations

The criteria that map onto mechanically observable facts (git/gh state, eval-harness pass/fail, `shirabe validate` output, enum diffs, file-existence/hop-counting) are uniformly strong — this PRD clearly did the work of grounding most of its acceptance criteria in checkable artifacts rather than vibes, and R4, R14, R17, R18, R20 in particular would be hard for a wrong implementation to sneak past. The weak spots cluster exactly where the underlying requirement itself said "this is a judgment call" (R7's evidence honesty, acknowledged in Known Limitations) or where the PRD's own supporting research shows the boundary is genuinely fuzzy (R16's routing-claim classification, which needed manual triage of ~860 false-positive-adjacent hits during drafting) — the PRD is honest about both gaps in prose but doesn't carry that honesty into the acceptance criteria that are supposed to be the actual completion contract.
