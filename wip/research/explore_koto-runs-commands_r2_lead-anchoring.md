# Lead: How should koto anchor command execution to a directory, so an action can never run against the wrong tree?

## Findings

### Where the cwd comes from today

`handle_next` (`src/cli/mod.rs:2892`, the `#[cfg(unix)]` implementation) captures `let current_dir = std::env::current_dir()?;` at `src/cli/mod.rs:3082`, immediately after the workflow-exists check and before the state file is read. That one value feeds every execution site in the tick:

- `gate_closure` (`src/cli/mod.rs:3822-3838`) passes `&current_dir` straight into `evaluate_gates`, which `src/gate.rs:206-208` forwards unchanged as `working_dir` to `run_shell_command` for every `type: command` gate.
- `action_closure` (`src/cli/mod.rs:3894` onward) computes `wd` at `src/cli/mod.rs:3979-3983`: `current_dir.clone()` when `action.working_dir` is empty, otherwise `PathBuf::from(variables.substitute(&action.working_dir))` — a bare substitution with no `current_dir.join(..)`, so a relative `working_dir` is only anchored to the real tree because `Command::current_dir` (inside `run_shell_command`, `src/action.rs:36`) resolves a relative path against the *process's actual cwd*, which happens to equal `current_dir` at this point. There is no explicit join or canonicalization step anywhere in this path.
- `execute_with_polling` (`src/cli/mod.rs:995-1041`) takes `working_dir: &Path` as a parameter and threads it into `run_shell_command` on every poll iteration and into its own nested `evaluate_gates` call (`src/cli/mod.rs:4012`) — same `current_dir`, captured once per tick, reused for the whole polling loop.

`src/action.rs` (the file the round-1 brief pointed at) is not a closure-builder; it is the shared `run_shell_command` primitive (process-group isolation, timeout, output capture) called from both `gate.rs` and `cli/mod.rs`. It takes `working_dir: &Path` as a plain argument and does zero validation on it — no canonicalize, no containment check, no existence check beyond letting `Command::spawn` fail.

There is exactly one call site for `run_shell_command` in the action path (`src/cli/mod.rs:1022` inside polling, `src/cli/mod.rs:4021` for one-shot) and one for gates (`src/gate.rs:207`). A guard placed once, at the top of `handle_next` before `current_dir` is used to build either closure, covers every command-execution surface in the binary — there is no second code path that spawns shell commands.

### What a session already knows about its origin — and why none of it is usable

I read `WorkflowInitialized`'s payload (`src/engine/types.rs:455-468`): `template_path: String`, `variables: HashMap<String, String>`, `spawn_entry: Option<SpawnEntrySnapshot>`. No cwd, no root, no git info of any kind is recorded on the event itself.

`template_source_dir` lives on `StateFileHeader` (`src/engine/types.rs:245-260`), not on the event, and — this refines round 1's finding — it is **not** the invocation cwd at all. It is the *template file's own parent directory*, computed in `init_child_from_parent` (`src/cli/init_child.rs:456-467`): for an absolute `--template` path it's `template_path.parent()`; for a relative path it's `canonicalize(template_path).parent()`. For a shirabe workflow this resolves to something like `.../shirabe/skills/execute/koto-templates/`, not the repo root or worktree the workflow is supposed to act on. `path_resolution.rs`'s entire module docstring (`src/engine/path_resolution.rs:1-21`) confirms the field's one consumer: resolving *relative child-template paths* for the batch scheduler, falling back to `submitter_cwd` from the most recent `EvidenceSubmitted` event (`src/cli/mod.rs:3819`, recorded only for that resolver, best-effort, `Option`). Neither field is read anywhere in the gate/action execution path. `check_template_source_dir` (`src/engine/template_source_status.rs:94`) only powers `koto status`'s staleness note and the `koto init` collision message — pure diagnostics.

Net: **zero bytes of session state today record "the directory this workflow's commands should run in."** `koto init` doesn't even capture its own invocation cwd anywhere durable — `current_dir` in `handle_next` is recomputed fresh, from the live process, on every single tick, with nothing to check it against.

Two files on the original reading list turned out to be tangential and I want to flag that rather than pad the analysis: `src/cli/workspace.rs` is `koto workspace prune`, an operator reclaim verb unrelated to execution; `src/engine/discovery.rs` is the request-store coordinator scan (`koto_root`-relative file walking for dispatch discovery), also unrelated to per-tick command anchoring. `src/discover.rs` is workflow-name validation (`validate_workflow_name`, `src/discover.rs` — the character allowlist that blocks path traversal in the *session name*, not in `working_dir`).

### The worktree complication — real, but not where the brief framed it

I read `phase-2.5-worktree-discipline.md` and `execute.md`'s `worktree_discipline_check` state closely, then went looking for where shirabe actually calls `git worktree add` or `niwa worktree create` inside a running koto session. It doesn't, in either `/work-on` or `/execute`'s single-pr path:

- The `worktree_discipline_check` state's gate is `test -f wip/work-on_{{PLAN_SLUG}}_impact.json` (`execute.md:110`) — a relative-path check against whatever the cwd is at gate-eval time. Its steps are `git fetch origin` + `git rebase origin/main` (`phase-2.5-worktree-discipline.md:26-29`) run **in place**. Despite the name, this phase is about detecting upstream `main` drift on a shared branch, not about relocating the process to a different git-worktree directory. I grepped both skills for `git worktree add` and `niwa worktree` — zero hits inside `skills/work-on/` and `skills/execute/`.
- `/work-on`'s Phase 1 setup (`skills/work-on/references/phases/phase-1-setup.md:16-26`) creates a branch with `git checkout -b` in the current tree, or reuses `SHARED_BRANCH` / the current branch — never a separate worktree directory.
- The one real worktree in this flow is in `/execute`'s **coordinated** multi-repo path (`skills/execute/SKILL.md:297-299`): "Each repo that needs changes is worked in its own worktree on that repo's own branch." But that path is explicitly *not* koto-driven — `/execute`'s coordinated mode is "a plain durable-state loop over the coordination PR's merge-order DAG" (SKILL.md:23-24), not the lifted `execute.md` template. Each per-repo unit dispatches its own separate `/work-on` invocation, which — if it runs `koto init` — does so from inside that repo's own worktree and stays there for that session's whole lifetime. `niwa`'s worktree model (`public/niwa/docs/guides/worktree.md:11-20`) creates worktrees as their own directories with `niwa worktree create`, entered once, not something a mid-flight koto tick jumps into.

So: within a single koto session's lifetime, shirabe's own templates never move the process between directories. The premise "shirabe's own workflows create and move between git worktrees mid-run" doesn't hold for the code as it exists — I want to be direct about correcting that rather than building the design around a scenario I couldn't find. What I *did* confirm, and what actually matters for anchoring, is the general hazard round 1 already proved empirically: **`koto next` trusts whatever the live process cwd happens to be, on every tick, with no memory of where the last tick ran.** That is a strictly bigger, harder-to-avoid hazard than "moves between worktrees" — it fires any time a fresh agent turn, a different shell, a background job, or a coordinator resumes the same session name from a different directory (exactly the `tmp/kototest` vs `tmp/elsewhere` proof from round 1), and it fires whether or not worktrees are involved at all.

The one place a *legitimate* cross-directory need does exist: `niwa worktree create` or `EnterWorktree`-style isolation happening at the **outer harness level**, between an agent's own turns, independent of anything koto's templates ask for — e.g. an operator decides mid-run that the rest of the work should happen in a freshly created worktree, and the agent's shell cwd changes as a side effect of a tool outside koto's control. Any anchoring design has to have an explicit, deliberate way to say "yes, this session now lives here" for that case, without silently trusting cwd drift the rest of the time.

### The two round-1 safety findings, re-examined in this context

**(a) `working_dir` unescaped vs. `command` shell-escaped (#186).** Confirmed at `src/cli/mod.rs:3975-3983`: the comment explicitly says command uses the shell-safe substitution because it "goes to `sh -c`," while `working_dir` "is a path, not a shell word, so it keeps the plain substitution." That reasoning is correct as far as shell-metacharacter injection goes — `working_dir` never reaches `sh -c`, it's passed as a `Path` to `Command::current_dir`, so `;`, `$()`, backticks etc. in a substituted value don't get shell-interpreted there. The actual exploitable consequence of "unescaped" is path traversal (`..`) and absolute-path override, both of which are really *containment* bugs, not *escaping* bugs — and they're exactly what round 1 already demonstrated concretely (`working_dir: ".."` escaping upward). A containment check closes the exploitable part regardless of whether the substitution helper changes; I'd still align the substitution helper for consistency, but it's not the load-bearing fix.

**(b) non-existent `working_dir` → `exit_code: -1`, invisible to the agent.** Confirmed at `src/action.rs:49-58`: `Command::spawn` failure returns `CommandOutput { exit_code: -1, stdout: "", stderr: "failed to spawn command: {e}" }`. This is the same struct shape as a timeout, so from the agent's perspective a bad `working_dir` and a slow command look identical unless it goes digging in the event log's recorded stderr. This is a real, separate observability gap — but I'd note it becomes *less* likely to matter once containment is enforced upstream, because a containment violation should be caught and reported as a structured `NextError` before `run_shell_command` is ever called, rather than being allowed through to spawn and fail generically. The spawn-failure-visibility fix is still worth doing independently (any other cause of ENOENT, permission denied, etc. still hits this same silent path), just not a substitute for the containment check.

## Implications

- The fix has to live in exactly one place for it to be trustworthy: the top of `handle_next` (`src/cli/mod.rs`, `#[cfg(unix)]` variant, near line 3082), before `current_dir` is captured and before either closure is built. Because both gate and action execution funnel through this single function, a guard here is structurally complete — there's no second entry point to forget.
- `template_source_dir` cannot be repurposed as the anchor. It means something else (the template's own directory) and is already load-bearing for the batch child-path resolver; overloading it would break that resolver's semantics or require disentangling two different concepts that happen to share a field today. The anchor needs a new, dedicated header field.
- Because no session-level anchor exists anywhere in the on-disk format today, this is a genuinely additive design, not a repurposing one — old state files have no anchor and need a defined migration behavior (see options below).
- The worktree case, once correctly scoped, is not a "mid-run relocation" problem for koto to solve inside a single tick — it's an "explicit, audited rebind" problem for the rare case an operator or coordinator deliberately changes where a session's work happens between ticks. That argues for a real verb, not silent tolerance.

## Surprises

- `template_source_dir` is not "the directory the workflow was launched from" — it's the *template file's* directory, e.g. inside the shirabe plugin's `koto-templates/` folder, which is nowhere near the repo tree the workflow is supposed to act on. Round 1 characterized it as "used only for batch child-template lookup," which is directionally right, but I want to be explicit that it would be actively wrong to lean on it for anchoring even opportunistically — it points at the wrong directory entirely, not just an under-used one.
- `koto init` itself never records its own invocation cwd anywhere. Even setting aside the batch/child nuance, top-level `koto init` (the common case for `/work-on` and `/execute`) leaves `template_source_dir: None` unless the template path happens to be file-path-resolvable in a particular way — so today there is no field on a freshly initialized top-level session that says where it lives, full stop.
- The "worktree discipline" framing in shirabe's own docs is a red herring for literal git-worktree relocation — I went in expecting to find `git worktree add` calls inside the koto templates and found none. The design risk it protects against (upstream `main` drift under a long-running shared branch) is real and unrelated to directory anchoring.

## Open Questions

- Should the anchor default silently to `koto init`'s cwd, or should `koto init` require an explicit `--anchor` the way `--template` is explicit? Silent default matches every other implicit-cwd convention in the codebase and is what round 1's proof-of-concept assumed was already happening; requiring it explicitly is more honest about the hazard but adds friction to every `koto init` call site in shirabe (`work-on.md`, `execute.md`) that would need updating.
- For state files predating this field (`execution_root: None`), does `koto next` refuse to run any action/gate until an operator runs the bind verb once, or does it fall back to "trust cwd, warn once" to avoid breaking every session in flight the day this ships? I lean toward the former for safety but it's a real backward-compatibility call, not a technical one.
- Should the containment check be root-equality (cwd must canonicalize to exactly `execution_root`) or root-containment (cwd must canonicalize to `execution_root` or a descendant of it)? Equality is the safer default and matches every proven round-1 scenario; containment would tolerate an agent that `cd`s into a subdirectory of the intended tree without an explicit rebind, which is a real, benign thing agents do (e.g. `cd recipes/` to run a scoped command) but which round 1 never actually tested as unsafe or safe.

## Summary

Nothing in koto's on-disk state today records where a workflow's commands are supposed to run — `template_source_dir` is the template file's own directory, not the working tree, and `koto next` simply recomputes `std::env::current_dir()` fresh on every tick, feeding it unchecked into both the gate and action closures at a single choke point (`handle_next`, `src/cli/mod.rs:3082` onward) that also builds the `working_dir` used by `run_shell_command`. Shirabe's own koto templates never actually relocate a running session between git worktrees mid-run — despite the `worktree_discipline_check` name, that phase does an in-place `git fetch`/`rebase`, not a directory move — so the anchoring design doesn't need to tolerate silent cwd drift as a normal event, only guard against it as a hazard and provide one deliberate, audited way to rebind when an operator genuinely does relocate the tree. I recommend recording a canonicalized `execution_root` on the state file header at `koto init` (defaulting to invocation cwd), refusing to run any gate or action at `handle_next` when the live cwd doesn't canonicalize to exactly that root, resolving `working_dir` by joining and canonicalizing under the root rather than trusting raw substitution (closing both the `..`-escape and the #186 asymmetry as one fix), and adding an explicit `koto session bind` verb that appends an auditable event for the legitimate re-anchor case — with spawn/containment failures surfaced as structured, agent-visible `NextError`s rather than silent `exit_code: -1` stderr strings buried in the event log.
