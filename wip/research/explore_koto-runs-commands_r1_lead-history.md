# Lead: Why does shirabe not use `default_action` in its koto templates — was this considered, deferred, or overlooked?

## Findings

**The capability was designed and shipped in koto, on schedule, for exactly this purpose.** koto issue #71 ("implement default action execution for deterministic states", closed) specifies koto running commands itself for five states — `context_injection`, `setup_issue_backed`, `setup_free_form`, `staleness_check` (one-shot), and `ci_monitor` (polling) — as "the mechanism that makes the automation-first principle concrete." Its parent design, `docs/designs/current/DESIGN-shirabe-work-on-template.md` in koto, frames this as Phase 0b of a plan whose entire point was eliminating ~42% of skill instruction lines (420 of 995) by having koto execute deterministic work instead of an agent. koto#75 (`feat(engine): add template variable substitution and default action execution`) merged 2026-03-23 and closed #71. The milestone "shirabe work-on koto template" shows all 11 issues (#65-#77) closed, 0 open — nothing here was left undone on koto's side.

**The template that was supposed to use it never did, from its very first commit.** koto issue #72 ("write the work-on koto template") was closed not by implementation but as superseded: "the work-on koto template now lives in the shirabe plugin ... not in the koto repo. Closing." The actual template was authored directly in shirabe, PR #20 (commit `711d385`, merged 2026-03-26, "feat(work-on): integrate koto orchestration with template and eval infrastructure", closing shirabe#18). I pulled that very first commit of `skills/work-on/koto-templates/work-on.md` (557 lines) with `git show 711d385:skills/work-on/koto-templates/work-on.md` and grepped it: zero occurrences of `default_action`. This is not a case of the field being added and later stripped — it was never present, even at initial authoring, despite the design it claims to implement being entirely about that field.

**shirabe#18's own description is inaccurate about provenance.** It says the template "was built and validated in koto's plugins directory" before migration. `git log --all --diff-filter=A -- "*work-on*"` in the koto repo returns nothing — no `work-on.md` template file has ever existed in koto's git history at any point. The template was authored fresh in shirabe from the start; the "migration" framing in the issue doesn't match what git shows.

**The current template uses gates + agent prose exactly where the design specified default_action.** I checked the three one-shot states by name:
- `context_injection` (skills/work-on/koto-templates/work-on.md): "Read `references/phases/phase-0-context-injection.md` for detailed steps. If the gate fails (artifact missing), submit `status: completed` after creating the artifact..." — agent does the work, gate only verifies.
- `setup_issue_backed`: "Read `references/phases/phase-1-setup.md` for branch naming and baseline format. If the gate fails, submit `status: completed` after creating the branch and baseline..." — same pattern.
- `staleness_check`: the gate itself runs `check-staleness.sh --issue {{ISSUE_NUMBER}} | jq -e '.introspection_recommended == false'` — but this is a verification gate, not an execution action; if it fails, the agent is told to submit a `staleness_signal` evidence value, not to see captured stdout/stderr from a default_action per the koto#71 design.

None of the five states koto#71 named have an `ActionDecl`/`default_action` block. All five are either agent-prose-driven with a checking gate, or (staleness_check/ci_monitor) run their shell command directly inside the gate's own command rather than via a separate action-then-gate flow.

**No documented rejection anywhere.** I searched:
- shirabe issues for "koto" (50 results) — none about default_action being tried and rejected. Two relevant open issues instead point at gate-only design assumptions: shirabe#80 ("staleness_check gate portability in shirabe" — the gate directly shells out to a script that doesn't ship with shirabe) and shirabe#245 (`ci_monitor` has no merge-state gate).
- shirabe#51 ("chore(koto): file koto feature requests") lists koto feature requests filed for the ongoing Koto Adoption effort (#65, #66, #87, #104, #105, #106, #107, #108) — none re-request or reference default_action; the ask list moved on to other primitives entirely.
- `git log --all -S "default_action"` in shirabe returns exactly two commits, both this exploration's own docs artifacts (`docs(explore): capture scope for koto-runs-commands`, `docs(explore): capture round 1 findings for scope-koto-adoption`) plus one unrelated hit: shirabe PR #278 (`fix(execute): unblock the single-pr path on macOS`, merged 2026-08-15), which added `scripts/check-template-interpolation.sh`. That script's own comment explicitly scopes itself to "gate `command:` values and `default_action` command values" — i.e., someone building unrelated interpolation-safety tooling in August 2026 wrote future-proofing for a `default_action` field that, per every template file, has never actually been populated. This is defensive breadth, not evidence of use.
- The two newer koto/shirabe unification designs that touch work-on's koto integration post-date the original design and never mention `default_action`, `action execution`, or koto running commands at all: `DESIGN-work-on-koto-unification.md` (koto v0.8.0 batch spawning) and `DESIGN-work-on-efficiency.md` (complexity-based routing). Both are framed entirely around gates, evidence schemas, and koto's scheduler. The topic simply doesn't recur.

**koto's own tests do exercise `default_action`** — the engine code and its design doc describe unit/integration tests for one-shot execution, polling, override prevention, and confirmation-required actions (per koto#71's Validation section and the design's Decision 1-3 architecture). This is a capability that works and is tested inside koto; it's just never consumed downstream.

## Implications

This is a straightforward implementation gap, not a rejected idea. The design was written, the engine capability was built and merged on the schedule the plan called for, and then the template — authored by the same person (dangazineu) days later — simply didn't use it. The PR #20 description confirms the mental model that shipped: "Gates auto-advance past completed work on resume... The skill tells agents what koto commands to run rather than encoding the state machine in prose" — this is a materially weaker automation model than the design's default_action mechanism (agent still runs the mechanical commands; koto only verifies afterward), but it was written up as if it fulfilled the design's automation-first goal. No one has since revisited it — the koto feature-request tracking issue (shirabe#51) and both later unification/efficiency designs moved on to other capabilities without circling back.

## Surprises

- shirabe#18's claim that the template was "developed and tested" in the koto repo before migration doesn't match git history — no such file ever existed there. Minor but worth flagging since it's currently the documented provenance story.
- The August 2026 interpolation-safety script (shirabe#278) treats `default_action` as a real, current concern worth defending against injection bugs, seven-plus months after the template that would use it shipped without it — suggesting at least one engineer's mental model still includes default_action as active/expected, even though no template uses it.

## Open Questions

- Was there a conversation (Slack, PR review comment, etc.) outside git/GitHub where default_action was consciously dropped for scope/time reasons during PR #20? Not visible from any artifact I can access.
- Does shirabe's current gate-then-prose pattern actually violate any explicit constraint (e.g., reversibility) that would have blocked default_action for `setup_issue_backed` (branch creation — plausibly irreversible-ish) or was it simply never attempted for any of the five states, including the reversible ones like `context_injection`?

## Summary
koto shipped `default_action` on schedule (issue #71, PR koto#75, merged 2026-03-23) as the core mechanism of a design explicitly aimed at eliminating ~42% of skill-instruction lines, but shirabe's work-on template — authored days later in the same PR chain by the same author — never used it, not even in its first commit; no design, issue, or PR in either repo records a decision to skip it, and later koto-unification designs stopped mentioning it entirely. This reads as an overlooked/dropped implementation step rather than a documented rejection, though a script added in August 2026 (shirabe#278) still treats `default_action` as a concept worth defending in tooling, suggesting the gap wasn't fully forgotten, just never closed.
