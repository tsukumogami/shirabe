# Lead: Should koto-executed commands be restricted to read-only ones, and can a user's permission layer stay in the loop for the rest?

> **AUTHOR RULING (2026-08-20, post-exploration): the permission leg of this
> lead's recommendation is OVERTURNED.** Finding 1 below confirms that
> `default_action` runs outside the agent's tool layer, and the recommendation
> rests partly on that being a reason to keep remote mutations agent-run. The
> author has ruled that the bypass is the intended design: loading a skill that
> drives koto is the broad grant, and consent belongs at the decision to invoke
> the workflow rather than at each command. The recommended principle is
> therefore amended — koto runs a step when it is isolated to its own state and
> gate-verifiable independent of the action's own exit code; reversible
> repo-local steps convert now; irreversible outward-facing steps convert once
> failure output reaches the agent, deferred on diagnosability and
> irreversibility rather than on authorization. The granularity finding
> (finding 3), the var-plumbing finding (finding 4), and the read-only analysis
> all stand. Treat the yields cited here as floors. See
> `wip/explore_koto-runs-commands_findings.md`, section "Author Ruling".

## Findings

**1. The permission-bypass claim is accurate at the code level, and no preview/approval mechanism exists to fix it.**

`koto/src/action.rs` (`run_shell_command`, shared by gates and `default_action`) spawns `Command::new("sh").arg("-c").arg(command)` directly as a child of the koto binary process, in its own process group. This runs whether the caller is a gate check or a `default_action`; it is never routed through the agent's own Bash tool, so a session's Bash allow/deny/ask permission rules for `git push` or `gh pr create` never see it as a discrete tool call — they can't, because it isn't one.

`requires_confirmation` doesn't change this. Reading `koto/src/cli/mod.rs:3990-4045`: `run_shell_command` executes first, the `DefaultActionExecuted` event (with the command, exit code, stdout, stderr) is appended to the session log, and *only then* is `action.requires_confirmation` checked to decide whether to return `ActionResult::RequiresConfirmation` (which halts the loop) or `ActionResult::Executed` (which doesn't). The flag is "I already ran this, do you want to continue," not "may I run this." Round 1's finding holds exactly.

Could koto surface the intended command to the agent *before* running it, so the agent executes it through its own tool layer on the happy path and koto only verifies afterward? I found no such mechanism anywhere in the codebase — the only `dry_run` flag in koto is on the unrelated operator command `koto workspace prune`, nothing in `default_action`'s path. Building one would mean: koto's directive names the command, the agent runs it via Bash (visible to the permission layer), submits evidence, and a gate on the same state checks the outcome. That is not a new capability — it is exactly shirabe's current prose+Bash+gate pattern. `default_action`'s entire value proposition was collapsing that round trip so the agent doesn't spend a turn on a mechanical step; a "propose then agent-executes" redesign gives that back. So yes: it reduces to "prose plus a gate," which is what shirabe already does today, not a third option.

Is there koto precedent for an approval step before a side effect? None at the engine level — I grepped for `propose`/`dry_run`/`confirm`/`approval` across `src/` and the only approval-shaped thing in either repo is shirabe's own `deferral_approval` template state (`work-on.md:663-694`): "a blocking human-approval gate ... the human's decision is the evidence." But that gates a *workflow transition* on human judgment about deferring an acceptance criterion — it's implemented entirely as template prose telling the agent to halt and ask, not by any koto primitive that intercepts a shell command before execution. There is no "propose command, wait for yes, then run it" primitive in koto.

**2. The read-only restriction, applied concretely to both maps, is closer to a full stop than a tweak.**

Applied to `/execute`'s Wave A (8 commands, ~15% of 53, per the map-execute lead): both convertible blocks are writes-remote — `orchestrator_setup`'s create-or-reuse block (`git checkout`, `git push`, `gh pr create`) and `plan_completion`'s `run-cascade.sh --push` + `gh pr ready` (commit, push, PR state flip, ROADMAP/PLAN deletion). The restriction kills both — **100% of `/execute`'s current Wave A**. The only genuinely read-only candidate anywhere in the execute map is `ci_monitor`'s polling, and the map's own author (independently of this restriction question) already argued it shouldn't get a `default_action` at all — it would duplicate the `merge_state_clean` gate koto already runs. So for `/execute`, the read-only restriction converts the yield from "8 now, 6-7 more pending engine work" to effectively **zero** net-new commands.

Applied to `/work-on`'s Wave A (3 sites): `extract-context.sh` and `plan_context_injection`'s fetch+store write to koto's own context store, not to the target repo or a remote — a materially different risk category from "branch creation, pushes, PR edits" (the counter-case's own named examples). Read charitably, those two survive; `pr_creation`'s `gh pr list --head` existence check is unambiguously read-only and survives under any reading. So work-on keeps roughly 1-3 of 3 Wave A sites depending on how tightly "side effect" is scoped. But the eight retry-clearing blocks — the largest block of Wave B — die either way: their core act is a nested `koto next --with-data` performing a real state transition, which is by definition not read-only, and separately the map's own empirical check found that specific pattern broken today regardless (the outer `koto next` call reports a stale result after the nested call already advanced the session).

Net: the restriction leaves standing almost exactly the states that were already safe as agent-run prose+gate, and removes almost everything conversion was supposed to buy for `/execute` specifically.

Enforceable how? Not at compile time — I checked `koto/src/template/compile.rs` and `types.rs`; there is no read-only/side-effect classification anywhere in the schema, `default_action.command` is a bare shell string with the same type as a gate command. It could only be a convention, or a shirabe-side lint pattern-matching command strings for verbs like `push`/`create`/`rm`/`edit` (in the style of the existing mermaid-drift checker) — heuristic, and trivially defeated by wrapping a mutation in an innocuously-named script.

**3. The two leads disagree on scope, not on facts.**

Template-patterns proved a mechanism claim, verified against the real binary (with one correction found by the empirical probe: conditional transitions in a state must share a `when` field to pass the mutual-exclusivity check): an isolated, single-purpose, cheaply-gate-verifiable command runs silently on success and routes cleanly to `EvidenceRequired` on failure, with zero koto changes. Its worked example was a synthetic `create_branch` state — not any actual named state from a shipped template.

Counter-case made a candidate claim about the actual states the design doc points at. I re-read `phase-1-setup.md`: "Create Feature Branch" is a decision tree (reuse `SHARED_BRANCH`, reuse if the user said to continue, reuse if already on a feature branch, only create otherwise), and "Establish Baseline" says to use "project-specific commands from the language skill or CLAUDE.md" — no single fixed command exists. Both citations check out. `setup_issue_backed`/`setup_free_form` bundle that judgment together with mechanical work inside one coarse, multi-step state.

These aren't in conflict — they answer different questions. "Does the primitive work" is yes (template-patterns, confirmed empirically). "Are today's named target states good conversion units" is no, not as currently drawn (counter-case, confirmed by reading the actual phase file). The resolution is granularity: the unit of conversion has to be an isolated mechanical sub-step, not today's phase-spanning state — a point map-work-on reached independently under "state-granularity mismatch" when it found `implementation`'s mid-cycle AC recheck and `pr_creation`'s pre-PR diff individually convertible but structurally unreachable at the state boundaries the templates currently draw.

**4. Per-repo command configuration exists and meaningfully weakens the brittleness objection, but doesn't erase it.**

Confirmed: `koto init` accepts `--var KEY=VALUE` (`koto/src/cli/mod.rs:761`, "Validate and resolve `--var KEY=VALUE` arguments against the template's declared variables"), and `default_action.command` already substitutes `{{VAR}}` — both templates use this throughout (`{{PLAN_SLUG}}`, `{{SESSION_NAME}}`, etc.). A `TEST_COMMAND`/`VERIFICATION_COMMAND` variable, declared once in frontmatter and resolved once by the agent reading CLAUDE.md/the language skill at `koto init` time, would let both `setup_*`'s baseline run and `finalization`'s final verification reference `{{TEST_COMMAND}}` instead of a hardcoded string. This is shirabe-side authoring work, not a koto engine change — map-work-on independently reached the same conclusion under "needs-var-plumbing."

What it fixes: today the agent re-derives the right test command from CLAUDE.md/the language skill at *every* qualifying state (at least twice per `/work-on` run). Var-plumbing converts that into a *one-time* judgment call at session start. Real reduction in repeated work.

What it doesn't fix: the concrete example the counter-case cited — the shipped `tests_passing` **gate** (`work-on.md:441`, `[ ! -f go.mod ] || go test ./... 2>/dev/null`) — is a hardcoded, compiled-in command with no `{{VAR}}` at all today. That's a live, un-fixed bug independent of this whole exploration; fixing it means someone edits the template to use `{{TEST_COMMAND}}`, and nobody has. It's also a second, orthogonal brittleness axis var-plumbing doesn't touch at all: per r2's empirical probe, `run_shell_command` deadlocks past ~64KB of combined stdout/stderr and reports a false `timed_out` with the output discarded — a real `go test ./...` failure dump on a large monorepo can trip this regardless of whether the command string is right. Var-plumbing solves "wrong command for this repo"; it does nothing for "right command, too much output."

## Implications

- The read-only restriction and the granularity fix (finding 3) point the same direction: what actually survives contact with both maps is small, isolated, repo-local, gate-verifiable steps — not "koto runs everything on the happy path." The counter-case's instinct ("conversion is right for essentially one state") undersells work-on slightly (1-3 sites survive a charitable read, not zero) but is close to exactly right for `/execute`.
- The 64KB pipe-buffer deadlock (r2-empirical-probe) is not a `default_action`-specific problem and dominates every other finding in severity: it already misreports a passing `tests_passing` gate as `timed_out` in production, today, with zero conversion work done. Any recommendation about widening `default_action`'s reach is moot until this is fixed, because the failure mode — a real pass reported as a failure, evidence discarded — is exactly the silent-failure shape finding 1's incident (`BRIEF-skill-preflight-checks.md`) already burned the team on once.
- Var-plumbing (finding 4) is a genuinely cheap, purely shirabe-side improvement that should happen regardless of any koto-side decision here — it's available now and removes real repeated agent judgment, independent of whether the broader default_action rollout proceeds.

## Surprises

- The read-only restriction, which reads in the counter-case as a moderate compromise ("still capture the ci_monitor win"), actually zeroes out `/execute`'s entire current conversion yield once applied line by line — I expected it to trim the map, not collapse it, until I checked both Wave A rows against the restriction directly.
- `koto init --var` already solves the mechanism half of the environment-brittleness objection. I expected to find this as an open gap; it's shipped and in use by both templates for other variables, just never applied to the one case (`TEST_COMMAND`) the counter-case's strongest example turns on.
- The two round-2 leads read, on the surface, like they contradict each other ("it works today, cheaply" vs. "the candidates are bad") but on inspection they were never testing the same claim — neither lead states this explicitly in their own summary, and reconciling them required going back to the primary source (`phase-1-setup.md`) rather than trusting either summary's framing of the other.

## Open Questions

- Whether a shirabe-side lint (heuristic verb-matching on `default_action.command` strings, similar to the mermaid-drift checker) is worth building as a soft enforcement of the read-only convention, given it can't be compile-time-guaranteed and is easy to defeat with an innocuously named wrapper script.
- Whether `koto context add`/`get` calls (writes to koto's own store, not the target repo) should count as "side-effecting" under a read-only restriction — the counter-case's own language names only git/gh mutations, and treating koto-store writes as a separate, lower-risk category is what keeps `/work-on`'s Wave A from collapsing to zero the way `/execute`'s does.

## Summary
The permission-bypass claim holds exactly as stated — `default_action` runs via `sh -c` as a direct child of the koto binary, never through the agent's Bash tool, and `requires_confirmation` fires only after the command has already executed and been logged; no preview-before-execution mechanism or approval-before-side-effect precedent exists anywhere in koto, and building one would just be shirabe's existing prose+Bash+gate pattern under a new name. A strict read-only restriction, applied line by line to both conversion maps, zeroes out `/execute`'s entire current Wave A (both candidates are writes-remote) and cuts `/work-on`'s to 1-3 of 3 sites depending on whether koto-context writes count as side effects — it is enforceable only as convention or lint, never at compile time. The two round-2 leads don't disagree on facts: one proved the mechanism works for an isolated, gate-verifiable command, the other proved today's actual named states bundle that mechanical work with real judgment (branch-reuse decisions, per-repo test commands) — the fix is converting at sub-state granularity, not per-state. Recommend: run a mechanical step through koto only when it is isolated to its own state, gate-verifiable independent of the action's own exit code, and either read-only or a repo-local mutation safe to reach twice; anything that mutates a remote (push, PR create/edit, the finalization cascade) or needs project-specific configuration to know what to run stays agent-run Bash, because that's the one surface where the user's permission layer and the developer's own judgment about the right command still get to see it before it happens — and none of this is trustworthy until the shared 64KB pipe-buffer deadlock, which already misreports a real test pass as a failure in production today, is fixed.
