# Lead: What does shirabe's tooling enforce or validate today around plan mode, doc structure, and issue creation -- and where would a new preference check land?

## Findings

**Enforcement layers, from strongest to weakest:**

1. **`crates/shirabe-validate` (Rust library) + `crates/shirabe` (CLI, `cmd shirabe`)** -- the single implementation used both locally and in CI. It replaced an earlier Go design (`docs/designs/current/DESIGN-gha-doc-validation.md`, status `Current` but superseded in practice -- the actual code is Rust, not Go; the design doc's architecture section describes a `cmd/shirabe` + `internal/validate` Go layout that was never built that way). It is invoked via `shirabe validate <files>` and via mode flags: `--lifecycle` / `--lifecycle-chain` (chain-aware status-transition checks), `--merge-gate` (coordination merge-order recompute), `--coordination-body` / `--pr-body` (static offline checks), `--check <CODE>` to run a single rule.

2. **`.github/workflows/*.yml`** -- CI wraps the same binary. Key ones: `validate-shirabe-docs.yml` (self-caller of the reusable `validate-docs.yml`), `check-plan-docs.yml` (runs `shirabe validate <plan>` for frontmatter/structure/R6-upstream, then `shirabe validate --lifecycle-chain <plan>` for status-transition legality -- explicitly replacing a retired bash script, per the workflow's own comment: "One implementation answers that question now, and it is the lifecycle model's"), `validate-lifecycle.yml`, `merge-gate` workflows, `pr-body.yml`/`validate-pr-body.yml`.

3. **`skills/review-plan`** -- an agent-driven (not tooling-driven) adversarial reviewer with four categories: A (Scope Gate), B (Design Fidelity), C (AC Discriminability), D (Sequencing/Priority Integrity). Runs as `/plan` Phase 6 or standalone.

4. **`scripts/` at repo root** -- mostly meta-checks on shirabe's own skill/template authoring (bash floor, template interpolation, duplicate rule lists, fixture leaks), not doc-content validation. `skills/plan/scripts/validate-plan.sh` was retired (see check-plan-docs.yml comment above) because it duplicated and contradicted the Rust validator's lifecycle model.

**What is validated today, concretely:**

- **Frontmatter schema** (`FC01`-`FC04` family in `checks.rs`, 8197 lines): required fields, closed status enums (overridable via `--custom-statuses`), required section headings, a status-declared-vs-status-in-body consistency check (FC03).
- **`FC14`**: structural consistency between a PLAN's `execution_mode` frontmatter field (`single-pr` / `multi-pr` / `coordinated`) and which body sections are populated. E.g. `execution_mode: single-pr` with a populated `## Implementation Issues` table fires: *"execution_mode is 'single-pr' but '## Implementation Issues' is populated -- switch the frontmatter to 'multi-pr' or move the content to '## Issue Outlines'"*. This is purely structural -- it enforces that the declared mode matches the doc's shape. **It does not evaluate whether `multi-pr` was the right choice**, only that the doc is internally consistent once a mode is chosen.
- **Lifecycle/status transitions** (`lifecycle.rs`, 4541 lines; `transition.rs`): which status a doc may hold given its upstream's status, posture-aware (`--mode=draft` vs `--mode=ready`) -- e.g. a single-pr PLAN mid-PR is draft-tolerable but must resolve before ready.
- **Coordination** (`coordination.rs`, `merge_gate.rs`, `upstream.rs`): cross-repo PR reference format (F2), merge-order DAG acyclicity, live merge-gate recompute from `gh` (never trusting PR-body text, per F4), private-identifier redaction (F1).
- **`FC-CONVENTIONS`** (`checks.rs:3543`): checks for a `## Release Notes Convention: <path>` header in CLAUDE.md. **This is the only CLAUDE.md convention header the Rust validator currently checks.** It's notice-level (advisory, not error) -- "repos without a declaration receive [a notice, not necessarily a hard block]."

**Doc validation architecture, and what it can/can't see:** The validator reads Markdown files (frontmatter + body) and, separately, a repo's `CLAUDE.md`/`CLAUDE.local.md` for a small number of recognized convention headers via string-matching (`visibility.rs` parses `## Repo Visibility: (Public|Private)` with a documented header regex, walking up from the target file to find the owning repo's CLAUDE.md). So the validator **can** see repo-level config, but only for headers it has been explicitly coded to look for, and only ones written into `CLAUDE.md` in the established convention-header format. It has no generic config-file reader (no `.shirabe/config.toml`, no repo-config struct) -- everything is either a CLI flag (`--visibility`, `--custom-statuses`, `--mode`) or a hardcoded CLAUDE.md header parser.

**Existing precedent for exactly this kind of preference -- already built, one level removed from the target:**

CLAUDE.md (this repo) already declares two durable workspace preferences using the identical pattern the author is asking for:

```
## PR Grouping Policy: coarsest-legal
...one PR per repository (the coarsest legal unit). A repo splits into
more than one PR only on a recorded trigger. This is a durable
workspace preference, resolved `flag > CLAUDE.md-header > default`;
the default is `coarsest-legal`.

## Reviewability Ceiling: default
...This is a durable workspace preference,
resolved `flag > CLAUDE.md-header > default`; `default` defers to
the ceiling defined in `references/coordination-strategy.md`.
```

Both explicitly state the resolution order `flag > CLAUDE.md-header > default` and point to `references/coordination-strategy.md`'s "Coarsest-Legal-Grouping Rule" (line 126) for the semantics: a repo's per-repo PR grouping in a *coordinated multi-repo effort* stays at one PR unless one of four named triggers fires (independently mergeable, independently rollback-able, exceeds reviewability ceiling, or breaks a merge-order cycle).

This is the closest existing analog to "prefer-fewest-PRs vs prefer-atomic-increments" -- same shape (a named header, `flag > header > default` resolution, a rule doc it points to, "do not split absent a recorded trigger") -- but it operates one level up: it governs **how a single repo's work is grouped into PRs within a coordinated multi-repo PLAN**, not whether a **single repo's own PLAN** should be `single-pr` vs `multi-pr` (issues under one milestone, separate PRs) in the first place. `skills/scope/SKILL.md` is the only skill that currently reads/mentions these two headers by name; the Rust validator's `FC-CONVENTIONS` check does **not** currently check for their presence or format the way it does for Release Notes Convention.

**`review-plan`'s Scope Gate (A) does not evaluate decomposition-necessity (single-pr vs multi-pr) either.** Read `skills/review-plan/references/phases/phase-1-scope-gate.md` in full: it evaluates issue *count* and *complexity coverage* against the design's component count (too-few/too-many heuristics: <0.5x or >5x component count), missing components, and a docs-coverage backstop. All of this runs *after* a mode (single-pr/multi-pr/coordinated) has already been chosen and only checks whether the issue breakdown is proportionate to scope -- it never asks "should this have been single-pr instead of multi-pr" or vice versa. That decision point lives earlier in the `/plan` flow (Phase 1 Analysis / Phase 2 Milestone, per the file list), which another lead is investigating directly.

**Precedent for hint-vs-hard-fail already exists, and it's a first-class mechanism, not ad hoc:** `crates/shirabe-validate/src/advisory.rs` is a dedicated "context-aware advisory explanation layer" governed by an explicit **advisory-never-gates invariant** (its own doc comment, line 10-19): "the advisory only *describes* the already-resolved findings," never moves the exit code. The verdict is computed by `posture` (`--mode=draft` vs `--mode=ready`) via `effective_severity`; certain finding codes are `PostureClass::DraftTolerable` -- they're notices under draft posture (in-flight, non-blocking) and errors under ready posture (must be resolved before merge). This is a well-established two-tier severity model already threaded through the CLI (`--mode`), the lifecycle checks, and CI (`check-plan-docs.yml` asserts `ready` only when `github.event.pull_request.draft == false`). A new "was multi-pr justified" check could reuse this exact mechanism: emit a `DraftTolerable`-class finding/notice on a `/plan` PR that declares `multi-pr` without a recorded justification trigger, non-blocking while in draft, promoted to a hard block only if still unresolved at ready -- mirroring `PR Grouping Policy`'s "split only on a recorded trigger" contract.

## Implications

- **The natural insertion point is CLAUDE.md, not a new config file.** The repo already has a documented, validator-aware convention-header slot (`## <Name>: <value>`) with a resolution contract skills are expected to honor (`flag > CLAUDE.md-header > default`). A `## PR Delivery Preference: prefer-fewest-prs` (or similarly named) header, parsed the same way `visibility.rs` parses `## Repo Visibility:`, is the lowest-friction way to make this both agent-readable (skills already grep CLAUDE.md for these headers) and tooling-checkable (FC-CONVENTIONS-style check can be extended, or a new `FC-xx` added).
- **Two distinct validators exist and a new check must pick the right one.** Structural consistency (does the doc's shape match its declared mode) belongs in `checks.rs` (FC14 already lives there and is the direct sibling). Whether the mode choice itself was *justified* is a judgment call today made by an agent (review-plan Scope Gate A, or earlier in /plan's Phase 1/2) -- the Rust validator has no "was this decomposition necessary" logic anywhere, and per its own architecture doc (flat sequential functions, data-driven `FormatSpec`), it isn't built to hold semantic/judgment checks; that's why lifecycle/coordination judgment calls (e.g., merge-gate triggers) are still expressed as recorded facts (a trigger name, a live `gh` state) rather than open-ended reasoning.
- **The advisory/posture mechanism means a hard requirement is not the only option.** A "hint back to the agent" is not a new pattern to invent -- it is exactly what `PostureClass::DraftTolerable` + `advisory.rs` already do for other findings, and the `/plan` Phase 6 review-plan step already has a `loop_target` mechanism (Category A findings loop back to Phase 3 Decomposition) that could carry a scope-preference finding without any new plumbing.

## Surprises

- `DESIGN-gha-doc-validation.md` still carries `status: Current` and describes a Go implementation (`cmd/shirabe` + `internal/validate`, module `github.com/tsukumogami/shirabe`, GoReleaser) that does not match the actual Rust crates (`crates/shirabe-validate`, `crates/shirabe`) in this checkout. The design's *decisions* (flat sequential check functions, `FormatSpec`-driven, collect-all-before-exit, GHA annotation format) clearly carried over into the Rust code, but the doc itself appears stale on language/module layout and wasn't flagged as superseded in the frontmatter I read. Worth a note to whoever owns doc hygiene, though out of scope for this exploration.
- `PR Grouping Policy` and `Reviewability Ceiling` already implement almost exactly the preference-resolution pattern the author is proposing, just scoped to coordinated multi-repo grouping rather than single-repo mode choice. This is close enough that the plan-decoupling work should probably explicitly reference or reuse `references/coordination-strategy.md`'s Coarsest-Legal-Grouping Rule as prior art rather than reinvent the resolution contract.

## Open Questions

- Should a new preference header be a genuinely new name (e.g. `## PR Delivery Preference:`) or should the *existing* `PR Grouping Policy` header be widened in scope to also govern single-repo single-pr-vs-multi-pr, given it already encodes "coarsest-legal absent a recorded trigger"? That's a design decision, not a research question, but the precedent makes it a live option.
- Is FC-CONVENTIONS meant to be extended per-header (each new convention header gets its own hardcoded presence/format check), or should it become table-driven? Right now it only checks Release Notes Convention; PR Grouping Policy and Reviewability Ceiling exist in CLAUDE.md prose but are not validator-checked at all. A new preference header should decide up front whether it needs FC-CONVENTIONS coverage or can stay skill-only (agent-read, never CI-validated).
- Who owns the "recorded trigger" for a single-pr-vs-multi-pr choice, analogous to the four named triggers in Coarsest-Legal-Grouping Rule? Without an equivalent enumerated trigger list, a `DraftTolerable` finding has no crisp condition to check against.

## Summary

shirabe validates PLAN structure (FC14: does `execution_mode` match populated sections) and status-transition legality via a single Rust CLI (`crates/shirabe-validate` + `crates/shirabe`) run identically in CI and locally, but nothing today checks whether `single-pr` vs `multi-pr` was the *right* choice -- that judgment lives only in agent-driven `review-plan` Scope Gate A, which itself doesn't evaluate decomposition-necessity, only issue-count proportionality after a mode is already chosen. The natural landing spot is a new `## <name>: <value>` CLAUDE.md convention header (the exact mechanism already used by `Repo Visibility`, and matched almost exactly in intent by the existing `PR Grouping Policy`/`Reviewability Ceiling` headers' `flag > CLAUDE.md-header > default` contract), checked non-blockingly via the already-built `PostureClass::DraftTolerable` + `advisory.rs` hint mechanism rather than a new hard-fail path. The biggest open question is whether to extend the existing `PR Grouping Policy` header's scope or introduce a sibling, and whether a trigger list (mirroring Coarsest-Legal-Grouping Rule's four named triggers) needs to exist before any check -- hint or hard-fail -- has something concrete to evaluate.
