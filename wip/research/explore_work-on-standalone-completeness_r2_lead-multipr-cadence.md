# Lead: How could a document-chain cascade placed after `ci_monitor` in `/work-on` fire once per plan rather than once per issue on a `multi-pr` PLAN — and what would that discriminator cost to build?

## Findings

### 1. `/work-on`'s multi-pr mode has no loop machinery at all — it is a fresh invocation per issue

`skills/work-on/SKILL.md:137-141` is the entire multi-pr routing instruction:

> `multi-pr` — run in place, one issue at a time. Select the next unblocked issue from the PLAN (an issue is blocked while its Dependencies reference open issues) and run it as a single issue-backed unit against the repo-persisted PLAN, each landing its own PR. There is no shared branch and no cross-issue carry-forward — multi-pr issues are independent, per the DESIGN's ephemeral-home model.

"Run it as a single issue-backed unit" means the selected issue enters the ordinary issue-backed path of `skills/work-on/koto-templates/work-on.md`, ending at that template's own `terminal: true` `done` state (`work-on.md:820`). Nothing routes back to "select the next issue" — I grepped `skills/work-on/SKILL.md` for `repeat|again|until|remaining|no more|ran out` and the only hits are unrelated (`koto next <WF>` retry language, diff classification). There is no "loop until no unblocked issues remain" instruction anywhere in the file.

Continuing to the next issue therefore requires a **new, separate invocation** of `/work-on <PLAN>`. Each invocation's Resume logic (`SKILL.md` Koto Orchestration → Resume: `koto workflows` → if found `koto next <WF>`, else `koto init` fresh) will find the prior issue's workflow already terminal and fall through to a fresh `koto init`, re-running "Select the next unblocked issue from the PLAN" from scratch. So the "loop condition" — is there an unblocked issue left — is evaluated in prose, freshly, at the top of every invocation. It is never expressed as koto state, never gated, and never persisted as machine-checkable loop state. It is not visible to any koto template; it lives entirely in the agent's prose reasoning at entry time.

Confirms the lead's framing precisely: nothing in this path computes or stores "this was the last issue." It only ever asks "is there a next one."

### 2. There is no `work-on-plan.md` parent template — the multi-pr path never spawns children

`docs/designs/current/DESIGN-work-on-koto-unification.md` originally proposed exactly the missing piece: a parent orchestrator template (`work-on-plan.md`) with a `spawn_and_await` state carrying `materialize_children` + a co-located `children-complete` gate (lines describing "Plan mode" data flow, and Phase 4 deliverables: "`koto-templates/work-on-plan.md` with `spawn_and_await`... `materialize_children` hook... `children-complete` gate co-located on `spawn_and_await` (E10)"). That parent template does not exist under `skills/work-on/` — `find skills/work-on -type f` lists only `koto-templates/work-on.md` and `koto-templates/work-on.mermaid.md`.

`docs/designs/current/DESIGN-execute-skill.md`, Decision 2, explains why: "Extraction — move into /execute (chosen, E3). Move `work-on-plan.md`, the orchestrator prose, and `run-cascade.sh`... into /execute; keep `work-on.md` in /work-on as the canonical single-issue engine /execute spawns by cross-skill path." And later: "multi-pr: not owned by /execute; the /work-on dispatcher runs it in place, one issue at a time, against the repo-persisted PLAN" (`DESIGN-execute-skill.md:138`).

So the parent-child batch machinery (`materialize_children` + `children-complete`) was built, but it now lives entirely inside `/execute` (`skills/execute/koto-templates/execute.md:290-311`, the `spawn_and_await` state) and `/execute` explicitly excludes multi-pr (`skills/execute/SKILL.md:48`: "`multi-pr` — out of scope for `/execute`; multi-pr plans run one issue at a time"). I grepped both template files for `type: children-complete` and `materialize_children`: both appear only in `skills/execute/koto-templates/execute.md`, never in `skills/work-on/koto-templates/work-on.md`.

### 3. `/execute`'s signal, precisely, and why it is unavailable to multi-pr

`skills/execute/koto-templates/execute.md:290-311`:
```
spawn_and_await:
    gates:
      batch_done:
        type: children-complete
    ...
    materialize_children:
      from_field: tasks
      failure_policy: skip_dependents
      default_template: ../../work-on/koto-templates/work-on.md
    transitions:
      - target: pr_finalization
        when:
          batch_outcome: all_success
          gates.batch_done.all_complete: true
```

The signal is koto's own native gate type, `children-complete`, evaluated by koto's scheduler against the batch of children `/execute`'s own workflow materialized via `materialize_children` — this is koto bookkeeping, not something `/execute` computes itself. It is available **only to the koto workflow that is the parent-of-record for those children** — a structural property of being that parent, enforced by koto's own "E10" compile rule (`materialize_children` requires a co-located `children-complete` gate; `DESIGN-work-on-koto-unification.md` "Two-state orchestrator... Rejected: E10 makes this a compile error").

`/work-on`'s multi-pr issues are never materialized this way. Each is `koto init <WF>`'d directly, `WF = issue_<N>`, as its own top-level workflow (`SKILL.md` Koto Orchestration → Initialize). There is no parent workflow, so there is no `children-complete` gate to read. This answers the lead's question directly: the signal is a structural property of koto parentage, and `/work-on`'s multi-pr mode is, by design (`SKILL.md:140`, "no shared branch and no cross-issue carry-forward"), never a koto parent of anything.

To give multi-pr this signal, `/work-on` would need to rebuild the very `work-on-plan.md` parent template that was deliberately extracted into `/execute` — which would also mean multi-pr issues stop being independent top-level workflows, contradicting the explicit "no shared branch, no cross-issue carry-forward" design property that distinguishes multi-pr from single-pr/coordinated in the first place. This is not a small addition; it is forking `/execute`'s orchestrator architecture a second time, for a mode whose whole point was not needing it.

### 4. The no-chain case: `run-cascade.sh` requires a PLAN doc argument; the "clean skip" only covers a PLAN with no upstream chain, not "no PLAN at all"

`skills/execute/scripts/run-cascade.sh` takes a mandatory positional `<plan-doc-path>` (usage/arg parsing, `run-cascade.sh:697-707`: "if `-z "$PLAN_DOC"`... Error: plan-doc-path is required"). Two distinct "no-op" cases exist, and only one of them is a clean skip an unrelated invoker gets for free:

- **PLAN present, doc-tree chain already at its terminal / has no upstream at all** — clean, no-error skip. The pre-cascade lifecycle probe (`run-cascade.sh:759-771`) runs the chain validator in ready-posture; if it already passes, the script logs "chain already at ready-posture passing state — cascade is a no-op," emits `{"cascade_status":"skipped", ...}`, and exits 0. Separately, at the tail (`run-cascade.sh:1002-1017`), a PLAN whose `finalize-chain` report contains only the PLAN-delete node (no BRIEF/PRD/DESIGN above it) is also reported `cascade_status: skipped` — "the PLAN had no upstream chain (only the delete step ran)." Both paths exit 0 and require no caller-side guarding.
- **No PLAN doc at all** (a standalone issue-backed or free-form `/work-on` run has none to pass) is *not* handled gracefully by the script itself: `run-cascade.sh:733-736` treats a missing/nonexistent `$PLAN_DOC` as a hard failure — `{"cascade_status":"skipped","steps":[],"error":"PLAN doc not found: $PLAN_DOC"}`, **exit 1**. The script was never designed to be called with nothing; it always expects a concrete path.

Confirmed by usage: `/execute`'s own call site, `skills/execute/koto-templates/execute.md:709` — `${CLAUDE_PLUGIN_ROOT}/skills/execute/scripts/run-cascade.sh --push {{PLAN_DOC}}` — always supplies a concrete `{{PLAN_DOC}}`, because `/execute` is inherently PLAN-driven; it never faces the "no PLAN at all" case.

**Requirement this puts on any cascade-in-`/work-on` proposal**: the *caller* — not `run-cascade.sh` — must decide whether a PLAN doc (and upstream chain) exists at all before invoking the script. A standalone issue-backed `/work-on` run with no PLAN/DESIGN/BRIEF must never call `run-cascade.sh` with an empty or fabricated path; it must skip the call entirely. `run-cascade.sh`'s own no-op handling only takes over once you're already holding a valid PLAN path.

### 5. Multi-pr already has a per-plan-once obligation — and the codebase's answer to "how do you know it's the last one" was explicitly *not* to auto-detect

`skills/plan/references/quality/plan-doc-structure.md:95` states the PLAN's own Done trigger for multi-pr: "multi-pr: all issues closed and the work-completing PR runs the cascade." This is exactly the per-plan-once obligation the lead asked about (question 5) — chain finalization (PLAN `Active → Done → DELETED`, BRIEF/PRD `Accepted → Done`) must happen exactly once, on the last PR, not once per issue.

`docs/decisions/DECISION-multi-pr-posture-detection-2026-06-06.md` is the record of how this was actually resolved, and it directly informs (without deciding) the discriminator question:

- **Chosen mechanism**: posture is read from the PLAN's own frontmatter `status:` field, not inferred. "The author's gesture for 'this PR is the work-completing PR' is the single atomic commit set that flips `status: Active` to `status: Done`, deletes the PLAN file, and transitions BRIEF/PRD to `Done`." Whoever is doing the last piece of work makes this edit deliberately, by hand (or via `shirabe transition`) — the system does not detect "lastness" automatically.
- **Rejected — Option 2, "Strikethrough completeness in the PLAN's issues table"**: "Walk the PLAN's `## Implementation Issues` table, count strikethrough vs non-strikethrough rows; all-strikethrough → work-completing." Rejected explicitly because it "conflates the 'last child issue's PR just merged but the verify-then-delete PR is not yet opened' state with the 'work-completing PR' state... The strikethrough state is also dependent on the parent PLAN being updated synchronously with child-issue closures — exactly the drift FC09 emits a notice for, not a clean source of truth. Author has no explicit gesture; the posture flip is implicit and races with child PR merges."
- **Rejected — Option 3, git introspection**: diffing against `origin/main` to see if the PLAN is deleted. Rejected for added infra dependencies, and because it's redundant with the frontmatter signal anyway.

This is the closest thing to precedent in the corpus, and it points against automatic "last issue" detection, not toward a specific implementation of it. It is worth noting this mechanism is **not actually wired up for multi-pr today**: the cascade code that would perform this finalization (`run-cascade.sh`) lives only in `/execute` (`DESIGN-execute-skill.md` Decision 2, "Move... `run-cascade.sh`... into /execute"), and `/execute` excludes multi-pr. `/work-on/SKILL.md:183` confirms: "The plan-level orchestrator — shared branch and draft PR, child spawning, cross-issue context assembly, escalation, PR finalization, and the completion cascade — now lives in `/execute`... `/work-on` keeps only Plan-Backed Child Mode." No multi-pr branch of this finalization logic remains in `/work-on`. `docs/designs/current/DESIGN-multi-pr-plan-decoupling.md:652` states this gap outright, in the context of issueless multi-pr plans, but in language that generalizes: "Building that entry point — a `/work-on` dispatcher branch that reads the graph plus some non-GitHub completion signal — is separate, currently unowned work, and this design does not claim it." A "non-GitHub completion signal" for `/work-on` multi-pr driving is explicitly named in the corpus as unbuilt, unowned work — which is exactly the discriminator this lead is pricing.

### 6. GitHub-state discriminators face a categorical gap: issueless multi-pr plans exist and have no entry point at all today

`docs/designs/current/DESIGN-multi-pr-plan-decoupling.md` introduces `## Tracking Level: none|issues|issues-and-milestone` (line ~14) and a third `ISSUE_SOURCE=plan_item` value specifically so "an issueless multi-PR plan keys its work items on outline-derived local ids rather than GitHub issue numbers" (line ~20, elaborated at lines 240, 452-453, 509-510: `tracking_level == none` routes to "outline parse → ISSUE_SOURCE=plan_item, m-<slug>"). At `tracking_level: none`, a multi-pr plan has **no GitHub issues and no milestone at all**.

The same design's Consequences section names the resulting gap directly (line ~652): "No entry point can drive an issueless multi-PR plan. `/work-on M<N>` has no milestone to resolve against, and `/execute` declines `multi-pr` outright... so there is no path-driven fallback either." Any discriminator built on `gh issue`/milestone queries inherits this gap by construction — it simply cannot fire for the issueless variant, because there is nothing in GitHub to query. That variant currently has no working driver at all, so this may be an acceptable scope boundary for now, but it means a GitHub-state discriminator is not general over all multi-pr plans as the design stands.

## Implications

- Every "automatic" discriminator (Implementation Issues table, `gh` milestone/issue query, a dispatcher-written flag) has to solve a problem the corpus already looked at once, for a structurally similar question ("is this PR the work-completing one?"), and rejected automatic table-based detection for. That prior rejection does not conclusively rule out an "all issues closed" check for a different purpose (routing a cascade vs. classifying a PR's posture), but it is the same underlying signal (table sync state) with the same drift and race exposure, so it inherits those objections at minimum as things to close before shipping, not as a solved footnote.
- The `children-complete` route is correct-by-construction if built, but "if built" means re-deriving `/execute`'s parent-orchestrator architecture inside `/work-on` for multi-pr specifically — the exact thing the codebase split out of `/work-on` and gave to `/execute`, and multi-pr's whole reason for staying outside `/execute` is that it does *not* want a shared branch or cross-issue coordination. Building this discriminator this way pulls multi-pr partway back toward the architecture it was carved out to avoid.
- A "dispatcher context flag" discriminator has no host to live in today: multi-pr issues are independent top-level koto workflows with "no cross-issue carry-forward" (`SKILL.md:140`) by explicit design; a persistent flag would require inventing new cross-invocation state, which is exactly the "SKILL.md-only orchestrator... coordinating via `wip/` state" pattern `DESIGN-work-on-koto-unification.md`'s Decision 2 already rejected once (for the single-pr/coordinated case) as reintroducing "a second source of truth for batch progress."
- The cheapest-looking discriminator (`gh` milestone query, reusing the existing "list open issues in the milestone" pattern already used for milestone-argument input resolution) is real and buildable at low incremental cost for the common case (tracking level `issues` / `issues-and-milestone`), but is not a general solution: it is silent/inoperable for issueless multi-pr plans, which independently have no `/work-on` entry point today per Finding 6 — so this cost estimate should be read as "cheap for the multi-pr shape that currently works," not "cheap for multi-pr in general."
- The one thing that is unambiguously cheap and consistent with the corpus's own considered answer to the sibling problem: don't auto-detect at all — have the human/agent driving the final issue say so explicitly (a flag, an `AskUserQuestion`), mirroring the "author's gesture" pattern already adopted for work-completing-PR posture. This trades build cost for correctness risk shifted onto the operator, and inherits the same "PLAN status can be set wrong or left stale" failure the decision doc itself accepts as a trade-off ("Accepted trade-off: A clever author could set PLAN status to Done... never produce a work-completing PR... That is the forcing function working as designed" — i.e., the corpus treats a wrong or missing gesture as a *forcing function* problem for a human to notice and fix, not as silent failure).

## Surprises

- The DESIGN doc that actually names a "children-complete"-equivalent plan for `/work-on` (`DESIGN-work-on-koto-unification.md`) is still marked `status: Current` even though its own "Plan mode" architecture (a `work-on-plan.md` parent template owned by `/work-on`) was subsequently extracted wholesale into `/execute` by a later, also-`status: Current` design (`DESIGN-execute-skill.md`). Neither design's frontmatter records the other as superseding it; the actual current state has to be reconstructed by noticing which files exist on disk (`work-on-plan.md` does not; `execute.md` does) rather than by reading either document's status field in isolation.
- `DECISION-cascade-trigger-mechanism-2026-06-06.md` still describes, as the accepted decision, a "multi-pr chains in the work-completing PR" branch inside "the work-on skill template" that "Detects chain posture... by reading the PLAN's `execution_mode` and the chain's open-issue count" — i.e., an open-issue-count discriminator was explicitly adopted at one point. That branch is not present anywhere in the current `/work-on` SKILL.md or koto template; the cascade code it describes was later moved entirely into `/execute`, which excludes multi-pr. So the codebase briefly had (on paper) essentially the discriminator this lead is investigating, then lost it in a later architectural split, without an amendment record documenting the removal for multi-pr specifically (only `DESIGN-multi-pr-plan-decoupling.md`'s Consequences section flags the resulting hole, and only for the issueless-plan discussion).

## Open Questions

- If a `gh`-milestone-based discriminator were added at the `ci_monitor → cascade` boundary, would it reuse the exact query pattern from the Milestone-input Input Resolution flow, or does that flow's "select first unblocked issue" list differ in scope (open issues generally) from what a "did I just close the last one" check needs (all issues, checking none remain open)? I did not find an existing single reusable primitive for the latter; it would need its own `gh` call shape, not just borrowed code.
- Is there a plan for closing the issueless-multi-pr entry-point gap (`DESIGN-multi-pr-plan-decoupling.md:652`, "currently unowned work") that this lead's discriminator work should coordinate with, so a cascade-cadence discriminator and a general-purpose completion signal aren't built twice for the same underlying need?
- Whether the DECISION-cascade-trigger-mechanism-2026-06-06 record was ever formally amended or superseded when the cascade moved into `/execute` — I found no amendment note analogous to the one appended to DECISION-multi-pr-posture-detection-2026-06-06.md; this is a documentation gap in the corpus, not something this lead can resolve.

## Summary

`/work-on`'s multi-pr mode has no last-issue machinery today because it has no loop at all — each issue is a fully independent top-level koto workflow selected and run by fresh prose reasoning in a new invocation, with the actual `children-complete`/`materialize_children` batch-completion mechanism existing only inside `/execute`'s parent template, which multi-pr deliberately never touches. The one precedent for a per-plan-once signal in multi-pr — the chain-finalization "work-completing PR" — was explicitly resolved by rejecting automatic detection (issues-table completeness was tried and rejected for drift and races) in favor of a deliberate author gesture, and that finalization logic itself no longer exists in `/work-on` at all, having been extracted into `/execute` alongside the batch machinery; a `gh`-milestone-query discriminator is buildable cheaply for tracking-level `issues`/`issues-and-milestone` plans but is silent by construction for issueless multi-pr plans, which independently lack any `/work-on` entry point today. The biggest open question is whether a cascade-cadence discriminator should be scoped to the currently-working issue-tracked multi-pr shape only, or whether it needs to wait on (or fold into) the separately-flagged, currently-unowned work of giving issueless multi-pr plans any driver at all.
