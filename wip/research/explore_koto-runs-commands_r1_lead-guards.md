# Lead: What guards exist against unintended side effects when koto executes a command itself, and are they enough?

## Findings

**1. Working directory resolution — process cwd, not workflow root.**
The action closure in `handle_next` computes `wd` at `src/cli/mod.rs:3979-3983`:
```rust
let wd = if action.working_dir.is_empty() {
    current_dir.clone()
} else {
    std::path::PathBuf::from(variables.substitute(&action.working_dir))
};
```
`current_dir` is set once at `src/cli/mod.rs:3082` as `std::env::current_dir()?` — the OS process cwd at the moment `koto next` was invoked. If a template's `default_action` omits `working_dir` (the common case — none of the `ActionDecl` test fixtures in `src/template/types.rs` set it), the shell command runs wherever the caller's shell happened to be `cd`'d to. Gates use the identical `current_dir` value (`src/gate.rs:64`, wired at `src/cli/mod.rs:3955`). No code path validates that `current_dir` matches the directory the workflow was `koto init`-ed from — there is no such recorded value to check against (see Finding 2). A relative `working_dir` string in a template (e.g. `"scripts"`) is equally cwd-relative, since `PathBuf::from(...)` is fed straight to `Command::current_dir`, which resolves relative paths against the parent process's cwd, not the workflow root.

If the resolved `wd` doesn't exist, `run_shell_command` (`src/action.rs:26-58`) fails at `cmd.spawn()` and returns `exit_code: -1` with a "failed to spawn command" stderr — it does not silently fall back to another directory. That part fails safe. The unsafe case is a working_dir that *does* exist, just not the one the author intended.

**2. No binding between a session and a filesystem tree.**
`koto init` (`src/cli/mod.rs:1720` on) records no repo path, root directory, or cwd anywhere in `StateFileHeader` (`src/engine/types.rs:223`). The one path-shaped field on the header, `template_source_dir` (`src/engine/types.rs:260`), is populated for a completely different purpose: it records where the *template file* was read from, and it exists to support relative-path resolution when the batch scheduler spawns child templates (`src/engine/path_resolution.rs:1-121`) and to print a "stale template source" hint on `koto init` collisions (`src/cli/mod.rs:1700-1717`). It is never read by `handle_next`, never compared against the invoking cwd, and carries no enforcement.

Session lookup by `koto next <name>` is a flat, name-keyed lookup under `~/.koto/sessions/<name>/` — confirmed by the migration code in `src/session/local.rs:645-700`, which explicitly migrated *away* from a `base/<repo-id>/<name>` layout to the current flat `base/<name>` layout. `repo_id()` (`src/session/local.rs:645`) still exists but is now used only by the cloud backend's blob-prefixing (`src/session/cloud.rs:74-76`), not to scope or validate local session lookups. The practical consequence: a session name is portable across any directory on the machine. Running `koto next my-workflow` from `~/repo-a` versus `~/repo-b` looks up the exact same session and, for any state whose `default_action` doesn't set an explicit absolute `working_dir`, executes that state's shell command against whichever of the two you happen to be sitting in. Nothing short of template-author discipline (always set an explicit, absolute `working_dir`) prevents this — this is precisely the "wrong folder" scenario the user flagged.

**3. Reversibility policy (`requires_confirmation`) is author discipline, not compiler-enforced.**
`ActionDecl.requires_confirmation` (`src/template/types.rs:203`) is a plain bool with no default-true, no companion validation. Grepping `src/config/validate.rs`, `src/template/compile.rs`, and `src/export/check.rs` for `requires_confirmation` turns up nothing except the mechanical passthrough at compile time (`src/template/compile.rs:243`: `requires_confirmation: sa.requires_confirmation`). The design doc says this explicitly (`docs/designs/current/DESIGN-default-action-execution.md:442-446`):
> "The engine enforces this at the loop level — when the flag is set, the loop stops and returns to the caller. **The template author is responsible for setting this flag correctly; the engine can't determine reversibility automatically.**"

So the entire "irreversible actions require confirmation" safety property rests on a human correctly classifying every `default_action` command as reversible or not, with zero static or compile-time check catching a mis-classified `git push`, `gh pr merge`, `rm -rf`, etc. There is also no allowlist/denylist of dangerous commands or subcommands — the compiler validates variable references (`src/template/types.rs:834-840` checks `{{VAR}}` refs in `working_dir` are declared) but not command *content*.

**4. Timeout and process isolation are real and enforced, but timeout is not template-configurable for one-shot actions.**
`run_shell_command` (`src/action.rs:26-102`) spawns via `sh -c`, calls `libc::setpgid(0, 0)` in `pre_exec` to put the child in its own process group (`src/action.rs:41-46`), and on timeout sends `SIGKILL` to the whole group via `libc::killpg` (`src/action.rs:87-91`), then reaps the child to avoid a zombie. This is solid: a hung command and its descendants (e.g. a spawned dev server) get killed together, not orphaned. Default timeout is 30s (`DEFAULT_TIMEOUT_SECS`, `src/action.rs:11`) when `timeout_secs == 0`. However, for one-shot (non-polling) actions the call site hardcodes 30 regardless of template intent — `crate::action::run_shell_command(&command, &wd, 30)` at `src/cli/mod.rs:4020` — `ActionDecl` (`src/template/types.rs:198-208`) has no `timeout_secs` field at all; only `PollingConfig` (`src/template/types.rs:210-214`) carries `timeout_secs`/`interval_secs`, and only for the polling path. A legitimately slow one-shot command (a real build, a large test suite) simply gets killed at 30s with no way for the author to extend it short of routing it through polling machinery it wasn't designed for.

**5. Environment: fully inherited, no allowlist/denylist, no sandboxing — but shell-injection is closed by a strict value allowlist, not escaping.**
Neither `src/action.rs` nor `src/gate.rs` calls `.env()`, `.envs()`, or `.env_clear()` on the `Command` — confirmed by grep returning nothing. The spawned `sh -c` inherits the full environment of the `koto` process, unfiltered: any secret, credential, or `PATH` override present in the invoking shell is visible to the executed command. There is no sandboxing (no containers, no `nsjail`/`bwrap`, no `chroot`) — `setpgid` gives process-group isolation for *timeout cleanup*, not privilege or filesystem isolation.

Command-injection via `{{VAR}}` substitution is closed differently than the lead's framing assumed: it is not shell-escaped, it is allowlist-filtered at the value level. `VALUE_PATTERN` in `src/engine/substitute.rs:29` is `^[a-zA-Z0-9._/:@ \-]*$` — every variable value is validated against this at `koto init` and re-validated defense-in-depth on every read from events (`Variables::from_events`, `src/engine/substitute.rs:59-73`). None of `;`, `|`, `&`, `$`, backtick, quotes, `\n`, `(`, `)`, `<`, `>` are in the allowed set, so a `{{VAR}}` value cannot inject shell metacharacters, command substitution, or redirection — it can only ever land as literal path/identifier-shaped text (or, per Issue #186 handling at `src/engine/substitute.rs:99-135`, an explicit `''` empty-argument token). Space is allowed, so word-splitting an unquoted `{{VAR}}` into multiple argv tokens is still possible and is explicitly left to template-author quoting discipline (documented at `src/engine/substitute.rs:24-27`), but that's an argument-boundary bug, not arbitrary command execution. `working_dir` substitution uses the non-shell-safe `substitute()` (`src/cli/mod.rs:3982`) since it isn't going through `sh -c` — consistent and fine given it's fed to `Command::current_dir` directly, not interpolated into a shell string.

**6. Idempotency / re-entry: no de-dup against a prior `DefaultActionExecuted`, and this is a real gap.**
The action closure fires whenever `has_evidence` is false (`src/engine/advance.rs:288-289`: `let has_evidence = !current_evidence.is_empty();`), where `current_evidence` is the evidence the *current* `koto next` invocation was given (empty unless `--with-data`/override evidence was passed, or reset to empty after an internal auto-advance at `src/engine/advance.rs:514,558`). Crucially, the engine never looks backward at the event log for a prior `DefaultActionExecuted` event on this state before deciding to run again — `DefaultActionExecuted` (`src/engine/types.rs:544`) is written for audit/dashboard purposes (`src/cli/dashboard_data.rs:854`, `src/engine/persistence.rs:2573`) but is never read as an execution guard anywhere in `src/engine/advance.rs` or `src/cli/mod.rs` (confirmed by grep — the only reads are in persistence/dashboard code, not the advance loop).

Concretely: if `koto next my-wf` is called twice in a row on the same non-terminal, non-`requires_confirmation` state — because a caller retries after a transient network blip on their end, double-clicks a script, or races (see Finding 7) — the second call re-executes the exact same shell command with no memory of the first run. The design's safety net is "only reversible actions auto-execute" (`docs/designs/current/DESIGN-default-action-execution.md:55-56,71-72`), which mitigates *harm* from a second run but doesn't prevent the second run itself, and "reversible" is not the same property as "idempotent" — e.g. an action that appends a changelog line, increments a counter file, or creates a timestamped branch is reversible (you can undo it) but not idempotent (running it twice leaves two entries/branches), and nothing in the engine stops that.

The `rewind`/retry path (`src/cli/retry.rs`, `docs/designs/current/DESIGN-batch-rewind.md`) is explicitly non-destructive at the event-log level — `docs/guides/cli-usage.md:270` notes rewind "appends a new event rather than truncating history" — but a rewind to a state with a `default_action` and a subsequent `koto next` will re-run that action exactly like any fresh entry to the state, for the same reason: no execution-count check exists.

**7. Concurrency: no lock for ordinary (non-batch) workflows — an explicit, acknowledged gap.**
`handle_next` only acquires an advisory `flock` on the state file when the current state is batch-scoped (`state_is_batch_scoped`, checked at `src/cli/mod.rs:3859`). The surrounding comment is unusually direct about the tradeoff (`src/cli/mod.rs:3836-3848`):
> "Non-batch workflows intentionally skip the lock... Ordinary workflows never run a scheduler, so no ordering is needed and two concurrent ticks would at worst append-compete at the state file level -- which the engine's existing single-writer semantics handle."

That reasoning covers state-file write safety (event log corruption), but it does not cover shell-command safety: two concurrent `koto next my-wf` invocations against the same non-batch, non-terminal, `default_action`-bearing state can both observe `has_evidence == false` and both call `execute_action`, running the same command twice, concurrently, in the same working directory — a straightforward double-execution/race hazard for anything non-idempotent (parallel writers to the same file, two `git commit`s racing, two branch-creation attempts). `claim.rs` (`src/engine/claim.rs:1-60`) solves an adjacent but different problem — exactly-one-winner for *dispatching a child workflow* to a coordinator — and doesn't apply to a single session being ticked twice by two independent `koto next` invocations (e.g. two terminal tabs, or a coordinating script and an impatient human).

**8. Existing safety discussion in docs.**
`docs/designs/current/DESIGN-default-action-execution.md` is the authoritative design doc (spawned from Issue #71) and its "Security considerations" section (lines 431-449) explicitly scopes the threat model to "same as gate commands" and calls out exactly two things: (a) action output landing in the committed event log as a secrets-leak vector, mitigated only by "document that action commands should not produce sensitive output" plus 64KB truncation (`MAX_ACTION_OUTPUT_BYTES`, `src/cli/mod.rs:61`) — documentation, not enforcement; and (b) the reversibility constraint discussed in Finding 3. The doc does not mention working-directory correctness, session-portability, idempotency, or non-batch concurrency at all — none of Findings 1, 2, 6, or 7 are discussed anywhere in `docs/`, confirmed by grepping "irreversible", "destructive", "safety", "guard", "confirmation" across `docs/` (results limited to `workspace prune`'s unrelated `--force` gate in `docs/guides/cli-usage.md:822-827`, and hierarchical-workflow cleanup destructiveness in `docs/designs/current/DESIGN-hierarchical-workflows.md:290-318`, neither of which is about `default_action`).

## Implications

For shirabe's target state — koto running commands on the happy path with hard guards, agent-instruction fallback on failure — the guards that exist (process-group timeout/kill, output truncation, the shell-injection-closed variable allowlist) are real and enforced by the compiler/runtime, not just convention. But the three properties the user's stated concern ("running the command on the wrong folder") and general "unintended side effects" concern most directly depend on are **not** enforced: working-directory correctness depends entirely on every template author remembering to set an absolute `working_dir` on every `default_action`; irreversibility classification depends entirely on every template author correctly setting `requires_confirmation`; and double/concurrent execution safety depends entirely on every `default_action` command happening to be idempotent, which the schema doesn't require or check.

## Surprises

- The `template_source_dir` field looks, from its name, like it should be the natural place to anchor "the directory this workflow's commands should run in" — but it is used for an unrelated purpose (batch child-template file lookup) and is never consulted by the action-execution path at all.
- The non-batch concurrency gap is not an oversight the code is hiding — it's a deliberate, documented decision (`src/cli/mod.rs:3836-3848`) reasoned about purely in terms of state-file write safety, without apparently considering that the same race also double-fires arbitrary shell commands.
- Shell-injection safety comes from a value allowlist regex, not shell escaping/quoting — worth knowing precisely because it means safety holds only as long as every future variable source (env vars, GitHub API fields, etc.) is funneled through `validate_value`/`Variables::from_events`; a new code path that stuffs a raw string into `WorkflowInitialized.variables` without going through that validator would reopen injection.

## Open Questions

- Does anything upstream of `koto init` (e.g. a shirabe skill) intend to record the invocation cwd/repo root into the template's variables so authors could reliably set `working_dir: "{{REPO_ROOT}}"`? Nothing in koto itself provides or requires this today.
- Is there an intended per-action `timeout_secs` field on the roadmap, given `PollingConfig` already has the pattern? Today one-shot actions are hard-capped at 30s with no template override.

## Summary
Koto's execution guards are real for what they cover — process-group timeout/kill, 64KB output truncation, and a strict character-allowlist that closes shell injection through `{{VAR}}` substitution — but they say nothing about *where* or *how often* a command runs. Working directory defaults to the invoking process's raw cwd with zero binding between a session and the repo it was created in (sessions are looked up by a flat, portable name), so `koto next` from the wrong directory silently runs the action there; and reversibility (`requires_confirmation`) plus idempotency have no engine-level check at all — the design doc itself says the template author alone is responsible for correctly marking irreversible actions, and there is no defense at all against a non-idempotent action firing twice, whether from a caller retry or from two concurrent `koto next` calls on the same non-batch session, which the code deliberately leaves unlocked.
