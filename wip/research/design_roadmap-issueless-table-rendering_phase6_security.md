# Security Review

## Verdict: FAIL

The classic surfaces (subprocess, file write, network) are correctly assessed as unchanged, but the design as written turns an author-controlled integer into a slice index (`keys[id-1]`), and its dangerous-character enumeration is incomplete for the equality the validator actually applies, so the invariant it claims to establish by construction does not hold.

## Findings

1. **`keys[id-1]` is a reachable panic on author-controlled input**: High -- The Components table specifies `render_deps_cell` "resolves each `Feature N` to `keys[id-1]`". `feature_refs_in` (`populate.rs:936`) extracts *any* integer following the word `Feature`, straight from a `**Dependencies:**` line. `**Dependencies:** Feature 0` yields `id == 0`, so `id - 1` underflows (panic in debug, wrap-then-index-out-of-bounds in release). `**Dependencies:** Feature 12` on a three-feature roadmap -- an ordinary stale reference after a feature is deleted -- indexes past the end. Today's code is total over this input: `features.iter().find(|f| f.id == id)` (`populate.rs:834`) returns `None` and the token is silently dropped. The design replaces a total lookup with a partial one in a module whose parsers are explicitly documented as "total over arbitrary line input" and never panicking. This also breaks D2's byte-identical claim in the failure case, and in issue-creating mode the panic lands *after* `gh issue create` has run (`run_inner` creates issues at `populate.rs:124` and renders at `:127`), so the operator gets created issues, no document write, and a stack trace. Mitigation: specify the lookup as `features.iter().position(|f| f.id == id).and_then(|i| keys.get(i))`, keeping the "unknown id contributes no token" behaviour that `render_diagram` and `ready_or_blocked` already rely on.

2. **The fallback predicate does not enumerate what makes a label unusable as a validator key**: High -- The design asserts the duplicate comparison is "the same equality FC06 applies when it matches a dependency token against the key set." It is not. FC06 (`checks.rs:647-681`) compares `Row.key`, produced by `extract_entity_key` (`table.rs:417`), against dep tokens produced by `extract_deps` (`table.rs:383`). Those two apply *different* normalizations to the same label text, and the key cell -- unlike the dependency cell -- is strikethrough-wrapped for terminal features. Concrete failures that pass the proposed `,`/`|`/empty/duplicate predicate:
   - **`~~` in a label of a `Done` feature.** The renderer emits `| ~~<label>~~ |` for the key and a bare `<label>` inside the dependent's cell. For a label `a~~b`, `strip_strikethrough` (`table.rs:439`, pattern `~~([^~]*)~~`) collapses `~~a~~b~~` to `ab`, while the dependency token stays `a~~b`. FC06 then reports "dependency `a~~b` names no row in this table" -- an error-level finding on the tool's own output, which is precisely the D1 failure the design says it eliminated. Any odd number of `~~` runs in the label reproduces it.
   - **`#<digits>` in a label.** `extract_entity_key` runs `ISSUE_REF_PATTERN` (`#(\d+)`) over the whole cell first, so the label `Retire #123 shim` produces the row key `#123`, not the label. Two features whose labels both mention `#123` collapse to one key in FC06's `HashSet` with no duplicate detected and no warning emitted; a dependency on either silently resolves to whichever row. If the label also contains a `/` before the `#` (`A/B split #7`), the dep token keeps the slash, `is_local_key` returns false (`checks.rs:689`), and the edge is dropped from verification entirely.
   - **`](` in a label.** `normalize_feature_ref` reduces `[Cache](a)` to `Cache`, so two labels differing only in link target are one key to the validator and two distinct strings to `key_fallback_reason`.
   Mitigation: state the predicate as a fixpoint test rather than a character blacklist -- fall back unless normalizing the label the way the validator normalizes a key returns the label unchanged, *and* the normalized forms are unique across features. Commas and pipes stay explicit (they break `split_row`/`extract_deps` before normalization ever runs). If `extract_entity_key`'s normalization has to be re-expressed in `populate.rs`, that is the two-implementations hazard D1 was written to avoid, and the honest fix is to export it from `shirabe-validate`.

3. **`render_warnings` reports a fallback that issue-creating mode does not perform**: Medium -- `render_warnings(&[Feature]) -> Vec<String>` takes no mode parameter, yet step 4 has both `run_issueless` and `run_inner` print it. Under Decision C2 `render_table` keeps plain stripped labels, so in issue-creating mode a comma-bearing label produces the line `key falls back to F4 (label contains a comma)` while the rendered table contains no `F4`. That directly contradicts the stated mitigation "a roadmap can never fall back silently or warn about a row that did not." Mitigation: pass the key table (or a mode flag) into `render_warnings`, and emit the key diagnostic only where the fallback is applied -- issue-creating mode should either warn in its own words about an unusable key or stay silent.

4. **The description cell carries the same hazards as the key and the design treats only one of them**: Medium -- The design frames the empty-body bug as "renders `__`", which is the degenerate case of a general rule: `is_italic_cell` (`table.rs:444`) rejects any cell starting `__`, so *any* description whose first character is `_` produces the identical FC05 error. A body opening `_Note:_ this feature...` or `__init__ parsing is deferred.` renders `| ___init___ parsing is deferred._ | | | |`, classifies as an entity row, and fails FC05 exactly as the reproduced two-feature fixture does. The placeholder text fixes the empty case only. Two further cases the section does not reach: a `|` anywhere in the body splits the description row so `rest_empty(&cells[1..])` fails and the row classifies as an entity row (the design calls this "a rendering defect", which understates it -- it is the same self-invalidating-output class it is fixing, and it is inconsistent to fall back on a pipe in a label while accepting one in a body); and the 197-character cut can *create* malformed markup that the untruncated text did not have, most concretely by dropping the closing `~~` of a strikethrough span in a `Done` feature's description, flipping a well-formed italic cell into an entity row. Mitigation: apply the same usability test to the description -- fall back to the placeholder (or prefix-escape) when the derived text starts with `_` or contains `|`, and re-check the derived text after truncation, not before.

5. **Diagnostics interpolate unbounded, uncontrolled label text into stderr**: Low -- The warning shape embeds `f.label` raw and unbounded. `parse_features` cannot put a `\n` in a label (`scan_body`/`split_lines` in `frontmatter.rs:291,311` split on `\n` and strip a trailing `\r`), but an *interior* `\r` survives, as do tabs and C0 controls including `ESC`. A `\r` returns the cursor to column zero and overwrites the emitted warning; an `ESC[` sequence reaches the author's terminal directly. Length is also unbounded -- a CR-only-line-ending document parses as a single line, so the label absorbs the rest of the file and the diagnostic prints it in full. Nothing confidential leaks (the label is in-repo content the author is looking at), so this is log forging and terminal escape injection, not disclosure. Mitigation: render the label in the diagnostic through the bounded, sanitizing path the diagram already uses -- `truncate_label`-style char bound plus dropping/escaping C0 controls.

6. **The security invariant's test does not cover the path the change creates**: Low -- The design says the `Safe; rm -rf /tmp/nonexistent && echo HIJACKED` test "is unchanged and still covers the path." That test (`crates/shirabe/tests/populate_cli.rs:350`) runs `--dry-run` in issue-creating mode. Issueless mode has no CLI-level test at all today, and the label reaching the key column there is new. Mitigation: add the same fixture under `--no-issues`, asserting both the verbatim round-trip and a clean `shirabe validate` on the result.

7. **Two pre-existing surfaces the section's "no new" verdict passes over without naming**: Low (informational, unchanged by this design) -- (a) `atomic_write` creates the temp sibling with `fs::File::create` (`populate.rs:1048`), which follows symlinks and does not use `O_EXCL`, on a name derived from pid and clock; in a directory an attacker can write to, the "atomic write" the module lists as a security invariant can be redirected. (b) `--milestone` is interpolated verbatim into the reserved section body and `--repo` into the rendered issue-link URL, neither validated; a milestone containing a `## ` line would corrupt the section structure the *next* `replace_section` run depends on. Both are operator-supplied and out of scope for this change, but a Security Considerations section that concludes "no new untrusted-input path" should say the CLI-argument surface was examined and found unchanged, rather than being silent about it.

## Claims Verified

- "`gh` arguments go through `Command::arg` ... no shell, no string templating" -- **true** (`populate.rs:475-484`; `gh_repo_owner_repo` uses `.args` with fixed literals).
- "Nothing in this change adds a subprocess invocation or moves label text closer to one" -- **true**.
- "The issueless path constructs no `Command` at all" -- **true**; `run_inner` returns into `run_issueless` at `populate.rs:120` before `obtain_mapping` and `resolve_owner_repo`.
- "The changed functions are pure string builders" -- **true** as specified (B3 keeps IO in the run paths).
- "The key is either the label with decoration stripped ... or `F<n>`; no escaping, quoting, or character rewriting is introduced" -- **true**.
- "The existing `HIJACKED` test is unchanged and still covers the path" -- **misleading**; it covers issue-creating mode only, not the new issueless key path (finding 6).
- "No author input reaches the output through a new path" -- **false as worded**; label text reaching the issueless key column and Dependencies cells *is* a new path in that mode. The defensible claim is that it is no new *class* of exposure, since issue-creating mode already renders labels there.
- "`F<n>` is derived from the feature's position, not its text" -- **true**.
- "A body containing `|` still breaks the row ... a rendering defect, not a privilege boundary" -- **true but incomplete**; it is not a privilege boundary, but it is the same self-invalidating-output defect being fixed, and the design does not justify falling back on a pipe in a label while accepting one in a body (finding 4).
- "The bound narrows the surface rather than widening it" -- **mostly true**; truncation can introduce unbalanced markup that the full text did not have (finding 4).
- "Counting is `chars().count()` ... a multi-byte character is never split" -- **true**; note it can still split a grapheme cluster or leave a bidi control unterminated, which is cosmetic-to-confusing rather than exploitable here.
- "`feature_keys` adds an O(n^2) duplicate scan ... 441 comparisons" -- **true**, negligible.
- "The duplicate comparison is the same equality FC06 applies" -- **false** (finding 2).
- "No new file write" -- **true**; the write path (two `replace_section` calls plus the optional output map) is untouched.
- "No new parsing of untrusted input" -- **false**; `key_fallback_reason` inspects label content and, per the Components table, an author-controlled `Feature N` integer becomes a slice index (finding 1).
- "The existing verbatim invariant is preserved by construction" -- **true at the string level**, but string identity is not key identity to the validator (finding 2).
- "A roadmap can never fall back silently or warn about a row that did not" (Mitigations) -- **false in issue-creating mode** (finding 3).

## Summary

The subprocess and write-path reasoning is sound and I verified it against the source: issueless mode constructs no `Command`, the `gh` argv path is untouched, the atomic write is unchanged, and the 200-character bound is a real reduction in a previously unbounded copy of author text. Where the section is weak is in treating "the label is not transformed" as the whole invariant. The property that actually matters is that the string the key column emits and the string the dependency cell emits normalize to the same key *inside the validator*, and the enumerated characters -- comma, pipe, empty, duplicate -- do not cover the normalizations `extract_entity_key` and `extract_deps` apply, so `~~`, `#<digits>`, and `](` in a label produce FC06 errors or silently merged keys on the tool's own output. Newlines are not reachable in a label (the body is split on `\n` before parsing), but interior `\r`, tabs, and C0 controls are, which matters for the unbounded stderr diagnostics rather than for the table. The blocking item is finding 1: the design's own Components table specifies `keys[id-1]`, which converts a `Feature 0` or a stale out-of-range `Feature N` reference into a panic in a module documented as total over arbitrary input.
