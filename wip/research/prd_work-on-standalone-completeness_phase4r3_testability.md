# Testability Review (round 3): PRD-work-on-standalone-completeness

## Verdict

FAIL

## The new R19 family — falsifiability

**R19's first bullet** ("every terminal tick this feature introduces retains its context record when a root session runs it") is sound. The retention mechanism this PRD is describing is real and concrete in the koto engine: `finish_terminal_tick` in `koto/src/cli/mod.rs` takes a `no_cleanup: bool` and, when true, returns before `append_request_store_result_to_child`, `append_terminal_index_for_session`, and `append_child_completed_to_parent` all run — i.e. before any of the three durable records of completion are written. A tester can drive each new terminal state as a root session and check the record survives. Constructible.

**R19's second bullet** ("a child session running the same states does NOT request retention, and its parent's child-completion gate still converges... demonstrated by running a parent to convergence over a child that reaches one of the new terminal states") is also constructible — koto already has the machinery (`ChildCompleted` event, `children-complete` gate, `RequestStoreResult`) this exercises, and the scenario is exactly what would expose the bug the PRD's own rationale describes (retention suppressing both of the gate's read sources). But the criterion only demands the demonstration for "one of the new terminal states," not all of them. If this feature introduces more than one new terminal tick, a per-state regression in the root/child discriminator on any tick but the one chosen for the demo passes silently. That is a real, if narrow, coverage gap — not a "does this catch a wrong implementation" failure on the demonstrated state, but an incomplete quantifier.

**R19a** ("a regression test fails if the retention behaviour is made unconditional") is not circular. It is not "a test asserting a test exists" — it is a mutation-style check: identify the guard that makes retention root-only, invert it, and confirm the new test then fails. That is mechanically executable once an implementation exists. The residual weakness is that neither R19a nor its acceptance criterion names *what* "unconditional" refers to (a flag, a template conditional, a function argument) — reasonable to leave open at PRD altitude, but it means the check's precision depends entirely on whoever writes the test choosing the same guard a reviewer would expect. Acceptable, not ideal.

**R19b** ("the root-only mechanism used is the one established by the separately landing fix, not a second implementation of the same idea") is the weak link, and it fails for two independent reasons, not one:

1. **No concrete anchor for "same mechanism."** R5a's parallel criterion turns an abstract dependency-direction principle into a grep-able check ("does not reference any path under the plan entry point's directory"). R19b has no equivalent: no named function, module, flag, or file path a tester can diff against. "Not a second implementation of the same idea" is exactly the kind of judgment call the format spec's Acceptance Criteria guidance ("binary pass/fail — no subjective judgment") warns against. Two reviewers looking at the same two diffs could genuinely disagree about whether they're "the same mechanism" or two mechanisms that happen to produce the same effect.

2. **The referenced work does not (yet) establish what R19b assumes it establishes.** I traced the "separately-filed defect covering today's terminal ticks" to issue #360 ("work-on and execute don't pass --no-cleanup, so a blocked run loses its context record"). Its own suggested scope is to pass `--no-cleanup` **unconditionally** on `/work-on`'s terminal ticks, modeled explicitly on `/scope`'s pattern, which "retains unconditionally." Nothing in issue #360 as filed conditions retention on root-vs-child. Since `/work-on`'s koto template is also the child-materialization target (the same fact this PRD's own rationale leans on for R19/R10), an unconditional implementation of issue #360 would retain context for every child too — reproducing the exact wedge this PRD's R19 exists to prevent. R19b's premise — that #360 "establishes the root-only mechanism" — is not yet true of the thing it points at. A tester encountering this at verification time has no defined fallback: the PRD doesn't say what happens if the separately-landing fix lands looking like its own filed AC (unconditional) rather than like what R19b assumes.

**Ordering dependence (R19b specifically).** The PRD states the dependency ("lands before this work") but gives no protocol for a tester who reaches this criterion before the other work has landed, and no protocol for what "reuse" means if that work's actual shape diverges from a root-only mechanism (as issue #360's current text does). Compare to R19 itself (previous draft, reviewed last round), which pinned ordering cleanly because the compared artifact's *shape* was not in question. Here both the ordering and the shape of what's being reused are open.

**R16 is under-covered.** No acceptance criterion verifies that a routing claim's file was actually edited to say what the inventory's "new text" column promised — AC15 (R16a) only requires the inventory to *record* prior/new text pairs, and AC16 (R16b) only requires the candidate-generating command to be re-runnable with no unlisted hit. Neither closes the loop back to the source files for the non-eval claims (README.md, the pipeline-model reference, and whatever else the inventory names). R17 closes this loop only for the three eval scenarios. An implementation that produces a perfect, honest inventory and then only applies half of its "new text" entries would pass every listed criterion for R16's family while leaving R16 itself — "every routing claim... SHALL be updated" — unmet.

**R8 is verified for presence, not correctness.** The acceptance criterion for R8 confirms every obligation has exactly one classification (gate-enforced or evidence-carried); it does not check that the classification chosen is the one R6/R7's own definitions require (observable-from-`gh`/git → gate; irreducible judgment call → evidence). An obligation that is mechanically observable but classified as evidence-carried instead — weaker enforcement, dressed as compliance — would pass AC6 (table complete), AC8 (its evidence field is well-typed and rejects placeholders), and never be caught, because no criterion re-derives the classification independently and compares it to what's recorded.

No other requirement (R1–R22, including R5a, R7a, R16a, R16b, R19, R19a, R19b) is an orphan in the strict presence sense — each has at least one tagged acceptance criterion.

## Required changes

1. **R19b needs a concrete comparison target.** Name what "the mechanism" is at a level a tester can diff against without judgment — e.g. "the same conditional expression / helper / flag introduced by [the separately-landing fix], referenced or called from here rather than reimplemented" — mirroring how R5a turned a dependency-direction principle into a grep check. Absent that, add an explicit fallback for the case (which the current state of the referenced fix suggests is live) where the separately-landing work does not itself land root-only: state whether this feature's requirement to reuse "the root-only mechanism" is void if that mechanism doesn't exist yet, and what a tester does in that case.
2. **Close R16's execution gap.** Add a criterion (or extend R16a's/R16b's acceptance criteria) verifying that, for a sample or for all non-eval routing claims in the inventory, the file at the recorded line now reads the recorded "new text" — not just that the inventory says it should.
3. **Close R8's correctness gap**, or explicitly accept it as a Known Limitation the way R7a's own residue already is. Either add a criterion that independently re-derives each obligation's classification from R6/R7's own tests and compares it to the table, or add one sentence to Known Limitations naming this specific residue (the document already does this pattern for the general classification-is-a-judgment concern; this is a sharper, checkable instance of it that the current Known Limitations paragraph doesn't name).
4. **R19's second bullet**: either require the parent-convergence demonstration for every new terminal tick this feature introduces (not "one of the new terminal states"), or explicitly scope it down with a stated reason (e.g., "all new terminal ticks share one code path, so one representative demonstration suffices") so a reviewer isn't left to guess whether partial coverage was a deliberate call.

## Observations

The R19 rewrite is a substantial improvement in specificity over the previous draft's "retain every terminal tick's context record" — it correctly narrows to root-only, adds a regression test, and its rationale (the retention flag suppresses the same two sources the parent's gate reads) checks out exactly against the koto engine's actual `finish_terminal_tick` code path. That part of the rewrite is sound. R19b is where the family breaks down: it was written to close an ordering/reuse concern honestly, but it does so by naming a constraint ("reuse, don't reinvent") without giving a tester any fixed point to check reuse against, and the specific fix it's pointing at (issue #360) currently describes exactly the unconditional pattern this feature's own rationale says is the trap. That's not a hypothetical edge case — it's the most likely way this dependency actually plays out unless someone updates issue #360 first.
