# Lead: What is the dependency-ordered, sized work list across both repos?

## Findings

### How I sized these

Every item below was already established by rounds 1-2; I read every r1/r2 file plus the exploration's own decisions log before sizing anything, then opened the specific files each item touches to pin down line numbers and confirm nothing had drifted since those rounds ran. Two things I found independently while doing that, not previously flagged by any lead:

1. **`src/session/local.rs:657-719` (`migrate_if_needed`) is the exact source of koto's ~106KB migration-warning spam**, and the root cause is a one-line consequence: when a session's flat-layout copy already exists (`dest.exists()`, line 691), the old-layout entry is *not* moved out of `old_dir`, so `old_dir` stays non-empty, so `fs::remove_dir(&old_dir)` at line 717 silently fails every time (`let _ = ...`), so the same ~1,250 warnings print again on the *next* invocation, forever. This is a five-minute read once you know where to look, and it fully explains the r2 probe's open question ("is the migration scan supposed to run on every invocation, or is it a first-run migration that never records completion?").
2. **Shirabe already has a "Current" design doc that deliberately rejected the epoch-scoping/context_assignments direction**: `docs/designs/current/DESIGN-work-on-retry-clearing.md` (status: Current, upstream `PRD-work-on-retry-clearing.md`). It's the design authority for the exact 8 retry-clearing blocks the transition-hooks lead flagged as the strongest "koto should just do this" candidate. It chose "remove the key on the retry path, verify with `koto context exists`, both signals must clear" as "the smallest change that holds," specifically because at the time `context_assignments` was unimplemented and the design explicitly reasons about why a uniform superset-clearing rule beats a mechanism scoped per-edge. No round-1 or round-2 lead cites this doc. It changes the shape of the "epoch-scope the context store" item from a clean win into a shirabe-side design reversal that has to be argued on its own terms, not just implemented once koto ships a primitive.

## Recommended sequence

**Wave 0 — land immediately, no dependencies, no design docs, pure defects/cleanup.** K1, K2, S2, S3, S4a, K10a. All six are independent of each other and of everything else in this list; K1 and K2 are the highest-priority items in the whole set because they're live bugs in mechanisms shirabe already ships and runs today (`tests_passing`'s `go test ./...` gate is one `go test` run away from a false 30-second "timed out" failure with the evidence destroyed) — this is true whether or not shirabe ever adopts `default_action` anywhere. S2/S3/S4a/K10a are one-file cleanups worth doing on their own merit.

**Wave 1 — parallel tracks, both starting after Wave 0's K1.** Track A: K5+K6 together (same lead's answer, same file family, small). Track B: S1a, the two koto-free `default_action` conversions with no context-store dependency (`pr_creation` existence check has zero koto-dependency at all and could even move into Wave 0; `orchestrator_setup`'s branch-decision block similarly). Track C: K8's design doc — start writing this in Wave 0/1 in parallel with everything else, since it has no code dependency on K1 through K7 and answers the user's "hard guards" ask directly; it's large enough (new on-disk field, new CLI verb, backward-compat call) that starting the design conversation early is itself valuable, independent of when the implementation lands.

**Wave 2 — after K1+K2 both land.** S1b (extract-context.sh and the plan_context_injection fetch — both nest a `koto context add`, both were the exact call shapes the probe traced). S5 (tests_passing's guard — a smarter/broader command is more likely to cross 64KB, so re-authoring it before the drain fix just moves the false-failure risk instead of removing it).

**Wave 3 — after K5+K6 land.** Extend S1 to any state where "the gate failed" alone isn't a good enough failure signal for the agent to act on — which per the counter-case lead is most side-effecting conversions (branch creation, PR edits). Before K5, converting those states to `default_action` trades a debuggable agent-run command for an opaque gate-exit-code; after K5, the agent gets the action's own stdout/stderr on the failure path, which is the actual value proposition.

**Wave 4 — K7, after its short design note.** The design note should be quick (two narrow open questions, not a full architecture debate) but shouldn't be skipped — the same-tick staleness trap is exactly the kind of thing that looks done and isn't, per the output-routing lead's own account of nearly missing it. Once K7 ships, the settled-branch-record block (execute.md's most fragile hand-authored shell, with a filed incident behind it) becomes the highest-value single conversion in the whole exploration: it's currently defended by more prose explaining why it's fragile than the script itself, which is precisely what a compile-time-validated capture is supposed to make unnecessary.

**Wave 5 — K8's implementation**, once its design doc resolves the three open questions (default-anchor behavior, pre-existing-session migration behavior, equality-vs-containment). Bundle K9 into this PR rather than shipping it separately — a containment violation is the first real user of a structured spawn/containment error type.

**Deferred, pending an explicit decision — not scheduled into a wave.** K3/S4b. This is the one item where "should wait for evidence" applies literally: the koto engine work (K3) is well-scoped and small, but it does not by itself retire anything in shirabe, because shirabe already has a Current, deliberately-reasoned design doc (`DESIGN-work-on-retry-clearing.md`) that chose a different mechanism and explicitly argued why a uniform manual-clear-and-verify rule beats a per-edge or automatic one. Before anyone picks up K3, someone needs to either (a) write a short shirabe design note that revisits that doc's decision and states why epoch-scoped/assignment-based clearing is now worth the switch, given the map-work-on lead's finding that the *current* manual blocks have their own real bug (a nested `koto next --with-data` inside a retry block leaves the outer call reporting a stale result), or (b) decide the current mechanism's flaw is worth fixing in place instead, and drop this item from the roadmap entirely. Either answer is legitimate; picking neither and just implementing K3 "because koto issue #204 exists" would ship an engine feature shirabe's own design record already argued against once.

**K10b** sits at the end deliberately — write it once, after K5/K6/K7 ship, so it documents the schema that actually exists rather than repeating the exact doc-vs-runtime drift r1 already found once between koto-author and koto-user.

### Worth doing regardless of whether shirabe ever adopts `default_action`

K1, K2, K8/K9 (anchoring guards gates too, not just actions — every `type: command` gate in every shirabe template already runs against the unguarded `current_dir`), S2, S3, S4a, S5, K10a. None of these depend on shirabe converting a single state to `default_action`; all seven have standalone value as defect fixes or as the safety guard the user explicitly asked for. Everything else on this list (K3/K5/K6/K7/K10b/S1/S4b) only pays off in proportion to how much of `/execute` and `/work-on` actually gets converted.

## Implications

The two corrections found in this round change the shape of the recommendation more than any new sizing detail does. First, the pipe-buffer deadlock (K1) isn't a prerequisite for `default_action` adoption in the abstract — it's a live defect in gates shirabe ships today, which means the honest sequencing starts with "fix what's already broken" rather than "prepare for a new capability." Second, the retry-clearing item can't be scheduled as a normal dependency chain (koto ships primitive → shirabe adopts it) because shirabe already made and recorded a different choice for the same problem; treating K3 as just another koto feature request undersells that a real design conversation has to happen on the shirabe side first, one that argues against an existing "Current" document rather than filling a gap.

Separately, the sequencing surfaces that K8 (anchoring) doesn't actually depend on anything else in this list and answers the user's stated ask most directly — it would be a mistake to schedule it last just because it's the largest item. Starting its design doc in parallel with Wave 0/1 costs nothing and the eventual implementation is independent of how far `default_action` adoption goes.

## Surprises

- `migrate_if_needed`'s bug is almost embarrassingly small once traced to source — a `let _ = fs::remove_dir(&old_dir)` that was always going to fail silently on the "skip" branch, since the skip branch by construction leaves `old_dir` non-empty. Neither round flagged the exact line; the r2 probe's own open question ("is the migration scan supposed to run on every invocation...") is answered by five lines of code.
- `DESIGN-work-on-retry-clearing.md` existing at all, unreferenced by any prior lead, changes K3 from "the strongest candidate found so far for koto should just do this" (the transition-hooks lead's own words) into the one item on this list that needs a human decision before any code gets written, on either side of the repo boundary.
- Sizing K8 last in the candidate list undersold it — reading `src/cli/mod.rs` directly confirms the guard genuinely lives at one choke point (`handle_next`, before `current_dir` feeds either closure), which is a structurally clean insertion point for a large-sounding feature. The size is in the design questions (migration, defaults), not in the code's blast radius.

## Open Questions

- Who owns the shirabe-side decision on `DESIGN-work-on-retry-clearing.md` — does it get revisited as part of this exploration's own follow-up plan, or does it wait for someone to hit the outer-invocation-stale-result bug the map-work-on lead already reproduced and file it as its own defect first?
- Should K9 (structured spawn/containment errors) ship as a narrow standalone fix ahead of K8, given it has independent value for any spawn failure (not just containment violations) and doesn't need K8's design questions resolved first? I sized it bundled with K8 as the cleaner PR boundary, but a case exists for pulling the generic spawn-error part out earlier.
- K10b's exact home — extending `template-format.md`'s existing Layer 1-3 structure, or a new layer, since `default_action` changes engine behavior (auto-execution) rather than being a routing primitive like gates — was flagged as open by the authoring lead in round 1 and nothing in round 2 or this round resolved it; whoever writes K10b will need to make that call.

## Summary

Two items land before anything else because they're already broken, not because they gate a future feature: the `run_shell_command` pipe-buffer deadlock and koto's own migration-warning spam, both one-file fixes with no design doc needed, both undercutting gates shirabe ships today. The rest sequences into small koto plumbing fixes (action_output on failure, no-gate failure detection) that make the three-path pattern actually diagnosable, two koto features that need short design notes first (`capture_stdout_as`, execution anchoring — the latter answering the user's "hard guards" ask directly and independent of `default_action` adoption entirely), and one item — making `context_assignments` real — that can't be scheduled as a simple dependency chain because shirabe's own `DESIGN-work-on-retry-clearing.md` already chose a different, reasoned answer to the same problem and needs to be explicitly revisited, not quietly superseded.
