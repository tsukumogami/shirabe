# PRD: Offline Ablation for Withheld Instruction Sections

## Status

Done

The completeness, clarity and testability reviewers passed it on a third
round. The downstream DESIGN owns the approach.

Absorbed [BRIEF-offload-offline-ablation](docs/briefs/BRIEF-offload-offline-ablation.md); carried in Absorbed Brief.

## Absorbed Brief

The feature exists so that withholding an instruction section is measured
before it's done for real, instead of argued about and then discovered in
real runs that already paid for any mistake. The brief framed that as five
gaps in the eval harness, which this document's Problem Statement states in
full: no way to run a skill with a section missing without editing shipped
files, grading by a judge rather than the check a withheld section would
rely on, no per-run token figures to set beside the baseline, a without-skill
arm thrown away ungraded, and nothing watching the rules nobody targets.

The outcome it asked for is that a maintainer about to withhold a section
sees how agents behave without it, judged the way production would judge
them and on the same footing as the pinned baseline, and learns what the run
count can't tell before treating "no difference seen" as "safe". Those are
this document's Goals and Decision Thresholds, and the four people it
imagined (a maintainer measuring a section, a reviewer re-deriving a result,
an analyst excluding fixture runs, a process owner checking erosion in other
rules) are its User Stories.

Its boundary held the feature to measuring inside eval runs, one
demonstration on a small script-checked section, and nothing a normal run
loads; the full study, a rule registry, a live canary, guard rules for
irreversible actions and the provisional definitions stayed out. Those are
this document's Out of Scope.

## Problem Statement

A run of `/work-on`, `/execute`, `/scope` or `/deliver` loads its `SKILL.md`,
the koto directives for the states it visits, and the references those name.
The baseline pinned at commit `2a3719e` in `docs/measurement/offload-baseline/`
counts that load per profile (36,789 weighted tokens for `work-on`) and
defines, as `provisional-1`, how often a rule is broken while it's preloaded.
Its counterpart, the rate for a withheld rule observed after the rule's text
has been delivered once, is named there and left for later work.

The later work is withholding: taking a section out of what every run loads
and delivering it only when the check that guards it fails. Each such change
has to show, before it ships, that agents without the section don't break its
rule more often than the tokens saved are worth. shirabe can't show that
today. `scripts/run-evals.sh` runs a skill as shipped; its only grader is the
`/skill-creator` session judging each scenario's expectations; it throws away
the without-skill arm it already pays for; and every arm runs as a subagent of
one grading session, so no arm's tokens can be told apart. And nothing samples
the rules nobody targets, so a withholding that looks free on its own rule
could erode a neighbouring one unseen.

## Goals

- A withholding decision can be measured offline, before any user's run is
  affected, on the same rule keys and definitions as the pinned baseline.
- The measurement is graded the way production would grade it: by the
  section's deployed check.
- The result says what its run count can and can't decide, so an
  underpowered result is never read as permission.
- The capability is proven once, end to end, on a real section with a real
  check, and every number it reports regenerates from committed files.

## Definitions

Terms the baseline defines (rule key, opportunity, production, violation,
observation point, numerator, denominator, attribute names) keep its
`provisional-1` meaning. This PRD adds:

- **Arm.** One way of running a scenario: `full` (the skill as shipped),
  `withheld` (the skill with one section removed), or `without_skill` (no
  skill loaded).
- **Run.** One arm of one repetition: one model session. Each run has its own
  session, so its token usage is its own.
- **Deployed check.** The script that would guard the section once it's
  withheld. Given one production (for the demonstration, the evidence a run
  submits to a koto state), it reports `complied`, `violated` or
  `not-checkable` for the section's rule, with a failure message on
  `violated` that contains the section's text.
- **Delivery.** The harness intercepts each production at the moment the run
  makes it, before it reaches koto, and runs the deployed check on it. The
  first time a production violates, the harness refuses it and returns the
  check's failure message to the agent as the tool's error output, the way a
  gate refusing evidence would, so the workflow doesn't move on. That is the
  one delivery a run gets. Every other production is passed through to koto
  unchanged. It's harness-driven; no koto template or gate changes.
- **Second observation point.** The next production of the same output in
  the same session after the delivery. A run whose first production complied
  or wasn't checkable is never delivered to, and its second point is
  `not-reached`. A delivered run that ends without producing again records
  `not-produced` at the second point; by the baseline's early-ending rule it
  contributes no opportunity there, and the summary reports how many such
  runs each arm had beside the second point's rate.
- **Audit rule.** A rule other than the withheld section's, with its own
  script check, that nothing checks in a normal run. A scenario declares its
  audit pool.
- **Ablation fixture.** A koto session created by an ablation run. Its
  template is loaded from a scratch copy of the plugin tree, never from a
  checkout or an installed plugin.

## User Stories

- As a maintainer preparing a feature that withholds a section, I want to
  run the scenario with and without the section and see the violation rate
  and token saving per arm, so that I decide on evidence instead of argument.
- As a check author, I want one documented contract for what a deployed
  check receives and returns, so that the check I write for a section can
  grade its ablation and later guard its withholding unchanged.
- As a reviewer of a pull request that cites an ablation, I want to
  regenerate its figures from committed files with one command, so that I
  can trust the numbers without re-running model sessions.
- As an analyst computing the preloaded rate from real sessions, I want
  ablation sessions to be recognisable from their koto session record, so
  that I can exclude them from a real-run population.
- As a process owner approving a withholding, I want to see whether rules
  nobody targeted eroded in the same runs, so that a withholding that looks
  free on its own rule can't hide a cost elsewhere.

## Requirements

### Functional

- **R1. Variant switch.** The eval runner takes a withheld-section selector
  naming one section by the baseline's rule key, a `<path>#L<start>-L<end>`
  or `<path>#<heading text>` location plus its source commit, and a
  repetition count. For each run it copies the whole plugin tree (`skills/`,
  `references/`, `scripts/`, `.claude-plugin/`) at the working tree into
  scratch space, removes the section from the `withheld` arm's copy, and loads
  only that copy into the arm's model session. The files under `skills/` and
  `references/` in the repository are byte-identical before and after the run.
- **R2. Span resolution.** A line-range key names lines `start` through `end`
  inclusive of the file at the source commit. A heading key names the heading
  line through the line before the next heading of the same or a higher level,
  at the source commit. The runner reads that text from the source commit and
  requires it to occur exactly once, byte for byte, in the file of the tree
  being run; the removal deletes exactly those bytes. A malformed key, an
  unknown commit, a missing file, or a span found zero or several times
  refuses the run before any session starts, with a message naming the key
  and which of those it was.
- **R3. Arms.** Each repetition runs the three arms from the same scenario
  setup. The `full` and `withheld` arms get the same prompt text; the
  `without_skill` arm gets the scenario's own prompt for it, since it has no
  skill to invoke, and the summary shows both. The `full` and `without_skill` arms also
  load their koto template from a scratch copy, so every arm's koto session
  is an ablation fixture.
- **R4. Deployed-check grading.** Each arm is graded by the deployed check
  the scenario declares for the section, invoked by the harness, never by an
  LLM. A record's `observed_by` is `script`. A check that exits with anything
  other than its three documented outcomes, or doesn't finish within the
  scenario's time limit, records `not-checkable` with the reason, and the run
  continues.
- **R5. Observation points.** Every run records its first observation point,
  and the second as defined above. The same delivery applies to all three
  arms: in `full` the section was also preloaded, in `without_skill` nothing
  was. A run that never makes the production records `not-produced` at the
  first point and is excluded from the denominator, as the baseline's
  early-ending rule says.
- **R6. Token capture.** Each run records its input, cache-read,
  cache-creation and output tokens as summed from its own model session's
  usage records. It also records: static instruction tokens, computed by
  running the baseline's `count` method over the arm's plugin copy for the
  skill's profile (raw and weighted; 0 for `without_skill`, which loads no
  plugin); observed instruction tokens, the bytes of plugin files the session
  actually read plus the skill body it was given, divided by 4; the observed
  instruction tokens loaded before the first koto directive; and total tokens
  per koto state, attributing each model turn to the state the last
  `koto next` returned.
- **R7. Audit sampling.** Each run evaluates audit rules drawn from the
  scenario's audit pool at the sampling rate the design states, using the
  same sample for all three arms of a repetition. Audit outcomes are recorded
  beside the withheld section's.
- **R8. Result record.** Each run appends one JSON record carrying the
  baseline's attribute names (`definition.version`, `rule.source`,
  `rule.source_commit`, `skill`, `template.path`, `template.git_blob`,
  `template.koto_hash`, `state`, `run.id`, `opportunity.index`,
  `opportunity.outcome`, `observed_by`) for each observation, plus the arm,
  the repetition, the observation point, the koto version, the token figures
  and the audit outcomes. The `without_skill` arm carries the same keys; its
  koto fields describe the fixture session it drove.
- **R9. Fixture marking.** A documented rule, in the measurement directory's
  README, classifies a koto session as an ablation fixture from its recorded
  template source directory alone, including when its template hash equals a
  pinned one. Every session an ablation creates matches the rule, and a
  session started from an installed plugin or a checkout doesn't.
- **R10. Summary.** A summary command reads committed run records and prints,
  per arm and observation point: violations, checkable denominator,
  not-checkable count, rate, and the exact (Clopper-Pearson) two-sided 95%
  upper bound; the mean token figures and their difference from the `full`
  arm; the static raw and weighted instruction tokens beside the pinned
  baseline's figure for the same profile; per audit rule, the `withheld`
  arm's rate minus the `full` arm's in percentage points; and the smallest
  uplift distinguishable from zero at the run count, as defined under
  Decision thresholds. It prints the decisions the result can and can't
  support by that table. An arm with no checkable run prints `n/a` for its
  rate and bound.
- **R11. Regeneration.** One committed command regenerates every figure the
  demonstration reports from committed files, without a model session, and
  exits non-zero, naming the figure, when a committed figure differs from
  what it computes. CI runs it on every pull request that touches the
  ablation files.
- **R12. Demonstration.** The demonstration withholds
  `skills/work-on/references/phases/phase-2-introspection.md#L20-L24` at
  `2a3719e` (257 bytes, the only statement of what `/work-on`'s
  introspection state submits). Its scenario starts each arm at the
  `introspection` state of a real `/work-on` koto session against a fixture
  issue whose approach has changed. Its deployed check judges the evidence
  the run submits to that state. It runs 2 repetitions of the three arms,
  the minimum that proves the path end to end on real sessions, and commits
  the records, the summary and the spend. A demonstration that happens to
  see no violation reports that and still stands; the violation and delivery
  paths are proven by tests with a stub agent.
- **R13. Check contract.** A deployed check and an audit check share one
  documented contract: an executable that exits 0 for `complied`, 1 for
  `violated`, 2 for `not-checkable`, prints a one-line reason, and on
  `violated` prints the failure message to deliver. A deployed check is
  given one production; an audit check is given the finished run's record of
  koto calls and koto session. The design fixes how each receives its input.

### Non-functional

- **R14. Normal runs unchanged.** No file listed in
  `docs/measurement/offload-baseline/load-manifest.tsv` changes, and no koto
  template changes. New checks and harness code live outside `skills/` and
  `references/`.
- **R15. Existing evals unchanged.** Without the selector,
  `scripts/run-evals.sh` runs the same code path as before this feature, and
  its existing test script passes unchanged.
- **R16. Public content.** Nothing committed or in the pull request contains
  a local home-directory path, a session, instance or job identifier, a
  `wip/` path, a private repository's name, or the name of an external
  telemetry vendor.

## Decision Thresholds

These come from the program this feature serves and are what the summary
judges a result against.

| What is withheld | Break-even uplift | Where a violation forces a scrutiny re-run |
|------------------|-------------------|--------------------------------------------|
| A single rule | about 1.5 to 3 points | about 0.3 to 0.6 points |
| A 4 KB section | about 10 to 20 points | about 2 to 4 points |
| A 16 KB reference | about 40 to 90 points | about 8 to 18 points |

A section takes the row its byte size is nearest: under 1 KB is a single
rule, 1 KB to 8 KB the 4 KB row, over 8 KB the 16 KB row.

- **Section decision rule.** 15 to 30 runs of the `withheld` arm, deciding on
  zero violations after at most one delivery: the second observation point
  where a delivery happened, the first where none was needed.
- **Audit bar.** At least 30 runs per workflow; an audit rule whose
  `withheld` rate exceeds its `full` rate by more than 5 points fails the
  withholding.
- **Detection limit.** The smallest uplift distinguishable from zero at `n`
  runs per arm is `k/n`, for the smallest `k` at which `k` violations in
  `withheld` against 0 in `full` gives a one-sided Fisher exact p below 0.05.
  At 30 runs per arm that is 5 of 30, about 17 points. Single-rule thresholds
  are far below that, so no offline run count here can show a single rule is
  safe to withhold; those decisions need the zero-violation rule over many
  runs or a later live canary. "No difference seen" at such a count is never
  evidence that withholding is safe.

## Acceptance Criteria

- [ ] With a line-range selector and with a heading selector, the runner
  removes exactly the named bytes from the `withheld` arm's plugin copy, and
  `git status --porcelain -- skills references` is empty after the run.
- [ ] A malformed key, an unknown commit, a missing file, a span not found,
  and a span found twice each refuse before any model session starts, and the
  message names the key and the reason.
- [ ] Each repetition produces one record per arm from the same scenario
  setup, the `full` and `withheld` arms from the same prompt, and every
  record's `observed_by` is `script`.
- [ ] A check that exits outside 0, 1 and 2, or exceeds the time limit,
  yields `not-checkable` with a reason, and the run's other records are
  written.
- [ ] With a stub agent that submits a violating production and then a
  compliant one, the first submission is refused with the check's failure
  message, never reaches koto, and the record shows `violated` then
  `complied`; with one that submits a compliant production first, the second
  point is `not-reached`; with one that stops after the refusal, the second
  point is `not-produced`, is left out of that point's denominator, and is
  counted in the summary's not-produced figure.
- [ ] Each record carries the token figures R6 lists; the `withheld` arm's
  static raw instruction tokens equal `round((B - S) / 4)`, where `B` is the
  profile's raw byte total over the `full` arm's copy and `S` the span's
  bytes; the `without_skill` arm's are 0.
- [ ] Each record carries audit outcomes for the sampled rules, all three
  arms of a repetition carry the same sample, and the design states the
  sampling rate.
- [ ] Each record carries every attribute R8 lists.
- [ ] Every koto session the demonstration created is classified as a
  fixture by the documented rule, and the rule classifies a session started
  from the installed plugin as not a fixture, including one with the same
  template hash.
- [ ] Over committed fixture records with known counts, the summary prints
  the expected rates, Clopper-Pearson bounds, token deltas, audit erosion,
  detection limit, and `n/a` for an arm with no checkable run.
- [ ] The summary names the thresholds row the section falls in, says
  whether the detection limit at the run count is below that row's
  break-even uplift, and, when it isn't, prints that the result can't
  support withholding the section and names the zero-violation rule or a
  live canary as what can.
- [ ] A scenario with an empty audit pool runs, and the summary prints that
  no audit rules were sampled.
- [ ] The regeneration command reproduces every committed demonstration
  figure, and exits non-zero naming the figure after one figure is edited.
- [ ] The demonstration's records and summary for 2 repetitions of three arms
  on the introspection-evidence section are committed, with its spend.
- [ ] No file in the baseline's load manifest and no koto template differs
  from `main`, and `scripts/run-evals_test.sh` passes unchanged.
- [ ] A grep of the pull request's diff and body finds no home-directory
  path, session, instance or job identifier, `wip/` path, private repository
  name or telemetry vendor name.
- [ ] The pull request is open against `main` with every CI job green.

## Out of Scope

- Withholding any section from a normal run, including behind a flag.
- The full ablation study across candidate sections; each later withholding
  feature runs its own at the decision rule's run count.
- A rule registry, new koto gates, or linter check states. Delivery in an
  ablation is the harness refusing a production at the tool boundary, not a
  koto gate or a template change.
- A live canary on real runs.
- Any section guarding an irreversible action (creating a pull request,
  pushing, merging, destroying a record) as a demonstration candidate.
- Changing the `provisional-1` definitions or the baseline figures.
- Replacing the LLM-judged grading of ordinary evals, or grading their
  without-skill arm.
- Running ablations in CI; they cost model sessions and run on demand.

## Decisions and Trade-offs

- **Demonstration run count.** The brief left open how many runs the
  demonstration pays for. It runs 2 repetitions, the minimum that proves
  the path end to end on real sessions, because usage had to come down; at 2
  runs per arm no uplift at all is distinguishable from zero, and the
  summary says so. Larger counts (15 to 30 runs per arm, 30 per workflow for
  audits) are what a later withholding feature runs for its own decision,
  not something this feature runs.
- **Demonstration section.** The introspection-evidence section is small,
  guards nothing irreversible, and its rule is fully judgeable from the
  structured evidence a run submits to koto, so a script can grade it. koto
  already refuses an evidence value outside the enum, which leaves the
  section's remaining content, the rationale an `approach_updated` verdict
  must describe, as what the check measures.
- **Grade all three arms with one check.** Grading the without-skill arm with
  the same check costs nothing extra and turns a discarded run into a lower
  bound.
- **Delivery at the production, through the check's failure message.**
  Refusing the production when it's made and returning the check's failure
  output is what a deployed gate would do, so the second observation point
  measures production behaviour. Letting the workflow move on and delivering
  afterwards, or re-prompting with the whole section, would measure
  something else.
- **One session per run.** Running arms as separate sessions, instead of as
  subagents of one grading session, is what makes per-run tokens exact.

## Known Limitations

- At the run counts this feature can afford, an offline result can only rule
  out large effects. Single-rule withholding decisions stay with the
  zero-violation rule or a live canary.
- Each run is a full model session, so the demonstration's figures carry the
  variance of a 2-run sample.
- The fixture scenario starts at the introspection state; what a real run
  carries into that state from earlier ones isn't reproduced.
