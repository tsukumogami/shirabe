# PLAN: Coordinator successor dispatch with its role

## Status

Active

## Scope Summary

The design gives `skills/coordinate/scripts/dispatch-worker.sh` a fourth mode,
`--successor`, that a coordinator runs from the `wait` hub, or from
`rotation_end` at discipline scope, to start its own successor. The mode never
touches pick, so an owed verdict, a pause, a parked decision or an empty scope
can't stop it, while the worker path keeps every one of those refusals. It
builds the invocation from the run's own facts (`coord-log.sh run-facts` and
`vars`): `/shirabe:coordinate <ROADMAP> --role <role>` at roadmap scope and
`/shirabe:coordinate --discipline <name> --host <owner/repo> --role <role>` at
discipline scope, with the role read from the record's Run `role` row. A
script-only `successor` render field in `render-brief.sh` admits the
discipline shape, and `--role` moves after the scope group. A pending
successor is one Run row, `successor`, written `dispatching` before the launch
and `dispatched` or `dispatch-failed` after, refused a second time with exit
12, settled by reconcile, and cleared by the successor's own takeover or
rotation carry. A new exit 13 holds the handover while a decision arrival is
unrecorded.

The plan covers all of it, and all of it lands in tsukumogami/shirabe: no koto,
niwa or template structure change is needed, and the template stays at compat
2. Every acceptance criterion traces to a requirement in
`docs/prds/PRD-coordinate-successor-role.md`, named in parentheses. Nothing is
filed: the steps are the work items.

## Decomposition Strategy

Walking skeleton. Step 1 runs the whole handover at roadmap scope for a
manager on one real input, a run whose only open unit owes a verdict: the
coordinator's `successor_input.json`, the mode, the `successor` Run row, the
rendered brief, a stubbed niwa launch, and the successor's opener taking the
run over, clearing the row and reporting "Role: manager.". Step 2 opens the
discipline invocation and all four role and scope pairs. Every later step adds
one guarantee on top, named by what a coordinator sees.

The order is chosen so each step can land alone. Every way a successor can
start clears the row (the takeover in step 1, the rotation carry in step 3)
before step 4 starts refusing a second successor on it, so a carried row can't
block a rotation's own handover. Tests and docs go with the step whose
behaviour they cover; the coordinate skill's Roles section and the brief
template's `role` paragraph land with steps 1 and 2.

## Steps

### Step 1: a roadmap manager whose only open unit owes a verdict hands over to a successor that takes its run over as manager

**Goal**: A coordinator at the `wait` hub of a roadmap run hands over through `dispatch-worker.sh --session <run> --successor`, crossing the whole handover on one real input: a manager run whose only open unit is a milestone with its verdict owed. The mode reads no pick facts, builds `/shirabe:coordinate <ROADMAP> --role manager` from the run's own `ROADMAP` variable and Run `role` row, records the pending successor as a Run `successor` row around a stubbed niwa launch, and the successor's opener, started from the brief's tokens with `--dispatched-by`, takes the run over, clears that row and reports itself as a manager.

### Step 4: a second successor is refused while one is pending, and a re-run with the same topic confirms or re-launches it under the same row

**Goal**: A coordinator that already has a successor pending can't start a second one, and running the same dispatch again after a crash or a lost launch finishes the first instead of duplicating it. Under the run's lock, `dispatch-worker.sh --session <run> --successor` first settles the Run `successor` row with a new shared function, `dc_successor_settle <session> <root>` in `dispatch-common.sh`. A `dispatching` row whose session `niwa list` shows becomes `dispatched`. A `dispatched` row whose session a successfully read listing doesn't show becomes `stranded`. An unlisted `dispatching` row, and any row when the listing can't be read, stays as it is. Then, while the row reads `dispatching` or `dispatched` under another topic, the mode exits 12 naming the row's status and topic. A re-run with the row's own topic resumes that dispatch: a `dispatched` row is confirmed with no write or launch, and an unlisted `dispatching` row is re-launched under the same row with no second `dispatching` write. A `dispatch-failed` or `stranded` row frees the slot for a new topic, and the existing exits stay as they are: 3 for reusing that row's topic, 5 for a topic a live session uses. A `dispatched` confirm write that the record refuses because a takeover fenced the run is a success: the mode prints `session=<name>` and `taken_over=<successor run>` and exits 0. Step 5 reuses the same settle function at reconcile. The settle and the exit-12 refusal run after `successor_input.json` is read and the lock is taken, and before the live-session check. That departs from the design's original order, which put them before the input read: the refusal compares the input's topic with the pending row's, so the input is read first, and an input error still exits 1 ahead of exit 12. The design's Amendments section records the change.

### Step 5: reconcile settles a pending successor row and the report names it with the command to run again

**Goal**: A coordinator that restarts with a successor pending sees the Run `successor` row settled before it acts, and its first report tells it what the row means and what to run. The record read (`reconcile-read.sh`) and the pass's one read in `reconcile-pass.sh` take the Run section beside their four, and the read's output gains `successor`: the row's value, or null. When that value reads `dispatching` or `dispatched`, the pass plans one more write, `reconcile-settle.sh --successor --session <run>`, in the same write class as the holding settle and the legs classification: it starts only when its whole budget of 20 s fits, never beside another write, and it's stopped and read again like any write. The new mode takes the run's successor lock, `.niwa/dispatch-briefs/.successor.<run>.lock` under `dc_workspace_root`, with the same noclobber create `dispatch-worker.sh` uses, and doesn't take over a held one. It then runs step 4's `dc_successor_settle <run> <root>`, so the rule is the dispatch's own: a listed `dispatching` row becomes `dispatched`, an unlisted `dispatched` row becomes `stranded` only after a listing that was read, and every other row stays. It prints one fact, `{kind: "successor", status: ok|not_verified, before, now, settled, session, reason, read_at}`, and exits 0 as every re-check does; a held lock, an unreadable listing (the function's 3), an unreadable row (2) and a refused write (the writer's code) are each `not_verified` with the reason and no write. The pass exit and its one line don't change, and neither does the reconcile gate's verdict: a pending row never makes the pass `blocked` or keeps it pending past the write's own reads, and a failed settle lands under "Not verified". `reconcile-report.sh` takes the fact as an optional `successor` input. A write is a change ("Changed since then"). While the row reads `dispatching` or `dispatched` after the pass, the report gains `successor: {row, status, topic, session, line}` and the text one `Successor pending:` line after the Scope line, built from the row as the settle left it, or as the record read found it when the settle didn't finish. A `stranded` or `dispatch-failed` row gets no line, since the slot is free.

Two follow-ups from step 4's review land here. The first is that the exit-12 message for a `dispatched` row could name an unreadable listing. For an unread listing, the point of the change, it prints ``the Run successor row reads `<row>`, but the listing couldn't be read, so whether its session is live isn't known; dispatch again once the listing reads, and the row settles first`` for either status. For a listed `dispatched` row it prints ``the Run successor row reads `<row>`, session `<session>` listed; a new successor can be dispatched once the row reads dispatch-failed or stranded``, and for an unlisted `dispatching` row ``the Run successor row reads `<row>`, its launch unconfirmed; to finish it, run `dispatch-worker.sh --session <run> --successor` again with successor_input.json naming `<topic>` ``. ### Step 6: a successor brief names its role only on its invocation line, and a handover waits while a decision arrival is unrecorded

**Goal**: A successor's brief names its role once, on its invocation line, whatever the coordinator wrote around it, and a handover never launches past a decision arrival the record hasn't taken yet.
