# PLAN: Decision Escalation Ladder

## Status

Active

## Scope Summary

A record-first escalation procedure. koto holds each question from the moment
it is raised to its answer, with a typed addressee, owner answers it has
verified, and reads that list what is open. shirabe gains a family of question
commands, a decide-first state in the worker templates, coordinator
enforcement in scripts, an undecided result from the decision skills, an
on-demand command and a guard on the question prompt. The work is dogfooded in
the tsukumogami organization before it is called done.

Steps 1 to 6 land in `tsukumogami/koto`. Steps 7 to 13 land in
`tsukumogami/shirabe`. Step 14 runs on released versions of both.

## Decomposition Strategy

Walking skeleton. Step 1 runs the whole life of a question inside koto on one
real input: one session raises a question addressed to `owner`, a read lists
it as open for `owner`, a second session records an answer aimed at it, the
open read no longer lists it, and the first session's next `koto next` reports
the answer. Every later step adds one behaviour on top of that path. First
come the rest of koto's rules: verification of the owner's answer, passing a
question up, precedence, precedent, retention. After a koto release comes what
shirabe builds on them: the question commands, the undecided decision, the
decide-first state, the coordinator's enforcement, the on-demand command. The
prompt guard needs nothing from koto and sits beside the koto steps. The last
step is the dogfooding run.

## Steps

### Step 1: A question raised in one session is listed as open for the owner, answered from another, and reported back to the asker

**Goal**: In the koto repository, cross the whole question path on one input: an `escalate` decision with the typed recipient `person:owner` recorded in session A is returned by a new open-by-person read, is answered by an `answer` entry recorded in an unrelated session B and aimed at A's question, stops reading as open, and is reported in a `questions` array on A's `koto next` until A records a decision citing the answer. koto's decision-record requirements and design are amended in the same pull request to say so.

The skeleton is deliberately thin. The answer is recorded by a session decider, because a person's answer needs the verification that step 2 adds. In this step any `answer` entry with outcome `answered` aimed at a question closes it; which answers count and which one governs are narrowed in steps 2 and 4. The `settled` and `withdrawn` outcomes, `readdress`, the new subject fields other than the typed recipient, the content area, the read by position, the precedent read, the wake ring and the retention changes are not part of this step.

Command names: this step uses `koto decisions record` as it exists, and proposes `koto decisions open --person <handle>` for the read and `koto decisions answer <raiser-session> <decision-id> --in <session> --text <text>` for the answer, modelled on `koto decisions reverse`. If the amended design settles on other names, the criteria and the check apply to those names and the worker's report says which were used.

**Acceptance Criteria**:

- [ ] `koto decisions record A --kind escalate --outcome escalated --subject question=q1 --subject text=... --subject recipient=person:owner --by session` exits 0, and `koto decisions show A <id>` returns the recipient as separate kind and handle values (`person`, `owner`), so a caller selects a person's questions with a field comparison and never splits or pattern-matches a string. `session:<name>` and `anchor:<name>` recipients read back the same way with their own kind.
- [ ] An `escalate` whose recipient has no type prefix, written before this change (for example `recipient=coord`), still appears in `koto decisions list <session> --format v1` and `koto decisions show` with the value it was stored with, marked as untyped, and is never returned by the open read for any person.
- [ ] `koto decisions open --person owner` exits 0 and prints JSON whose `questions` array holds A's question with its identity `<A's session id>/<decision id>`, the raising session's name, the question identifier and text, and the typed recipient. It takes no session argument, and it returns the question when A has no parent, no anchor, no `continues` relation and no other recorded link to any session.
- [ ] `koto decisions open --person someone-else` exits 0 with an empty `questions` array while A's question is open for `owner`.
- [ ] `koto decisions answer A <id> --in B --text "..." --by session` exits 0 and prints the new entry with kind `answer`, outcome `answered`, the question's session id and decision id as its target, the answer text, the decider and the run mode. Afterward exactly one new file exists under B's `ctx/koto/aimed/<A's session id>/`, and every file under A's session directory is byte-identical to what it was before the command (lock files aside).
- [ ] `koto decisions answer` aimed at a decision that does not exist, or at one whose kind is not `escalate`, exits 2 with a decision error naming the reason, and writes nothing in either session.
- [ ] With two questions q1 and q2 raised in A to `person:owner` and a third, q3, raised to `person:someone-else`, an answer aimed at q1 alone leaves `koto decisions open --person owner` returning exactly q2 and `koto decisions open --person someone-else` returning exactly q3. `koto next A` then reports q1 as answered with its own answer text and does not report q2 as answered, and a decision in A citing q1's answer leaves q2 as it was.
- [ ] An answer's target is the question's identity, the raiser's session id with the decision id, never the session's name: an answer that pairs A's session id with a decision id that exists only in another session exits 2 and writes nothing, and after A is removed and a new session named `A` is created, the earlier answer is not reported on the new A's `koto next` and closes none of its questions.
- [ ] `koto decisions answer ... --by person:owner` exits 2 with a message saying a person's answer cannot be recorded yet, and writes nothing. No binary built from this step can store a person's answer that was never verified.
- [ ] After the answer is recorded, `koto decisions open --person owner` exits 0 with an empty `questions` array. Open is computed when the read runs: no file in A or B records the question as closed other than the `answer` entry itself.
- [ ] `koto decisions list B --format v1` lists the `answer` entry as a readable decision, and `koto decisions reverse` aimed at it is refused with exit 2. A reversal recorded in the aimed area before this change still lists, shows and takes effect as it did.
- [ ] `koto next A`, run after the answer is recorded, exits with the code it would have had without the question, and its response carries a `questions` array with one element: the question's identity, its state (`answered`), and the answer in effect with its text, its decider and the session it was given in. The same array is present when A's workflow has already reached a terminal state, and on every repeat of `koto next A`.
- [ ] `koto next A` reports the answer without writing: A's and B's session directories are byte-identical before and after the call that only reports (no transition submitted), and the call makes no network request under the cloud backend.
- [ ] A session that continues A through koto's existing succession (`koto init <succ> --template work.md --continues A --supersede`, the form `tests/decisions_succession_test.rs` uses) gets the answer to A's question in the `questions` array of its own first `koto next`.
- [ ] Once A records a decision whose basis names the answer (`koto decisions record A --kind judgment --outcome settled --subject what=... --by session --basis B:<answer id>`), the next `koto next A` carries no `questions` key. A decision in A that does not cite the answer leaves the array in place.
- [ ] `koto next` on a session that holds no question prints a response byte-identical to the one the previous binary printed: `cargo test --test next_response_baseline` passes with its fixtures unchanged.
- [ ] Entries written by an older binary still read: `cargo test --test decisions_record_test --test decisions_reverse_test --test decisions_chain_test --test decisions_succession_test --test decisions_gate_pass_test --test decisions_cloud_test` passes with no expected value edited, and a session directory holding decisions written before this change lists the same entries with the same statuses under the new binary.
- [ ] A reader of `docs/prds/PRD-decision-record.md` finds, numbered after the existing requirements: the recipient of an `escalate` typed as a session, an anchor or a person, with an untyped recipient on an existing entry still readable; the `answer` kind with its `answered` outcome and its subject; that an answer is stored in the session it is given in and never in the asker's; the read of open questions for a person, which makes no chain test; open as something computed at read time; and the report on `koto next`, repeated until the asker cites the answer and present on an ended workflow. The statements that kinds, outcomes and subject fields are closed name `answer` and the typed recipient among what is allowed.
- [ ] A reader of `docs/designs/DESIGN-decision-record.md` finds the aimed area described as holding reversals and answers, the read-time rule this step builds for open, the command surface for the open read and the answer, the `questions` array of `koto next` with its fields and its no-write, no-network, never-blocking contract, and a note that a binary older than this change reads an `answer` entry as unreadable. Both documents say that a person's answer, precedence between answers, passing a question up and retention are not yet covered, so nobody reads the interim closing rule as final.
- [ ] `docs/guides/cli-usage.md` describes `koto decisions open`, `koto decisions answer` and the `questions` array with the same names and fields the binary prints.

### Step 2: An owner's answer is accepted only when a question-prompt call in that session showed the stored question and returned that answer

**Goal**: In the koto repository, a question's content is stored once in a write-once area capped at 16 KiB and hashed, and an `answer` by a person decider is recorded only after koto has checked it against the harness's record of the question-tool call in the session it is recorded in. koto takes the answer text from that call's result, marks the entry verified, and reads the mark as verified only in a session this machine created.

**Acceptance Criteria**:

Content

- [ ] Writing content of exactly 16,384 bytes for a question succeeds, and writing 16,385 bytes exits non-zero with a message that names the 16 KiB cap and leaves nothing stored.
- [ ] A second content write for the same question exits non-zero, whether the bytes are the same or different, and the content read returns the first write's bytes afterward. A write through the context store to a key under `koto/packets/` is refused the same way writes under the other decision areas are.
- [ ] The content read, run from a session other than the raiser's and given the question's identity `<raiser-session-id>/<decision-id>`, prints bytes identical to those written (compared with `cmp`, including any trailing newline or its absence).
- [ ] The `packet` value shown on the question's `escalate` entry equals the hash of the stored bytes, and an `escalate` whose `packet` does not match the content written for it is refused.

Verification of a person's answer

- [ ] With a fixture in which the call exists in the session, is the question tool, shows the stored `question` text and every option `label` at the named position, carries the question's identity at that position and has a result from the user, an `answer` by `person:owner` that hands in the pointer (harness session id, call id, position) exits 0, and the stored entry shows the pointer.
- [ ] The recorded answer text equals the text the call's result holds for that position when the caller passes different answer text, and when the caller passes none. A free-text reply in the result is stored verbatim.
- [ ] A fixture whose call asked three questions backs one accepted answer for each of positions 1, 2 and 3, each against its own stored question, and each entry holds the result text for its own position.
- [ ] A second `answer` citing a call and position that an earlier answer already cites exits non-zero and writes nothing, and the first entry is unchanged.
- [ ] Each of these exits non-zero, writes no entry, and prints a message naming the one check that failed: the pointer names no call in that session's record; the call named is not the question tool; the question at that position does not carry the identity of the question being answered; the result did not come from the user (a denied or errored call, or a result supplied by something other than the user's reply); the position is outside the questions the call asked.
- [ ] The comparison is of exact bytes, shown by one refusal case each, every one naming the question-text or the option check: the `question` text with one byte changed; with trailing whitespace added; with a difference in Unicode normalization only; one option `label` with one byte changed; with only its letter case changed; one option dropped; one option added; two options swapped. The fixture that differs from these in nothing is accepted.
- [ ] The record read is the one for the harness session the answer is recorded in, and no other: with a matching call that exists only in harness session X's record, an `answer` recorded in a koto session bound to harness session Y exits non-zero and writes nothing, whether the pointer names X or names Y with X's call id. No caller input chooses where koto looks for the record.
- [ ] A pointer is accepted only with a person decider: an `answer --by session` handing in a pointer that would pass every check exits non-zero and writes nothing, so a session's answer never carries the mark. The mark verifies the prompt and its reply; the person handle stays the caller's claim, and an entry recorded for a handle other than `owner` reads as that handle's answer, never the owner's.
- [ ] Two `answer` commands started together for the same call and position leave exactly one entry, and the other exits non-zero naming the reused call position; the test runs the pair at least 20 times.
- [ ] At least one accepted fixture and one result-not-from-the-user fixture (a denied call) are structural copies of real harness records captured in this workspace: every field name and nesting kept, every text value replaced by a marker string. The pull request names how they were captured, and a test fails when koto reads a field the captured structure does not have.
- [ ] An `answer` by a person decider with no pointer exits non-zero with a message saying a person's answer needs the question-prompt evidence. An `answer` by a session decider with no pointer is still accepted as step 1 left it.
- [ ] A harness record in a shape koto does not recognize (a missing or renamed field in the call or its result, a result with no per-question answer, a line that is not valid JSON where the call should be) is refused with a message saying the record's shape is not recognized, and nothing is written.
- [ ] No refusal message contains text from the harness's record. Each refusal fixture carries a distinctive marker string in its question text, option labels and result, and the marker appears in none of koto's output or error text; the message holds the check's name and the pointer the caller handed in, nothing more from the record.

The verified mark

- [ ] Reading an accepted entry (the single-entry read and the listing) shows the evidence with a verified mark whose source label is `observed`, while the person handle on the same entry stays labelled `handed`.
- [ ] No flag or field a caller can pass produces the mark: an `answer` whose input claims the entry is verified, with a pointer that fails a check, is refused, and one with no pointer is refused as above.
- [ ] Reading the same entry from a copy of the session that arrived through `koto session import` shows it as a remote session's answer and does not show it as verified, though the stored bytes of the entry are identical to the original's.
- [ ] Reading the entry from a session this machine obtained by a pull from shared storage shows the same remote reading, and reading it in the session on the machine that recorded it still shows verified after that session has synced to shared storage.
- [ ] Reading a verified entry does not open the harness's record: with the fixture record removed after the answer is accepted, the entry still reads verified in the session that recorded it.

Documents

- [ ] A reader of `docs/prds/PRD-decision-record.md` finds new requirements, numbered after R48, stating the content area with its cap and write-once rule, each check koto applies to a person's `answer`, that the answer text comes from the call's result, the verified mark with its `observed` label, and the remote reading for a session that arrived by import or by a pull, each with an acceptance criterion.
- [ ] A reader of `docs/designs/DESIGN-decision-record.md` finds `koto/packets/` named as a fourth write-once area, each field of the harness's record koto reads for the call and for its result, with that field's path in the captured record, where in a prompt position the question's identity is carried, how koto finds the record for a harness session, that an unrecognized shape is refused, and that the trust in the mark rests on the harness's record, whose format is observed and not a documented contract.

### Step 3: A passed-up question is listed once under every coordinator above its raiser, with who it now waits on

**Goal**: In the koto repository, a question can be passed up with a new `readdress` entry that keeps its identity, and a new open read by position returns every open question raised at or below a session or anchor, or currently addressed to it, exactly once, with its current addressee and the addressees it has had. The open read by person follows the current addressee, so a question appears for a person only while it waits on that person.

Deliberately left out. Any `answer` with outcome `answered` still closes a question as step 1 left it, including one from a session the question has moved away from; which answers count, and precedence among them, are step 4. This step refuses a `readdress` at write time unless it is recorded in the raiser or in the session the question currently waits on, which is the minimum that keeps the addressee history a single line. Step 4 adds the rest of the pass-up rules: that the new recipient must be the recorder's own recorded dispatcher or a person, and that the reads re-judge every stored entry and return one that breaks a rule marked as not counted with the reason. The ground a session relied on when passing up, settle and withdraw, needs, the limit of twenty, the precedent read, one question's full history as its own read, retention, the wake ring and the performance bound are later steps. Nothing here depends on step 2: no person decider, no content area, no verified mark.

"Position" uses links koto already records. A session is directly below the session or anchor that `koto session origin <name>` reports as its dispatcher, which comes from a dispatched-by link (`koto init --dispatched-by <name>`, `koto session link <session> --dispatched-by <name>`) or from the anchor holding it. koto has no read today that walks those links downward from a coordinator (the retention hierarchy treats them as undirected), so this step adds that walk, on the same local scan the open read by person uses.

Command names: this step proposes `koto decisions readdress <raiser-session> <decision-id> --in <session> --to <recipient>`, modelled on `koto decisions answer`, and `koto decisions open --at <session-or-anchor>` beside the existing `--person <handle>`. It proposes `addressee`, `addressees` and `relation` as the new fields on an open read's elements. If koto's amended design settles on other names, the criteria and the check apply to those names and the worker's report says which were used.

**Acceptance Criteria**:

Passing a question up

- [ ] With `worker` dispatched by `manager` and `manager` dispatched by `director`, and a question q1 raised in `worker` to `session:manager`, `koto decisions readdress worker <id> --in manager --to session:director --by session` exits 0 and prints the new entry with kind `readdress`, outcome `passed`, the question's session id and decision id as its target, and the new recipient as separate kind and name values.
- [ ] After that command exactly one new file exists under `manager`'s `ctx/koto/aimed/<worker's session id>/`, and every file under `worker`'s and `director`'s session directories is byte-identical to what it was before (lock files aside). A pass-up is stored in the session that passed the question up and nowhere else.
- [ ] The question's identity is unchanged by a pass-up: `koto decisions show worker <id>` prints the same entry, with the recipient it was raised with, before and after, and no second `escalate` exists in any session.
- [ ] A `readdress` aimed at a decision that does not exist, at one whose kind is not `escalate`, at an `escalate` with an untyped recipient, at a reversed `escalate`, or at a question an `answer` has already closed exits 2 with a decision error naming the reason, and writes nothing in any session.
- [ ] A `readdress` whose `--to` value has no type prefix, has a known prefix with a bad name, or names the question's current addressee exits 2 and writes nothing.
- [ ] A `readdress` is accepted only from the raiser or from the session the question currently waits on. After `manager` has passed q1 to `session:director`, a second `readdress` of q1 recorded `--in manager` exits 2 and writes nothing, and so does one recorded in a session that never was its addressee. One recorded `--in director` exits 0. One recorded `--in worker` (the raiser) exits 0 and is stored under `worker`'s own aimed area.
- [ ] `koto decisions readdress ... --by person:<handle>` exits 2 and writes nothing, `koto decisions record --kind readdress` is refused the way `--kind answer` is, and `koto decisions reverse` aimed at a `readdress` entry exits 2. `koto decisions list manager --format v1` lists the entry as a readable decision.
- [ ] The target is the question's identity, never the raiser's name: a `readdress` pairing `worker`'s session id with a decision id that exists only in another session exits 2, and after `worker` is removed and a new session named `worker` raises a question, the earlier pass-up does not apply to it. The new question reads as addressed to the recipient it was raised with in every open read.

Who it waits on

- [ ] Every element of `koto decisions open --person <handle>` and `koto decisions open --at <name>` carries `addressee`, the typed recipient the question waits on now, and `addressees`, the ordered list of every recipient it has had, starting with the one it was raised with. `recipient` still shows the one it was raised with.
- [ ] A question passed up twice reads as one question: after `manager` passes q1 to `session:director` and `director` passes it to `person:owner`, `addressee` is `person` / `owner` and `addressees` is `session:manager`, `session:director`, `person:owner` in that order, in every read that returns q1. Between the two pass-ups `addressee` is `session` / `director`.
- [ ] A pass-up moves only its own question. With q1 and q2 both raised in `worker` to `session:manager` and only q1 passed up, q2's `addressee` is still `session` / `manager` and its `addressees` has one element, in every read that returns it.
- [ ] `koto decisions open --person owner` returns a question only while it waits on `owner`. It does not return q1 while q1 waits on `manager` or `director`, and returns it once `director` has passed it to `person:owner`. A question raised to `person:someone-else` and passed by its raiser to `person:owner` is returned for `owner` and no longer for `someone-else`.

The read by position

### Step 4: The owner's answer outranks a session's, and a raiser can only withdraw its question or settle it from an answer of the owner's

**Goal**: In the koto repository, the reads decide which entries aimed at a question count and which one is in effect: a verified person answer outranks any session's entry whichever was recorded first, a session's answer counts only from the session the question waits on, and the raiser can close its own question only by withdrawing it with a reason or by settling it from evidence, which for a question waiting on a person means an answer of that person's that is in effect. A need its raiser cannot settle, the rule on where a pass-up may go, and the limit of twenty open questions addressed to a person land with it.

Deliberately left out. The precedent read by subject label, one question's whole history as its own read, and the `state` and `result` fields on `judgment` are step 5. Retention, the cleanup refusal, the wake ring, the performance bound and the koto release are step 6. This step adds the `label` and `need` subject fields on `escalate` only because the settle rule compares them; no read selects by `label` here. Criteria about a person's answer mean an accepted, verified person answer recorded as step 2 allows, with the pointer step 2 defines, from a recorded fixture and never a live prompt.

Command and field names: this step proposes `--outcome settled` and `--outcome withdrawn` on `koto decisions answer` (the default stays `answered`), recorded `--in` the raiser; `--subject label=<text>` and `--subject need=<decision|credential|reserved-step>` on an `escalate`; a `need` field on every element of the open reads; and, on every `answer` and `readdress` entry that `koto decisions list --format v1` and `koto decisions show` return, `counted` (true or false, with a `reason` when false) and, on a closing entry, `governs` (true on the one entry in effect). The stored status of an entry stays as it is. If koto's amended design settles on other names, the criteria and the check apply to those names and the worker's report says which were used.

The group "The limit of twenty" depends on nothing else in this step. If the pull request grows past what one review can carry, that group is the natural second pull request, and the rest stays together because settling, needs and precedence share one read-time rule.

Which entries count

- [ ] A question that holds only entries that do not count is still open to everything an open question accepts: `koto decisions readdress` and a later entitled answer both exit 0 on it.

Which answer is in effect

- [ ] A session answered first, the owner later: after `director` answers q1 as its addressee and an accepted person answer to q1 is then recorded, both entries read `counted` true, the owner's alone reads `governs` true, and q1 stays out of every open read.
- [ ] The owner answered first, a session later: with an accepted person answer on q1, a later `answered` answer by the addressee session exits 2 with a message saying the question is already closed and naming the entry in effect, and writes nothing. - [ ] With no person answer, the earliest counted session entry governs, ordered by time, then recording session name, then identifier. Two stored answers by the addressee session read `governs` true on the earlier and false on the later, and a session entry aimed at a question a counted entry already closed is refused at write time.
- [ ] Two person answers, the second citing the first as its basis: the second governs and the first reads `governs` false, also when the second's stored time is earlier than the first's. Both stay listed with `counted` true.
- [ ] Two person answers, neither citing the other: the one with the later time governs, and both stay listed.
- [ ] Exactly one closing entry of a closed question reads `governs` true in any listing, and an open question has none.
- [ ] Everything is matched by identity. After `worker` is removed and a new session named `worker` raises a question, no answer, settle, withdrawal or pass-up aimed at the earlier `worker`'s question reads as counted for the new one, which reads open with a one-element `addressees`.

- [ ] `koto next worker` reports the entry in effect and only that one: with a session's answer and a later owner's answer on q1, the `questions` array holds one element for q1 whose answer carries the owner's text, a person decider, the session it was given in and the verified reading step 2 defines. Where a pass-up may go

- [ ] A pass-up may name only a person or the dispatcher `koto session origin` reports for the session recording it (for a successor, the dispatcher of the session it continues). `koto decisions readdress worker <id> --in manager --to session:other-lead --by session` exits 2 with a decision error naming the destination rule and the dispatcher it would accept, and so does `--to session:worker` and `--in worker --to session:director`. `--in manager --to session:director`, `--in manager --to person:owner` and `--in worker --to person:owner` each exit 0.

Withdrawing and settling

### Step 5: A session finds the owner's earlier answers by subject, and attempts and provisional decisions can be listed

**Goal**: In the koto repository, a session can read the answers a person gave that are in effect in its chain, narrowed to a subject label, and can read one question's whole history by its identity. A `judgment` can carry the workflow state it was made in and a result of `decided`, `undecided` or `provisional`, and a new read lists those attempts for a session or for everything at and below a position, including the provisional ones still awaiting a person's review.

Deliberately left out. Retention, the cleanup refusal, the wake, the performance bound on the reads that already exist and the koto release are step 6 and the release that follows it; this step needs none of them and bounds only the reads it adds. Everything in shirabe is later: the `shirabe question` commands that call these reads are step 8, and so is every refusal that rests on them. koto refuses no pass-up and no `escalate` for want of an attempt, and judges neither whether an earlier answer covers a new case nor whether a choice was cheap to undo. The content read (`koto decisions content read`) exists since step 2 and is not changed. Criteria about a person's answer mean an accepted, verified person answer recorded from a recorded fixture as step 2 allows, never a live prompt. "The answer in effect", "counted" and "governs" mean what step 4 defines, and `label` is the subject field step 4 adds to an `escalate`; if step 4 merges under other names, the criteria apply to those names.

Command and field names: this step proposes `koto decisions precedent --person <handle> --chain <session-or-anchor> [--label <text>]`; `koto decisions history <session id>/<decision-id>`, taking the identity in the form `koto decisions content read` takes; `koto decisions attempts` with exactly one of `--in <session>` and `--at <session-or-anchor>`, and the optional filters `--result`, `--state`, `--question <identity>` and `--awaiting-review`; `--subject state=<state name>:<visit>` on a `judgment` and on an `escalate`; and `--subject result=<decided|undecided|provisional>` on a `judgment`. It also proposes that koto copies a question's `label` onto each `answer` it records for that question, so the precedent read still has the label once the raiser is gone. If koto's amended design settles on other names, the criteria and the check apply to those names and the worker's report says which were used.

Four rules the upstream design leaves to koto are fixed here and written into koto's amended design. (1) A session's chain is every session and anchor connected to it through the links `koto decisions open --at` follows, in either direction, together with the sessions each continues through a confirmed succession. (2) An answer belongs to a chain when the session it was given in is in the chain, or when the session that raised its question is still in the store and is in the chain. (3) An attempt is tied to a question through `basis`, in either direction: the question's `escalate` names the attempt, or the attempt names the `escalate`. (4) A provisional judgment stops awaiting review when it reads `reversed`, or when a question whose `escalate` names it in its `basis` is closed by a person's verified answer in effect.

**Acceptance Criteria**:

Unless a criterion says otherwise, the sessions are step 3's with one more worker: `worker` and `worker2` dispatched by `manager`, `manager` dispatched by `director`, and an unrelated `other-lead` with `other-worker` below it. q1 is raised in `worker` with `label=cache`, passed up to `person:owner`, and closed by an accepted `person:owner` answer recorded in `director`.

The precedent read

- [ ] `koto decisions precedent --person owner --chain worker2 --label cache` exits 0 and prints JSON whose `answers` array holds one element for q1's answer: the question's identity `<worker's session id>/<decision id>`, the question's `label`, the answer's session and identifier, its text, its time, its decider as kind `person` with handle `owner`, and the `verified` reading step 2 defines. The same command with `--chain worker`, `--chain manager` and `--chain director` returns the same single element, so a coordinator above the worker and a sibling of the raiser both find it.
- [ ] The label is compared byte for byte. With q1's answer in place, `--label Cache`, `--label cach`, `--label "cache "` and a label that differs from `cache` only in Unicode normalization each exit 0 with an empty `answers` array. `--label ""` exits 2.
- [ ] With no `--label`, the read returns every answer of that person in effect in the chain, each with its `label`, and an answer to a question raised with no `label` appears there with a null `label` and under no `--label` value.
- [ ] Only an answer that is in effect is returned. While q1 is still open the read returns nothing for it. A question whose entry in effect is a session's answer, a `settled` entry or a `withdrawn` entry yields no element. When a second person answer to q1 governs, as step 4 decides between two person answers, the read returns that one alone, and the earlier one is absent.
- [ ] A raiser's settle is never precedent in its own right: after `worker2` settles q5 (same label, waiting on `person:owner`) from q1's answer, the read for `cache` still returns exactly the one element for q1.
- [ ] Only a person's answer that reads `verified` is returned. An answer by a session decider that names the owner in a note, a `person:owner` answer in a session that arrived through `koto session import` (on this machine under a new name, or from another), and one obtained by a pull from shared storage are each absent from `--person owner`, while `koto decisions show` still prints each with the reading step 2 gives it. `--person someone-else` exits 0 with an empty array while q1's answer is in effect for `owner`.
- [ ] The read stays inside the chain. With q9 raised in `other-worker` with `label=cache` and closed by an accepted `person:owner` answer recorded in `other-lead`, `--chain worker2 --label cache` returns q1's answer and not q9's, and `--chain other-worker --label cache` returns q9's and not q1's. A session with no link to any other has a chain of itself and the sessions it continues: `--chain` naming it returns only answers given in it or to its own questions.
- [ ] An answer given outside the raiser's chain is still found from it: with q1's owner answer recorded in `other-lead` in place of `director`, `--chain worker2 --label cache` returns it.
- [ ] An answer outlives its raiser. After `worker` is removed with `koto session cleanup`, `--chain manager --label cache` still returns q1's answer with the identity and the label it had, read from the label copied onto the answer. An `answer` recorded for a question that carries a `label` shows that label in its own subject in `koto decisions show`, whatever the caller passed, and an answer to a question with no label stores and prints exactly what it did before this step.
- [ ] Everything is matched by identity. After `worker` is removed and a new session named `worker` raises a question that reuses q1's decision id with `label=queue`, the element for the earlier answer still carries the removed session's id and `label` `cache`, is not returned for `--label queue`, and the new question, being open, yields no element.
- [ ] Each element says whether the named session has taken the answer into account: `cited` is true when a decision in the run of the session `--chain` names cites the answer in its `basis`, resolved the way the `questions` report on `koto next` resolves a citation, and false otherwise. Each element also carries `below`, true when the answer was given at or below the named session as `koto decisions open --at` defines below. A `judgment` recorded in `manager` with `--basis director:<answer id>` turns `cited` true for `--chain manager` and leaves it false for `--chain director`.
- [ ] Several results come back in one stated order that does not change between runs: by the answer's time, then the answering session's name, then identifier. Two runs of the same read print byte-identical output.
- [ ] Every answer the read returns for a label and a person is accepted by step 4's settle as the basis for a question with that label waiting on that person, and an answer the read leaves out because it no longer governs is refused there.
- [ ] `--chain` naming no session or anchor exits 2, and so does the command without `--person` or without `--chain`. The read writes nothing: every session directory is byte-identical before and after it (lock files aside).

One question's history

- [ ] `koto decisions history <worker's session id>/<q1 id>`, run from any directory, exits 0 and prints one JSON document carrying: the question as raised (identifier, text, `label`, `need`, `state`, the `packet` hash and whether content is stored for it, the recipient it was raised with); the raiser's name and session id, the run mode it was raised in and, when the raiser has been superseded, its successor; whether the question is open; `addressee` and `addressees` as the open reads print them; and the answer in effect with its text, decider, reading, the session it was given in and the run mode it was given in, or null while the question is open.
- [ ] The same document holds an ordered list of everything recorded about the question: the raise, every pass-up with the session that recorded it and the recipient it names, every `answer` entry whatever its outcome with its session and decider, each attempt tied to the question, and each decision in this machine's store that cites one of the question's answers in its `basis`, with that decision's session, identifier, kind and decider. For q1 after `worker2` has settled q5 from its answer, the list ends with that settle as a citing decision.
- [ ] The order is causal, not by clock alone: entries are ordered by time, then recording session name, then identifier, except that an attempt the `escalate` names comes before the raise, a counted pass-up never comes before the pass-up it follows in the addressee history, and a citing decision never comes before the entry it cites. A fixture whose second pass-up carries an earlier stored time than the first still lists them in the order of `addressees`.
- [ ] Every `answer` and `readdress` entry in the list carries `counted`, with the `reason` when false, and every closing entry carries `governs`, with the values `koto decisions show` gives the same entry. An entry that does not count is listed and marked, never left out: a session's answer from a session that is not the addressee appears in q1's history with `counted` false while q1's `open` reads true.
- [ ] Each pass-up in the list names the attempts that preceded it: the identifiers of the attempts recorded in the passing session's run, tied to the question and recorded no later than the pass-up. A pass-up by a session with no such attempt carries an empty list, and an attempt recorded after the pass-up is not named on it.
- [ ] An identity whose session id is in no session of the store, or whose decision id that session does not hold, exits 2 with `decision_not_found` and a message naming the identity as given. An identity naming a decision that is not an `escalate`, or one with an untyped recipient, exits 2 with `invalid_decision`. An argument that is not `<session id>/<decision-id>` exits 2. The session's name in place of its id is not accepted.
- [ ] An entry koto cannot read does not fail the read. With a file that does not parse planted beside the entries aimed at q1 in `manager`, the command exits 0, lists that entry as unreadable with the session it sits in, and returns every other entry as before. An unreadable entry never reads as counted and never as the answer in effect.
- [ ] The history is by identity. After `worker` is removed and a new `worker` raises a question that reuses q1's decision id, the history of the new identity lists none of the entries aimed at the removed session's question.
- [ ] The read writes nothing: every session directory is byte-identical before and after it (lock files aside).

`state` and `result`

- [ ] `koto decisions record worker --kind judgment --outcome settled --subject what="..." --subject state=implement:1 --subject result=undecided --by session` exits 0, and `koto decisions show` and `koto decisions list worker --format v1` return `state` and `result` in the entry's subject with the values given. `result=decided` and `result=provisional` are accepted the same way, with or without `state`.
- [ ] Any other `result` value exits 2 with an error naming `subject.result`; a `state` that is not a state name koto accepts followed by `:` and a positive whole number exits 2 naming `subject.state`; `result` on a kind other than `judgment`, and `state` on a kind other than `judgment` and `escalate`, exit 2. Each refusal writes nothing: the session's directory is byte-identical before and after (lock files aside).
- [ ] `state` is the caller's value. koto stores it as handed and does not compare it with the workflow state the session is in, which every decision already records separately and which `show` still prints unchanged beside it.
- [ ] A `judgment` recorded with neither field, including every one written before this step, is not an attempt: `koto decisions list --format v1` and `koto decisions show` print it byte-identical to what the previous binary printed, with no new key, and no `koto decisions attempts` read returns it.
- [ ] An `escalate` accepts `--subject state=implement:1`, and every element of `koto decisions open --person` and `koto decisions open --at` returns `state` for a question raised with one and omits or nulls it for one raised without.
- [ ] `koto decisions list worker --format v1 --kind judgment --subject result=provisional` returns exactly the judgments recorded with that result, and `--subject state=implement:1` exactly those with that state, through the subject filter the listing already has.
- [ ] A `judgment` carrying either field reports nothing on its session's `koto next`, changes no exit code, and is returned by no open read.

Attempts

- [ ] `koto decisions attempts --in worker` exits 0 and prints JSON whose `attempts` array holds every `judgment` in `worker`'s run that carries a `result`, each with its session, identifier, `what`, `state`, `result`, decider, run mode, time and status. The run includes the sessions `worker` continues through `--continues ... --supersede`. `--result undecided` and `--state implement:1` narrow the list to exact matches, and combine.
- [ ] `koto decisions attempts --at director` returns the attempts recorded in `director`, in the sessions it continues, and in every session below it, each exactly once and each saying in `relation` whether it was recorded at the position or below it. It returns none recorded in `other-lead` or `other-worker`, and `--at other-lead` returns none of `worker`'s. An anchor is a position as it is for `koto decisions open --at`.
- [ ] An attempt is tied to a question through `basis`, in either direction. An `escalate` recorded with `--basis worker:<attempt id>` makes that attempt read as tied to the new question, and a `judgment` recorded in `manager` with `--basis worker:<q1 id>` reads as tied to q1. Each such attempt carries the question's identity in `question`, and an attempt tied to none carries null. A citation is resolved the way the `questions` report resolves one, so an `escalate` in a recreated session that reuses the cited name and identifier is not taken for the question.
- [ ] A caller can ask whether a session attempted a question before passing it up: `koto decisions attempts --in manager --question <q1's identity>` exits 0 with one element once `manager` has recorded such an attempt, and exits 0 with an empty array before, or when the only attempt for q1 was recorded in another session. An attempt recorded in `worker` is not returned for `--in manager`.
- [ ] koto itself refuses nothing for want of an attempt: `koto decisions readdress` by a session with no recorded attempt, and an `escalate` with no attempt behind it, exit 0 exactly as they did before this step.
- [ ] An undecided attempt is listed with the question it handed back: `koto decisions attempts --in worker --result undecided` shows q1's identity on the attempt q1's `escalate` names, and null on an undecided attempt no question names, so a caller can find an attempt that ended undecided and raised nothing.
- [ ] `koto decisions attempts` with both `--in` and `--at`, or with neither, exits 2 with a usage error. `--in` or `--at` naming no session or anchor exits 2, and so does a `--result` value outside the three and a `--question` that is not an identity. An empty result exits 0 with an empty `attempts` array.
- [ ] Attempts are ordered by time, then session name, then identifier, and the read writes nothing: every session directory is byte-identical before and after it (lock files aside).

Provisional decisions awaiting review

- [ ] A `judgment` recorded in `worker2` with `result=provisional` is returned by `koto decisions attempts --at director --result provisional --awaiting-review`, by the same read `--at manager` and `--at worker2`, and by none `--at other-lead`. It is returned by neither `koto decisions open --person owner` nor `koto decisions open --at` for any position.
- [ ] A provisional judgment is told apart from a decided one wherever it is read: `koto decisions list --format v1` and `koto decisions show` print `result` as `provisional` on the one and `decided` on the other, and `--awaiting-review` returns no entry whose `result` is `decided` or `undecided`.
- [ ] Each provisional element carries the run mode it was recorded in and its review: `awaiting`, `reviewed` with the review question's identity and the answer in effect, or `reversed` with the winning reversal as `koto decisions show` reports it. `koto decisions show` prints the same review for a provisional judgment.
- [ ] A person's verified answer ends the wait. After a question is raised whose `escalate` names the provisional judgment in its `basis`, the judgment is still returned by `--awaiting-review`, now with that question's identity. Once that question is closed by an accepted person answer in effect, `--awaiting-review` no longer returns the judgment, the read without `--awaiting-review` returns it with review `reviewed` and the answer's text and decider, and `koto decisions show` still prints the judgment as recorded with `result` `provisional`.
- [ ] Nothing less ends it. With the review question closed by its addressee session's answer, by the raiser's settle or withdrawal, or by a person answer that reads as a remote session's, the judgment is still returned by `--awaiting-review`. A decision by a session that cites the provisional judgment in its `basis` does not end the wait either.
- [ ] A reversal ends the wait. After `koto decisions reverse` aimed at the provisional judgment is accepted under the rules koto already has, `--awaiting-review` no longer returns it, the read without the flag returns it with review `reversed`, and its status reads `reversed` in every listing as any reversed judgment's does.
- [ ] Review is matched by identity: after `worker2` is removed and a new `worker2` records a provisional judgment that reuses the identifier, an earlier review question naming the removed session's judgment does not mark the new one reviewed.

Decisions and who made them, for a subtree

- [ ] No new read is added for this. `koto decisions list director --below --format v1`, which koto already has, returns every decision recorded below `director` with its decider, and after this step that listing shows the attempts with their `state` and `result`, the pass-ups, and each answer with its decider, reading, `counted` and `governs`, so one listing answers who decided what below a coordinator, a provisional decision included. ### Step 6: A session holding an open question survives cleanup, and recording an answer wakes the asker

**Goal**: In the koto repository, a session that holds an open question is kept by every removal koto makes by rule, a session that holds an answer or a pass-up aimed at a question joins that question's hierarchy, an explicit cleanup that would orphan a question is refused unless forced, and recording an answer rings the asker's wake file. The open reads and the `questions` read on `koto next` are shown to finish within five seconds on a store of 1,000 sessions holding 200 open questions, on the local backend and on the cloud test backend.

Deliberately left out. This step builds on what steps 1 and 3 put on koto main and on nothing else: no person's answer and no content area (step 2), no `settled` or `withdrawn` outcome, no needs, no precedence among answers and no limit of twenty (step 4), no precedent read and no `judgment` fields (step 5). "Open" here is whatever the open reads compute when they run, which today is an in-effect `escalate` with a typed recipient that no `answered` answer targets. Retention and the cleanup refusal ask that same computation, so when step 4 changes what counts as open, or which answer is in effect, they follow with no change of their own. The same holds for the ring: this step rings on the one closing entry that exists, an `answer` with outcome `answered`, and the outcomes step 4 adds ring from the place they are stored. The performance bound covers the reads that exist now, `koto decisions open --person`, `koto decisions open --at` and the `questions` read on `koto next`; the reads steps 4 and 5 add are bounded in their own steps.

No release in this pull request. The koto release that carries steps 1 to 6 is cut after steps 2, 4 and 5 have merged, by whoever merges them. This step's pull request creates no tag and changes no version number.

The wake is koto's existing per-session wake file, `<koto home>/wakes/<session>`, which a ring appends one opaque line to and truncates in place once it reaches 32 KiB. It carries no content: it means "look again", and the asker's tick reads the store as it always does. So no criterion below has a tick skip its scan because a wake is present, and none treats a wake line as an answer.

Names: this step proposes the retention reason `open_question` on a terminal tick's `retention` field, with the question identities beside it; a `--force` flag on `koto session cleanup`, which has none today; the error code `holds_question` for the refusal; and `orphaned_questions` on a forced removal's output. An aimed `answer` or `readdress` entry counts as an edge of the existing hierarchy, so a session kept by one reads `hierarchy`, the reason koto already prints. If koto's amended retention design settles on other names, the criteria and the check apply to those names and the worker's report says which were used.

**Goal**: In the shirabe repository, the plugin gains a second pre-tool hook, on the question tool (`AskUserQuestion`) only. ### Step 8: A question raised with shirabe is shown identically after the session restarts, and answered through the prompt as the owner

**Goal**: In the shirabe repository, on the koto release that step 6 ends with, the `shirabe` binary gains `shirabe question raise`, `pending`, `render` and `answer`: a session's question is validated, stored once and recorded in koto; any session renders it into the same bytes of question-prompt input after a restart or a compaction; and the owner's reply to that prompt is recorded as `person:owner` only by handing koto the pointer to the answered prompt. The shared procedure lands as `references/question-procedure.md`, and shirabe's koto minimum is raised to that release.

Left to later steps. The plan's outline names raising, listing, rendering and answering, and the design does not require the rest of the family to land with them, so each other subcommand arrives with the step that first calls it: `attempt` with step 9 (the decision skills record the undecided result before a question is raised); `precedent` and `withdraw` with step 10 (the decide-first state names them); `pass-up`, `settle` and `seen` with step 12 (the coordinator's scripts); `provisional` with step 13 (`/shirabe:pending`). This step still enforces the one rule of `raise` that rests on an attempt, by reading koto's record of it, and its criteria record that attempt with koto directly. Also left out: every skill, template, skill script and `requires.tsv` record; the third outcome in `references/decision-protocol.md` (step 9); replacing the coordinator's renderer (step 12); the on-demand command, and the change of the prompt guard's deny reason to name a command (step 13); and creating a koto session for a harness session no workflow drives (step 13), so `answer` and `raise` here need a koto session or anchor to record in.

The CLI does not author here. shirabe's rule is that skills author artifact bodies and the binary checks them. These commands keep to it: every field of a question's content is supplied by the calling session, and the command validates it, stores it in koto and lays the stored fields out in a fixed order. It composes no field, fills in no missing one, and writes no file in any repository.

Names. Command and flag names proposed here: `shirabe question raise --in <session> --content <file or -> [--to <recipient>] [--attempt <decision-id>] [--state <state>:<visit>]`; `shirabe question pending --in <session> [--person owner | --at <session-or-anchor>]`; `shirabe question render <identity>...` or `render --person owner`; `shirabe question answer <identity> --in <session> [--call <call-id> --position <n>]`. Proposed exit codes: 0 done; 1 shirabe refused the input before any koto write; 2 a usage error, as the binary gives today; 3 koto is missing or below the minimum; 4 koto refused, with koto's code and check name passed through; 5 a question that cannot be presented or an answer that does not read as verified. The koto names are those of the released koto: `koto decisions record --kind escalate` with `recipient`, `label`, `need`, `state` and `packet=sha256:<hex>`, `koto decisions content write` and `content read`, `prompt_header`, `koto decisions open --person` and `--at`, `koto decisions answer --by person:<handle> --prompt <harness>/<call>/<position>`, the `reading` field, `--outcome withdrawn`, `koto decisions attempts`, `koto decisions history`, `koto decisions precedent`. Where the release settles on other names, or the pull request on other flags or exit numbers, the criteria and the check apply to those, the classes of result stay distinct, and the worker's report says which were used. If the released koto refuses something this step's stored document needs (keys beyond `question` and `options`, or a need with no `options`), the worker reports it as a koto gap and does not change the stored format to get around it.

If the pull request grows past what one review can carry, the group "Answering as the owner" is the natural second pull request: raising, listing, rendering, the reference and the minimum are complete and checkable without it.

**Acceptance Criteria**:

Unless a criterion says otherwise, the sessions are `director`, `manager` dispatched by `director`, `worker` dispatched by `manager`, and `solo` with no link, in a scratch koto home, and `good.json` is a committed content fixture holding every required part with three options.

Raising: what is refused before anything is written

- [ ] `shirabe question raise --in solo --content good.json`, after an undecided attempt is recorded in `solo`, exits 0 and prints one JSON object with the question's identity `<solo's session id>/<decision id>`, the typed recipient, `need`, `label`, the `packet` hash, the stored byte count and koto's `prompt_header`. `koto decisions list solo --format v1 --kind escalate` then shows exactly one entry, and `koto decisions content read <identity> | sha256sum` prints the hex of that entry's `packet`.
- [ ] Each of these exits 1, names the failing part in its message, and leaves every session directory byte-identical (lock files aside): content with `context`, `problem`, `question`, `ground`, `label` or `waiting` absent or empty where a value is required (`waiting` may be an empty list); `options` with fewer than two entries, so no alternative beside the recommendation, or more than four; an option with no `label` or no `reason`; an unknown key; a file that is not JSON. No missing part is filled in by the command.
- [ ] Content whose stored form is exactly 16,384 bytes is accepted, and one of 16,385 bytes exits 1 with a message naming the 16 KiB bound, with no koto command that writes having run (shown with a koto stand-in that logs its calls).
- [ ] A `label` of 128 bytes is accepted and one of 129 bytes exits 1 naming the label bound. A `question` text or an option `label` that holds a control character, or exceeds the question prompt's limits as `references/decision-presentation.md` states them, exits 1 naming the field, so `render` never has to alter a compared field.
- [ ] `--to coord`, `--to session:` with an empty or malformed name, `--to robot:x` and `--to person:someone-else` each exit 1 naming the recipient; only `session:<name>`, `anchor:<name>` and `person:owner` are taken. With no `--to`, the recipient is worked out from `koto session origin`: raised in `worker` it is `session:manager`, raised in `solo` it is `person:owner`, and raised in a session whose origin reads `unrecorded` it is `person:owner` with `unlinked` true in the output.
- [ ] Content matching a known secret shape (the shapes the repository's public-content check refuses, held as one list) in any field exits 1 without printing the matched text. A `depends_on` naming a question that does not exist, or one that would close a cycle, exits 1.
- [ ] A decision question with no undecided attempt behind it is refused: with no `--attempt`, with an id that names no attempt in the raising session's run, or with one whose `result` is `decided`, `raise` exits 1 naming the missing attempt and writes nothing. With an undecided attempt it exits 0 and the `escalate` names the attempt in its `basis`, so `koto decisions attempts --in solo --result undecided` shows the question's identity on that attempt.
- [ ] A need is raised with `need` (`credential` or `reserved-step`) and `needed` in place of `options` and with no attempt, to `person:owner` from any session; content holding both `options` and `needed` exits 1. `--state implement:1` is stored as the question's `state`.
- [ ] A question marked as standing, on the question or on an option, whose question text, option labels or reasons would not fit the prompt unshortened exits 1 naming the mark; the same content without the mark is accepted.
- [ ] With twenty open questions already addressed to a person from the session, `raise` exits 4 carrying koto's refusal and its limit of twenty, and no content is stored.

Raising: what is stored

- [ ] The stored bytes are one JSON document with the keys in the design's order (`context`, `problem`, `question`, `options` with `label`, `reason` and the optional `standing`, `ground`, `waiting`, `label`, `depends_on`, and for a need `need` and `needed` in place of `options`) and no insignificant whitespace. The same content given with its keys reordered and re-indented stores byte-identical content with the same `packet`.
- [ ] A committed golden fixture (an input, its stored bytes, its hash and its rendered output) is compared byte for byte by a test, and the pull request states that a change to any of the three is a format change that breaks restore.
- [ ] Nothing half-raised is listed. koto takes the `escalate` first and the content second, so `raise` validates everything, computes the bytes and the hash, records the `escalate`, writes the content, and reads it back. When the content write fails (shown with a koto stand-in that fails that one call), `raise` withdraws the `escalate` it just recorded with a reason naming the failed write, exits non-zero, and `koto decisions open --person owner` no longer returns it. When the process is killed between the two writes (shown by recording an `escalate` with a `packet` and no content), `pending` leaves that question out of `questions` and reports it under a separate `incomplete` list with its identity and the koto command that withdraws it, and `render` of it exits 5 without output for it.

Listing what is pending

- [ ] `shirabe question pending --in manager --person owner` prints the questions open for `owner` and `pending --in manager --at manager` those at and below `manager`. Each element carries the identity, the raising session, the question text, `label`, `need`, the count of recorded waiting work items, the age since it was raised, the recipient it was raised with, the addressee it waits on now, its `relation`, the standing mark, `unlinked`, and `depends_on`.
- [ ] `pending --in manager` with neither flag returns both sets with each question once: a question raised in `worker` and passed up to `person:owner` is one element saying both that it comes from below and that it waits on `owner`. With a koto stand-in that logs its calls, the run makes exactly one `koto decisions open --person` call and one `koto decisions open --at` call.
- [ ] The order is by count of waiting work items, most first, then oldest first by the time koto recorded the raise, then by identity compared as bytes. A question whose `depends_on` names another open question is listed as held, after the ones that can be presented.
- [ ] An open question addressed to a person other than `owner` (recorded with koto directly) is listed with a flag saying so.
- [ ] A question whose answer has arrived is shown to its asker as answered and unseen: after an answer to a question raised in `worker` is recorded elsewhere, `pending --in worker` lists it under `answered` with the answer's text, decider, session and `reading` exactly as koto prints them, on every run, until a decision in `worker`'s run cites the answer (`koto decisions record worker --kind judgment ... --basis <session>:<answer id>`); the next run no longer lists it. An owner answer given at or below a coordinator is listed for that coordinator the same way until a decision in its run cites it.
- [ ] `pending` reads and never advances a workflow: every session directory is byte-identical before and after it (lock files aside), each session's `koto status` reports the state it reported before, and the stand-in's log holds no `koto next`.

Rendering

- [ ] `shirabe question render <identity>` exits 0 and prints one JSON document whose `prompts` array holds, for each prompt, `questions`, which is the question tool's input as it stands, and `text`. In `questions`, `header` equals the `prompt_header` koto returns for the question, `question` equals the stored `question` bytes, and the option `label` values equal the stored labels in stored order with the recommendation first: a test compares each against `koto decisions content read` and `koto decisions show` byte for byte, with content holding non-ASCII text, quotes and a trailing space.
- [ ] The prompt is understood with nothing printed before it: the `question` field of each prompt entry is the context, the problem and the question as three paragraphs in that order, separated by one blank line, and `raise` stores that same composed text as the content's `question`, so the bytes koto compares are the bytes the person read. The three parts are also kept as separate fields in the stored content for listings. `text` is a plain rendering of the same content for a session that cannot open a prompt and is never required reading before a prompt. If the question tool refuses or truncates a `question` of the length the 16 KiB content limit allows, the worker's report states the limit it found, `raise` refuses content whose composed question exceeds it, and nothing falls back to printing the context before the prompt.
- [ ] Each option's `description` carries that option's stored reason, the first marked as the recommendation. `text` holds the context, the problem and the question as one paragraph each, then the recommendation and each alternative with its reason, so the rendered presentation contains every part the requirements list. A reason longer than the prompt's limit is shortened at a fixed length with a fixed marker, control characters are removed from the display fields, and markup or instructions in any field come out as the same characters, never interpreted.
- [ ] Two runs of `render` for the same question print byte-identical output (`cmp` exits 0), and so do: a run with `--in` naming another session and from another directory; a run with a cleared environment after the raising session's workflow has reached its end; a run after the raising session has been superseded by a successor; and a run after `shirabe compaction pre-compact` and `re-anchor` have been fed the committed compaction fixtures for the raising session. The output holds no time, age, path or session name that could differ between runs.
- [ ] With six questions open for `owner` carrying 5, 3, 3, 2, 1 and 0 waiting work items, `render --person owner` returns two prompts, four questions then two, in the order `pending` gives: the two with 3 are ordered oldest first, and two raised in the same recorded instant by identity. A seventh that depends on one of the six is in neither prompt and is listed as `held`; once the one it depends on is answered, the next render presents it. No prompt ever holds more than four.
- [ ] A standing mark is shown: the `text` and the `description` of a marked option, or of every option when the question is marked, begin with a fixed phrase saying the answer sets a standing rule, and `pending` shows the mark on the same question. A marked question is never shortened.
- [ ] A need renders as a request with no options: it appears in `text` form under a `requests` list with its kind and what is needed, is never placed in a prompt's `questions`, and its rendered bytes are identical across the same runs as a question's.
- [ ] A question whose stored content does not hash to its `packet` (shown by replacing the stored bytes in a copied session) is not presented: `render` exits 5 naming a content mismatch and the identity, prints nothing from the content, and `pending` lists it as `incomplete`.

Answering as the owner

- [ ] With a harness record in which a question-tool call showed exactly what `render` printed for the question and a reply chose the second option, `shirabe question answer <identity> --in manager --call <call-id> --position 1` exits 0. `koto decisions show` for the new entry reads kind `answer`, decider `person` with handle `owner`, the pointer, the mark `verified` labelled `observed`, and the option's label as its text; the command's own output carries that entry's `reading` exactly as koto prints it; and `koto decisions open --person owner` no longer returns the question.
- [ ] `answer` has no input for answer text. `--text`, `--answer` and text on standard input are usage errors that record nothing, the handle is the one constant `owner` with no flag to change it, and a test over the binary's help output finds no option of `answer` that takes a value other than the identity, the session, the call and the position.
- [ ] With no `--call`, `answer` finds the pointer itself: in the record of the harness session running the command, it takes the latest question-tool call whose question at some position carries the question's `prompt_header`, and hands koto that call and position. It reads structured fields only and prints no text from the record. With no such call it exits 4 with check `call` and records nothing.
- [ ] Each koto refusal comes back as exit 4 with koto's code `prompt_unverified` and the name of the one check that failed, distinct per case and with the entry count of the recording session unchanged, shown with one fixture each: no such call (`call`); question text differing by one byte (`question-text`); an option label changed, dropped or reordered (`options`); a denied call or a reply not from the user (`result`); a position an earlier answer already used (`call-position-reused`); a call made before the question was raised (`time`); a pointer naming a harness session other than the one running the command (`session`); a call in a subagent's conversation (`sidechain`); a header that is another question's (`identity`). No message repeats text from the harness record: each fixture carries a marker string that appears nowhere in the output.

### Step 9: A structured decision hands a question back undecided instead of assuming an answer

**Goal**: In the shirabe repository, `/decision` and the lightweight decision protocol can end with no option chosen: the result is `UNDECIDED`, carries the question, a recommendation, every alternative with its reason and what would settle it, keeps its research, and is recorded in koto through a new `shirabe question attempt`. An unattended run applies the cheap-or-costly test and records it, `/design` and `/explore` raise the question a decision hands back, and a new decision record supersedes the accepted rule that an unattended run with no coordinator stops at its first question.

Left to later steps. The decide-first state that makes a worker record an attempt before a covered exit is step 10 for `/work-on` and step 11 for `/execute` and `/scope`, and so are those skills' own passages (`skills/scope/SKILL.md` and its chain-orchestration reference keep their wording until step 11). The coordinator's scripts and passages are step 12. Listing provisional decisions through `shirabe question provisional` and `/shirabe:pending` is step 13; here a provisional decision is read back with koto's own attempts read. This step adds one subcommand, `attempt`, and no other. How `/decision` researches, produces alternatives and runs its review does not change; only how it can end does.

Names. Proposed here: `shirabe question attempt --in <session> --what <text> --result <decided|undecided|provisional> [--state <state>:<visit>] [--chosen <text>] [--undo <cheap|costly> --undo-reason <text>] [--ground <ground>] [--basis <session>:<id>]...`, with step 8's exit codes (0 done, 1 refused before any koto write, 2 usage, 3 koto missing or below the minimum, 4 koto refused). In `decision_result`, `status: "UNDECIDED"` beside `"COMPLETE"`, with `question`, `recommendation` (name and reason), `alternatives` (each a name and a reason), `missing`, `attempt` (the recorded attempt's id), `question_key` and `report_key`; a provisional decision stays `status: "COMPLETE"` and adds `provisional: true` and `attempt`. In a decision block, `status="undecided"` beside `confirmed`, `assumed` and `escalated`, which keep their meaning. `<key_dir>/question.json` for the question content the decider writes, in the form `shirabe question raise` takes. `skills/decision/scripts/check-undecided.sh <session> <report_key>` for the check a caller runs on a handed-back result. The koto names are the released ones (`koto decisions record --kind judgment` with `state` and `result`, `koto decisions attempts`). Where the release or the pull request settles on other names, the criteria and the check apply to those, the classes of result stay distinct, and the worker's report says which were used.

Rules fixed here, where the design leaves a choice. (1) Evidence "does not settle" a question when no option is a clear winner or a fact the choice rests on could not be found: the cases the block format lists today as a best guess or a close call. A choice the evidence clearly favours stays `COMPLETE`, with `confirmed` or `assumed` as today. (2) Attended or unattended is read for the session the decision runs in, the way step 8's `answer` reads it, never from the fact that a decider agent was told to run without prompting. (3) The attempt is recorded in the session that will raise the question: the caller's session when a skill called the decision (`decision_context.session` under `/design`, `explore-<topic>` under `/explore`), and the decision's own session when nobody called it; only a decision nobody called raises its own question. (4) A provisional decision is written into a document as an `assumed` block, as a best guess is today; `provisional` is the word on the koto record. (5) A caller handed `UNDECIDED` writes no chosen option and no assumption for that question, finishes the decisions that do not depend on it, and stops before the phase that needs the answer; when the answer arrives it writes the answer as the choice, citing it.

If the pull request grows past what one review can carry, the group "`/design` and `/explore` raise what is handed back" is the natural second pull request: the command, `/decision`'s own result, the protocol and the decision record are complete and checkable without it.

### Step 10: A `/work-on` run about to stop at a covered exit must record an attempt, and ends waiting on the question it raised

**Goal**: In the shirabe repository, the `/work-on` template gains a `decide_first` state in front of every exit the requirements' Appendix A lists for it: the run cannot leave until koto holds a recorded attempt for that arrival, returns to its work when the attempt decided, and otherwise raises one question and ends at a waiting terminal whose result names the question. Invoking `/work-on` again after the answer continues the waiting run with the answer in hand, and a run that reaches no covered exit is unchanged.

Left to later steps. The same state in the `/execute` and `/scope` templates, `/execute` parking an issue on a question, and resuming a child that `/execute` materialized are step 11. The coordinator reading a worker's question by identity, and re-dispatching a run that answered its leg with the waiting terminal, are step 12. `/shirabe:pending` is step 13. Until steps 11 and 12 land, a caller reads the waiting terminal as it reads a blocked run. This step adds two subcommands, `precedent` and `withdraw`, and no other.

Names. Proposed here: the state `decide_first`; the context key `decide_origin` holding the covered state the run left; the arrival name `<origin state>:<n>`, passed as `--state` to `shirabe question attempt` and `raise`, where `n` counts the run's arrivals at `decide_first` with the sessions it continues included, so no two arrivals share a name; the evidence `decide_outcome` (`decided` or `raised`) and, with `decided`, `decided_next` (`resume` or `stop`); the gate `attempt_recorded`, a command gate running `skills/work-on/scripts/decide-first-gate.sh`, with exit 0 for a deciding attempt, 3 for an undecided attempt with its open question, 1 for neither and 2 when the record cannot be read; the waiting terminal `done_waiting`, with `question` in its result; `approval_decision: needs_answer` at `deferral_approval`; `shirabe question precedent --in <session> [--label <text>]` and `shirabe question withdraw <identity> --in <session> --reason <text>`, with step 8's exit codes. The design states the gate contract as exit 0 when the submitted outcome matches the record and 1 otherwise; a gate command does not see the submission, so this step gives each state of the record its own code and lets the edges pair it with the outcome. The koto names are the released ones (`koto decisions attempts`, `koto decisions precedent`, `koto decisions answer --outcome withdrawn`, `koto init --continues --supersede --carry --expect-state`, the `questions` array of `koto next`, the `holds_question` refusal). Where the release or the pull request settles on other names, the criteria and the check apply to those, the classes of result stay distinct, and the worker's report says which were used. Before fixing the gate, the terminal and the resume edge, the worker reads the koto author guidance shipped with the released koto and `references/default-action-conversion.md`; where koto cannot express one of them (a result map on the waiting terminal, an edge selected on a context key, succession for a session bound to a leg), the worker reports it as a koto gap and does not work around it.

Rules fixed here, where the design leaves a choice. (1) "Decided" has two ways out. The attempt may choose an option that lets the work go on, and the run returns to the state it left; or it may choose to stop, which is the session's to settle when nobody else needs to decide, and the run takes the exit it was about to take, to the same terminal with the same recorded reason. (2) `deferral_approval` keeps its place after `finalization`. Its halt becomes a value that routes to `decide_first`, and its `approved` and `rejected` edges are held until the run's record has, for that arrival, a deciding attempt whose basis names an answer in effect, so an approval still rests on an answer someone other than the run gave. (3) A need, a credential or a step reserved to the person, has no attempt behind it: an open need raised from the arrival opens the `raised` edge by itself. (4) A provisional attempt counts as a deciding one. (5) The question's `state` is the arrival name, so the state a resumed run enters is the covered state it left, never `decide_first`. (6) Resume through succession covers a root run opened without a caller's leg; a materialized child and a run bound to a leg end at the waiting terminal the same way and are resumed by steps 11 and 12.

Rules fixed here, where the design leaves a choice.
